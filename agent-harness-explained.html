Agent Harness 是什么 + 怎么用好（小白向）

📅 2026-05-29 🔍 无忌 Deep Research · 3 路并行 🐴 模型=大脑 · harness=身体 📐 公式：Agent = Model + Harness 🇨🇳 全程中文白话
一句话：模型（LLM）只是个「会输出文字的大脑」，agent harness 就是套在大脑外面的「身体 + 工作流程」——让它能调工具、记事情、循环干活、出错重试、被审批管住[1]。业界 2026 年反复念的公式是 Agent = Model + Harness（agent = 模型 + 一切非模型的东西）[1]。最反直觉、也最该记的一条：同一个模型换不同 harness，分数能差出一两个模型代差——同一个 Claude Opus 放进 Claude Code 的 harness 拿到 95%、放进朴素脚手架掉到 42%[2]。所以「用好/设计 harness」是 2026 年回报最高的投入点，也正是阿杰写 CLAUDE.md / skills / Mission Control 时一直在做、只是没用这个词的事[3]。

01执行摘要：5 条最硬结论▼

3 路并行调研（是什么+为何重要 / 部件+横评 / 怎么用好+对产品的意义）收敛出的核心判断，每条独立成块，方便扫。

✅ 结论 1：Agent = Model + Harness——模型是大脑只会吐文字，harness 是身体让它真能干活 🟢 多源共识

2026 年业界统一口径：一个 AI agent = 模型本体 + 模型之外的一切（工具执行、循环、上下文管理、记忆、权限、错误处理、子 agent 编排）[1]。模型负责智能，harness 负责控制。LangChain 的一句口号把它钉死：「如果你不是那个模型，你就是 harness」[4]。Anthropic、MongoDB、HuggingFace、Martin Fowler 口径一致，是当前最稳的共识锚点[1]。Claude Code 自述就是「the agentic harness around Claude」[1]。

🎯 结论 2：同一个模型换 harness，提升能超过升一代模型——harness 是回报最高的投入点 🟡 数字区间

多组同模型对比：同一个 Claude Opus 放进 Claude Code harness 在 CORE-Bench Hard 拿 95%、放进朴素 Smolagents 掉到 42%（差 53 分；MongoDB 给同基准是 42%→78%，不同来源在 78%~95% 区间，引用时取"差距巨大"而非绝对数）[2]。LangChain 只换 harness、同模型把 Terminal-Bench 2.0 从 52.8% 提到 66.5%（+13.7 分），比同期升一代模型（SWE-bench 只 +6.8 分）涨得还多[5]。结论一句话：先把 harness 调好，再考虑换更贵的模型[3]。

💡 结论 3：一个 harness 由 7-9 类部件组成，每缺一件就退化成普通聊天机器人 🟢 多源

生产级 harness 的标准部件：① Agent Loop（while 循环）② 工具/函数调用 ③ 上下文/记忆管理 ④ 权限与审批 ⑤ 错误处理与重试 ⑥ 子 agent 编排 ⑦ 可观测性/会话持久化，外加 Skills、生命周期 hooks、系统提示流水线[6]。缺了会出什么问题很具体：没循环=只是聊天机器人；没上下文管理=会话变长后自相矛盾；没权限层=「有用工具和危险工具的分界线」消失，agent 会删不该删的[6]。用 OODA 框架打个比方（⚠️ 这是无忌的类比、非 Anthropic 原话）：Observe/Orient/Act 大致都靠 harness、模型主要强在 Decide——Anthropic 原文表述是 gather context → take action → verify work → repeat[7]。

🧭 结论 4：harness 不是越多越好——做减法常比加功能更提质 🟢 一手实测

Vercel 一个小样本（5 个 text-to-SQL query）实测砍掉 80% 的工具：成功率 80%→100%，平均快约 3.5×、token 降约 37%（724s→141s 是最坏单条 query、非平均，同模型）[8]。更深一层警告：「为旧模型写的脚手架会拖累新模型」——强制 Claude 一次只改一个文件的规则，对 2024 年模型有用，对能跨文件协同的 2026 模型反而是「dead weight（死重）」[9]。所以 harness 要随模型迭代清理，单 agent 别堆超过 5-7 个高相关工具，多了拆子 agent[10]。

⚠️ 结论 5：做 AI 产品——模型已商品化趋同，harness 才是体验和护城河 🟡 厂商博客为主

「赢家不是拿到最好模型的人，是围着一个够用的模型造了最好 harness 的人」[11]。88% 企业 agent 项目到不了生产，失败几乎从不是模型——是 context rot（上下文腐烂）、缺护栏、无状态持久化、反馈环不闭合，全是 harness 工程问题[12]。一手实物证据：2026-03 Anthropic 误传 51.2 万行 Claude Code 源码到 npm，第三方拆解发现仅约 1.6% 是 AI 决策逻辑，98.4% 是 harness（权限/上下文/沙箱/工具路由/恢复）[13]。

02一句话讲懂 harness：挽具类比 + 大脑/身体▼

先把心智模型钉死，后面所有章节都用这条主线：模型 = 大脑（只会吐文字），harness = 身体 + 工作流程（让大脑真能干活的脚手架）[1]。

「harness」这个词本义是「挽具」（套马的缰绳、马具）。一匹马力气很大，但不套挽具就没法拉犁干农活；挽具把马的力气「导」向有用的活[16]。LLM 同理——智能在脑子里，但没有工具/记忆/状态/护栏/编排，这股智能就没法稳定干活[16]。

2.1 给小白的四个类比（讲的时候直接用）

类比怎么讲对应到 harness 的什么
① 挽具马力气大，不套挽具拉不了犁[16]智能要靠工具/护栏才能产出有用的活
② 大脑 vs 身体模型是大脑，harness 是身体、神经系统、操作系统、工具箱、规则手册[16]整个执行层 + 控制层
③ 发动机限速器harness 像发动机上的调速器（governor），挡住乱来的行为、放行有用的工作[16]权限/护栏层
④ 健忘症工程师没 harness 的 LLM 像每天清空记忆、重新上班的工程师；harness 给它日志/记忆/状态，能跨天接续[16]记忆 + 会话持久化层

另一个工程师爱用的类比：操作系统

模型 = CPU、上下文窗口 = RAM、harness = 操作系统、agent = 应用[17]。harness 作为 OS 负责「curate（整理）上下文、处理 boot 序列（提示/hooks）、提供标准驱动（工具）」。这就是为什么 2026 年 harness 比模型更被关注：传统 benchmark 测不出「第 50 次、第 100 次工具调用后模型怎么表现」，而那正是真实 agent 的战场[17]。

2.2 术语关系：Agent / Model / Harness / Scaffold / Framework

这几个词容易绕晕，HuggingFace 2026-05 官方梳理了一份，先锚定最大共识再细分[1]：

术语白话一句话区分
Agent最大的概念，能在循环里行动的完整系统= Model + Harness 合起来[1]
Model（LLM）大脑本体，文字进文字出，无记忆、无循环只负责"想"那一下[1]
Harness执行层：调模型、处理工具调用、决定何时停「怎么跑模型」[1]
Scaffold（脚手架）harness 里偏"行为定义"的那层：system prompt、工具描述、上下文管理「模型看到什么」[1]
Framework实现 harness 的软件包/抽象（LangChain、Claude Agent SDK）用来"搭" harness 的工具[1]

⚠️ 各家用词略有出入：firecrawl / MongoDB 把工具/记忆/护栏全算进 harness，HuggingFace 把 scaffold 单列[1]。讲小白时先锚定「Agent = Model + Harness」这个最大共识，再细分，别一上来就纠结 scaffold 是不是独立的[1]。

2.3 词源：harness engineering 怎么成的热词

HashiCorp 联创、Terraform 作者 Mitchell Hashimoto 2026-02 在博客提出「harness engineering（脚手架工程）」，第一次给"模型之外的一切"起了个统一的名字——prompt engineering 给不了这个名字；几天后 OpenAI 工程师跟进发实测数据，词迅速扩散[15]。Martin Fowler 站的 Birgitta Böckeler 2026-04 进一步定义，区分 guides（前馈控制）和 sensors（反馈控制）两类[18]。harness engineering 的本质纪律：每次 agent 犯错，就在环境里焊一个"让这个错结构上不可能再犯"的修复，并设计反馈回路在错误到人眼前自我纠正[18]。⚠️ "谁第一个用"有争议——Hashimoto 是普及者而非唯一源头[15]。

3.2 量化「harness 是大头」

MongoDB 类比 2015 年 Sculley 的 MLOps 论文（《机器学习是机器学习系统里最小的一块》）：生产级 governed agent 里每个 token 约需 50 行支撑代码，而周末玩具 chatbot 约 1 行/token——LLM 调用只是几行[20]。同时另一组数据：65% 企业 AI 失败可追溯到 Harness Defects（Context Drift 上下文漂移 / Schema Misalignment 结构错位 / State Degradation 状态退化）[6]。前沿模型能力已足够接近，差异化转移到"包模型的那层"——harness[12]。

3.3 为什么 2025-2026 突然成热词（三个原因）

① 词源——Hashimoto 2026-02 第一次给"模型之外的一切"起了统一名字[15]。② 模型升级变慢、harness 创新变快——大家发现"换 harness 比换模型涨分还多"[5]。③ 厂商商业模式转向——「Anthropic 不再卖 Claude，而是卖 Claude Code / Cowork / Agent SDK」，harness 成了护城河和锁定点；模型代际升级（4.5→4.7）SWE-bench 仅 +6.8 分，少于单换 harness 的涨幅[21]。模型与 harness 在数月 post-training 中「焊死」，拆开就掉性能，形成 co-evolution 锁定[21]。

⚠️ 辩证点（重要）：harness 不是越多越好。「为旧模型写的脚手架会拖累新模型」——强制 Claude 一次只改一个文件的规则，对 2024 年模型有用，对能跨文件协同的 2026 模型反而是 dead weight[9]。harness 要随模型迭代清理，详见第 9 章误区。

04一个 harness 由哪些部件组成▼

把「身体 + 工作流程」拆开看——一个把"只会吐文字的模型"变成"能干活的 agent"的 harness，靠七到九类部件。每个部件缺了会出什么问题，列在表里[6]。⚠️ 部件划分各家略有出入（有的把 sandbox/filesystem 单列、有的并入工具），无统一标准，下面取最常见的归类[6]。

4.1 核心 7 大部件

部件白话作用缺了会怎样
① Agent Loop（while 循环）反复「调模型→解析输出→执行工具→喂回结果→判断是否停」[6]没有它就只是聊天机器人
② 工具/函数调用把文件、bash、API、MCP server 暴露给模型，用原生 tool_calls 结构化调用[6]大脑没手脚，干不了实事
③ 上下文/记忆管理系统提示拼装 + 历史 + 压缩（compaction）+ 跨会话记忆文件；Claude Code 在约 80-90% 窗口触发压缩[6]会话变长后自相矛盾
④ 权限与审批只读/工作区/完全访问分级 + 路径检查 + 高危动作人工批准[6]「有用工具和危险工具的分界线」消失，删不该删的
⑤ 错误处理与重试按失败类型分类、限次、重试间必须改计划，强制"先过验证才能给最终答案"[6]陷入死循环
⑥ 子 agent 编排「spawn-restrict-collect」：派隔离的子 agent 干并行/专项、限工具、只回收摘要[6]主 agent 上下文膨胀
⑦ 可观测性/会话持久化append-only 事件日志、tracing、可崩溃重放[6]出错查不到、崩了续不上

此外还有 Skills / 渐进式披露（只在需要时加载信息）、生命周期 hooks、系统提示流水线（动态注入 CLAUDE.md / AGENTS.md）[6]。89% 组织已上某种 observability、62% 有逐步 tracing[6]。

4.2 用 OODA 框架理解（无忌的类比，非 Anthropic 原话）

OODA = Observe（观察）/ Orient（定向）/ Act（行动）/ Decide（决策）。⚠️ OODA 是本报告借来的类比，不是 Anthropic 的原话——其 Agent SDK 原文是 gather context → take action → verify work → repeat[7]。套到 OODA 上理解：Observe / Orient / Act 大致都靠 harness，模型主要强在 Decide。一个推论：文件夹/文件结构本身就是一种 context engineering，Skills 用渐进式披露只在需要时加载信息[7]。

4.3 一手架构范式：Anthropic Managed Agents 的三件解耦

Anthropic 工程博客（2026-04-08）把 managed agent 解耦成三个接口，这是 Agentic OS / 控制层最权威的一手设计范式[9]：

  • Session = append-only（只追加）事件日志，是「活在上下文窗口之外的持久 context 对象」[9]
  • Harness = 调 Claude + 路由工具调用的循环；无状态 brain 设计成「cattle not pets（牲口不是宠物）」，崩了用 wake(sessionId) + getSession(id) 从事件日志续跑[9]
  • Sandbox = 执行环境，凭据存外部 vault 不进代码执行环境[9]

用 OS 抽象类比：read() 不关心是 1970s 磁盘还是现代 SSD，工具接口 execute(name,input)→string 对未来 harness 不持立场[9]。

框架风格强弱

5.2 评测标尺：Terminal-Bench 2.0 按「harness+模型配对」排名

2025-11 发布，89 个任务，关键是按「harness+模型配对」排名而非单看模型，证明了核心论点[14]。同一个 Claude Opus 4.6 在 ForgeCode 上 79.8%、在 Capy 上 75.3%——4.5 个点差距纯来自 harness[23]。⚠️ 各来源绝对分数口径打架（有源称 Claude Code 92.1%、另有源同模型仅 75-80%），引用时只用"相对差距"[14]。

5.3 最深的一层：model-harness-fit（换模型不是换皮）

模型在后训练时就把 harness 的约定「烤进了权重」——编辑用 apply_patch vs old_string/new_string、记忆引用标签、系统提示分节[23]。所以「换模型不是换皮——模型一动，它上面所有东西都得跟着动」。真正的多模型支持要给每个模型配它自己的工具面（per-model tool surface），而非搭一个翻译层[23]。例：Codex 发 <oai-mem-citation> 标签 Claude 没有；Copilot CLI 只给 Codex 系开 apply_patch、只给 Claude 开 ToolSearch[23]。

06怎么"用好"现成 harness（配工具/写规则/管上下文/选自主度/护栏）▼

「用好现成 harness」（阿杰已经在做的）拆成 5 件事。这 5 件是从"用"跨到"设计"的台阶[3]。

6.1 配工具 = 给大脑装手脚（MCP 标准）

MCP（Model Context Protocol）是 2025 年给 agent 装工具的事实标准。白话：你写一个 MCP server 包住某个 API/数据库/工具，所有兼容客户端（Claude/Cursor/Copilot/VS Code）都能即插即用，不用每个 AI 单独写集成[27]。三个角色：Host（AI 跑的地方）、Client（连接器）、Server（工具包装层）；tools/list 发现工具、tools/call 调用[27]。

⚠️ 工具一多会撑爆上下文。Anthropic 的解法「Code Execution with MCP」：不把几百个工具当函数直接暴露，而是当成文件系统上的代码 API，agent 按需探索加载、写代码调用，大数据在执行环境处理完只把摘要带回——案例把 token 从 150,000 降到 2,000，省 98.7%（代价是需要沙箱）[28]。

6.2 写规则文件 = CLAUDE.md / AGENTS.md / .cursorrules

每次 session 自动加载的项目规则文件，告诉 agent「项目是什么（WHY）、技术栈和结构（WHAT）、怎么跑测试/构建/验证（HOW）」——阿杰已经在写[29]。要点：推荐 <300 行，根文件理想 <60 行；前沿模型可靠遵循 150-200 条指令（Claude Code 系统提示已占 ~50 条）；别让 LLM 干 linter 的活（代码风格交给 ESLint/Prettier）[29]。这是最高杠杆点，但写太长模型会忽略一半，任务专属指令该放 prompt 不该放这里[29]。

6.3 Agent Skills = 按需加载的领域能力（SKILL.md + 渐进式披露）

Anthropic 把「按需加载的领域能力」做成可复用原语：一个文件夹装指令+脚本+资源，三层加载——启动只读 YAML frontmatter 的 name/description；判断相关才读 SKILL.md 正文；需要细节才读附带的 reference.md[30]。正是阿杰写的那些 skill。要点：SKILL.md 正文建议 <500 行，超了拆文件；可跨 Claude.ai/Claude Code/Agent SDK 复用；一个 agent 能挂几百个 skill 不爆内存[30]。⚠️ description 写不好不会被触发；只装可信来源的 skill[30]。

6.4 选自主度 = 一条光谱，按风险分级

不是「人盯 vs 全自主」二选一，而是一条光谱：L0 只观察 → L1 告知 → L2 带理由推荐 → L2 需审批后执行 → … 全自主[31]。危险操作（删数据/改生产/花钱/改配置）必须先人工审批。推荐策略：先对所有动作设审批门，再随信心增长逐步放开自主[31]。

6.5 加护栏 = 硬边界 + 预算上限 + 沙箱 + 审批门

护栏 = agent 不能越的硬边界，没护栏就不算生产就绪[31]。构造哲学：「Humans steer. Agents execute（人掌舵，agent 执行）」——确定性强制（linter/CI 门）胜过概率性遵从（提示里写指令）[32]。具体手法：禁用 inline-suppress（不准 // eslint-disable）防 agent 绕约束；lint 错误嵌修复指令而非只贴违规标签；Plan-Execute-Verify（PEV）架构门控转移[32]。

6.6 生产级 harness 的 5 层架构（设计蓝图）

当你从"用"跨到"设计"，一个生产级 harness 有 5 层[6]：① 工具编排（选/链/执行工具 + 错误恢复）② 验证循环（执行中插单测/自我批判，fail-fast）③ 上下文与记忆 ④ 护栏（硬边界/预算上限/沙箱/人工审批门）⑤ 可观测性（执行追踪/审计日志）[6]。⚠️ 层的划分各家略有出入，是博客视角非学术。

07上下文工程速览（context engineering）▼

Context engineering（上下文工程）是 2025 年新兴的核心手艺，被 Anthropic 称为「prompt engineering 的下一代」[33]。它在 harness 部件里属于"上下文/记忆管理"那层，但太重要，单列一章。

核心信条：找最小的高信号 token 集合

Anthropic 2025-09 官方文章原话：「每个多余的词、每条冗余工具描述、每块陈旧数据都在主动拉低 agent 表现」[33]。一句话：少即是多。

7.1 核心技术三招

技术白话
right-altitude 系统提示"高度适中"——既不硬编码脆弱逻辑，也不空泛[33]
just-in-time 检索只存路径/链接，按需加载，别一次性塞满[33]
长任务三招compaction（压缩历史）+ structured note-taking（外部记忆/记事本）+ sub-agent（隔离上下文，回传 1000-2000 token 摘要）[33]

7.2 什么是 context rot（上下文腐烂）

context rot = 上下文越满，模型表现越差（即使没超限）——有效上下文窗口远小于标称值[10]。这就是为什么"塞得越多越好"是错的。相关常见坑：系统提示当数据库塞（6000-token 覆盖所有边界情况），应从 <1000 token 起步，看到失败才加规则[10]。

7.3 模型级失败可被 harness 设计修掉

Anthropic 研究指出三种模型级问题靠 harness 解决[6]：victory declaration（没验证就宣称完成）、context anxiety（上下文将满时草率决策）、one-shotting overreach（一次硬啃整个问题）[6]。对策：把验证做进执行中途（单测/自我批判）而非末尾，fail-fast 防止小错滚雪球[6]。Anthropic 长任务 harness 的做法：init agent + coding agent 两段式 + claude-progress.txt + git history 续接，每个新会话对之前零记忆[34]。

8.2 六个直接可用的升级点

① 你有现成的"权威话术"对外讲

公式 Agent=Model+Harness、「Claude Code 98.4% 是 harness 只有 1.6% 是 AI 逻辑」、「同一个 Opus 换 harness 差 53 分」——这些是给团队/用户/投资人解释「为什么做产品不是套个 GPT 就完事」的最佳弹药[13]。你做 AI 学习产品、用户在国内，这套话术能立刻让人懂「模型谁都能调，护城河在 harness」[11]。

② Vercel 砍 80% 工具直接打你的痛点——审一遍 30+ 个 skill

Vercel 砍掉 80% 工具反而成功率 80%→100%[8]。按这个证据，你 30+ 个 skill 里工具/skill 太多会拖累 agent 判断——建议审一遍哪些 skill 真在用、哪些是死重，做减法可能比加新功能更提质[8]。单 agent 别超 5-7 个高相关工具，多了拆子 agent[10]。

③ 「旧 harness 是 dead weight」是给 Mission Control 的架构警告

Anthropic managed-agents 把系统解耦成 Session(append-only 日志)/Harness(无状态循环)/Sandbox 三层、凭据放外部 vault——这正是你做异构 agent 控制层该抄的范式[9]。harness 要无状态、可独立演进，别把"为今天模型写的规则"硬编码进去，否则模型升级后全是死重。你 CLAUDE.md 里那些"强制单文件编辑"式规则，每隔几月该清一遍[9]。

④ 跨模型控制层：别搭翻译层，要 per-model tool surface

当你把 MC 做成跨模型（Claude + Gemini 逍遥 + Codex）的控制层时，别想着搭一个"翻译层"让所有模型共用一套工具面，要给 Codex 系开 apply_patch、给 Claude 开 string-replace/ToolSearch[23]。否则给模型不熟的工具会多烧 reasoning token 还更易出错[23]。协议上：MCP 管纵向 agent-to-tool，A2A 管横向 agent-to-agent——你要编排无忌/三丰/逍遥这些异构 agent，A2A 这条线值得看一眼[35]。

⑤ context_notes 续接 = Anthropic 长任务两段式的同一招，可再进一步

你 CLAUDE.md 里「session 结束前更新 context_notes 续接下一个 session」+「开工读 MC 状态」，跟 Anthropic 长任务 harness 的 init-agent + coding-agent + claude-progress.txt + git history 两段式是同一招[34]。可以更进一步：让 MC 自动给每个任务塞一个机器可读的 progress/feature-list（初始全标失败），让 worker agent「每次只推进一个 feature、做完强制自验证」，把 Codex 跨模型审查升级成 harness 里固化的 Verify 门（PEV），而非靠提示自觉[34]。

⑥ 给半米（国内 K12 学习产品）的提醒

把 agent 塞进半米时，决定体验的是 harness 的护栏和上下文质量，不是模型。学习产品里"答案泛泛/健忘"几乎都是检索和记忆设计问题，不是模型不行[11]。自主度光谱直接可落地：给 MC 任务加 risk/autonomy 字段，危险操作（删 Roam/改生产/花钱）强制 review，低风险自动跑——和你 --dangerously-skip-permissions 无人 session 是同一套思想的两端[31]。

⚠️ 中文锚词建议

中文世界对 harness 译法未统一（挽具/脚手架/控制层/工程化外壳）[1]。给国内用户讲时最好自己定个锚词（无忌倾向「控制层」或保留英文 harness + 一句"给模型套的挽具"），别让用户在"脚手架/外壳/框架"里绕晕。

09常见误区▼

小白（和不少团队）最常踩的几个坑，全是 harness 工程问题。

❌ 误区 1：工具堆越多越好

企业常给单 agent 暴露 20-30 个工具导致「选择瘫痪」，建议拆成每个子 agent 5-7 个工具[10]。工具使用率低于 10% 说明在浪费 token[10]。Vercel 砍 80% 工具反而成功率 80%→100% 就是铁证[8]。

❌ 误区 2：系统提示当数据库塞

最常见错误是 6000-token 系统提示覆盖所有边界情况，应从 <1000 token 起步，看到失败才加规则[10]。「每个多余的词都在主动拉低 agent 表现」[33]。

❌ 误区 3：以为 context rot 不存在（塞满也没事）

上下文越满模型表现越差，即使没超限——有效上下文窗口远小于标称[10]。这是"少即是多"信条的物理基础[33]。

❌ 误区 4：harness 写一次就一劳永逸（旧规则成死重）

「为旧模型写的脚手架会拖累新模型」——强制单文件编辑的规则对 2024 模型有用，对 2026 跨文件协同模型成 dead weight[9]。harness 要随模型迭代清理，不是越多越久越好[9]。

❌ 误区 5：靠"提示里写指令"约束 agent（概率性遵从）

「确定性强制（linter/CI 门）胜过概率性遵从（提示里写指令）」[32]。提示里写"不准 X"模型有概率违反，焊一个结构性门（如禁用 // eslint-disable）才能让错"结构上不可能再犯"[32]。

❌ 误区 6：以为换模型就能解决问题（其实是 harness 缺陷）

88% 企业 agent 到不了生产，失败几乎从不是模型——是 context rot、缺护栏、无状态持久化、反馈环不闭合[12]。多数 AI 抱怨（健忘/答案泛泛）是记忆和检索问题不是模型问题[11]。

10FAQ▼

Q一句话，agent harness 到底是什么？+

模型是「会输出文字的大脑」，harness 是套在大脑外的「身体 + 工作流程」——让它能调工具、记事情、循环干活、出错重试、被审批管住[1]。公式：Agent = Model + Harness[1]。

Qharness、scaffold、framework 有啥区别？+

scaffold = 模型"看到什么"（system prompt/工具描述）；harness = "怎么跑模型"（含 scaffold + 循环 + 工具执行 + 停止判断）；framework = 用来"搭" harness 的软件包（LangChain/Agent SDK）[1]。各家用词略有出入，先锚 Agent=Model+Harness 再细分[1]。

Q换更好的模型，还是先调 harness？+

先调 harness。同模型换脚手架的提升能超过升一代模型：CORE-Bench 42%→95%（区间）、LangChain +13.7 分 vs 升一代仅 +6.8 分[2][5]。harness 是回报最高的投入点[3]。

Q工具是不是给 agent 配越多越好？+

恰恰相反。Vercel 砍掉 80% 工具，成功率 80%→100%、token 降一半、延迟 724s→141s[8]。单 agent 别超 5-7 个高相关工具，使用率低于 10% 就是浪费 token[10]。

Q写 CLAUDE.md / skill 该写多长？+

CLAUDE.md 推荐 <300 行、根文件理想 <60 行；SKILL.md 正文 <500 行超了拆文件[29][30]。写太长模型会忽略一半（context rot），从短起步、看到失败才加规则[10]。

QClaude Code 和 Cursor / Codex 选哪个？+

看场景：Claude Code = agent 编排器，适合无人值守过夜跑、上下文连贯，但锁 Anthropic、token 高 3-4x[22]；Cursor = IDE-first 监督式，遇模糊决策点就停、需人盯[25]；Codex token 低 3-4x 但跨会话不建关系[23]。它们的工具面不互换（model-harness-fit）[23]。

Q什么是 context engineering（上下文工程）？+

Anthropic 称为"prompt engineering 的下一代"，信条是找最小的高信号 token 集合——少即是多[33]。三招：right-altitude 系统提示、just-in-time 检索、长任务靠 compaction + 外部记事本 + 子 agent 隔离[33]。

Q怎么管住 agent 不干危险的事？+

自主度是光谱（L0 只观察→全自主），按风险分级：删数据/改生产/花钱必须先人工审批[31]。推荐"先对所有动作设审批门、随信心放开"[31]。靠确定性门（linter/CI）而非"提示里写指令"[32]。

Q做 AI 产品，护城河在模型还是 harness？+

模型已商品化趋同，harness 才是体验和护城河。「赢家不是拿到最好模型的人，是围着够用模型造了最好 harness 的人」[11]。88% 企业 agent 死在 harness 不是模型[12]。

Q阿杰写 CLAUDE.md / skills，算在做 harness 吗？+

算，而且已经跨到"设计"层。CLAUDE.md=系统提示流水线、skills=渐进式披露、MC+context_notes=会话持久化/控制平面、Codex 审查=验证循环[9][30]。你不是在写提示，是在做 harness 工程[12]。

Qharness 写一次就不用管了吗？+

不行。「为旧模型写的脚手架会拖累新模型」成 dead weight，模型升级后旧规则该清[9]。harness engineering 的纪律：每次 agent 犯错就焊一个结构性修复，并随模型迭代清理[18]。

Qharness 中文该叫什么？+

中文未统一（挽具/脚手架/控制层/工程化外壳）[1]。无忌建议给国内用户讲时锚定「控制层」或保留英文 harness + 一句"给模型套的挽具"，别在多个译法里绕晕[1]。
