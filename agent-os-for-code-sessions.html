给 AI Code Session 做一个操作系统

📅 2026-05-29 🔍 无忌 Deep Research · 5 路并行 🧩 编排 + 监控 + 多项目 三合一 🤖 统管异构 agent 📚 47 来源 🔬 经 Codex 跨模型审查
一句话：在 Wave Terminal 上做"管 N 个异构 agent 的操作系统"，技术底座完全可行，但定位要摆正——Wave 给的是三大能力的现成原语（block + wsh + badge），不是开箱即用成品。真正的核心价值得落在你的 Mission Control（编排大脑 + 任务依赖 + 状态机），Wave 当"可视化 + 进程托管外壳"。最大的活儿是 agent-agnostic 抹平层——Claude Code / Codex / Gemini 的事件机制各不相同，得自己写薄 adapter。一条正在成型的行业主张是 "标准化控制平面，而不是标准化 agent"，"工程师 = AI Orchestrator" 也正成为主流叙事，你做的这件事方向完全对。

01执行摘要：5 条最硬结论▼

5 路并行调研收敛出的核心判断，每条独立成块，方便扫。

✅ 结论 1：Wave 底座可行性 = 高，但它是"原语"不是"成品" 🟢 多源

Wave Terminal（wavetermdev/waveterm，Apache-2.0，约 20.9k stars，最新 v0.14.5/2026-04-16）的三件套 Block + wsh + badge 天然覆盖你要的三大能力[1][4]：编排（wsh run --cwd <项目> -- claude/codex/gemini 脚本拉起任意 agent block）、监控（badge rollup 在 tab 聚合多 session 状态）、多项目（workspace/tab 隔离）。但这些是积木，编排逻辑还得你自己拼。

⚠️ 结论 2：最大的活儿是"异构 agent 抹平层"——Wave 官方只给了 Claude 专属集成 🟢 多源

Wave 的官方"Claude Code Integration"寄生在 Claude Code 自己的 lifecycle hooks 上（permission_prompt/Stop/PreToolUse 调 wsh badge 亮状态灯）[5]。好消息（经 Codex 跨模型核查修正）：Codex / Gemini 也各有 hook 机制——Gemini CLI 有成熟 hooks（.gemini/settings.json，BeforeTool/AfterTool/SessionStart 等，可阻断）[46]、Codex 有 codex-hooks 引擎 + hooks.json（仍在演进，plugin 加载路径未完全落地）[47]。所以抹平层是"把三家各自的 hooks/事件统一映射成 MC 状态灯"，是真活儿但不是空白未知。这也是 Warp 据称已原生抹平（🟡 无独立 citation）、而你在 Wave 上要自建的差异点。

🎯 结论 3：监控这一路有"天降标准"——三大 agent 都内置 OpenTelemetry 🟢 多源

Claude Code、OpenAI Codex CLI、Google Gemini CLI 都内置 OTLP 导出，且都向同一标准（OTEL GenAI gen_ai.* 语义约定）靠拢[12]。VictoriaMetrics 实测：一个 OTEL Collector 同时吃 CC/Codex/Gemini/Qwen[13]。所以 agent-agnostic 监控不靠某个 SaaS 拼 SDK，而是"一个 Collector 端点接所有 agent"这个架构事实。监控层别自己造轮子。

🔁 结论 4：别从零设计编排——已有现成同构物可抄 🟢 多源

agent-kanban（leader-worker + depends_on 环检测 + 子任务 + SSE 监控 + 人审 merge + CC/Codex/Gemini/ACP 多 runtime）几乎就是 Mission Control 的开源同构物[9]；想要确定性可审计引擎看 Bernstein（Goal→TaskGraph→并行→Janitor 门禁→merge，44 个 CLI adapter）[10]；同名的 builderz-labs/mission-control（5.1k★）有 adapter 抽象 + 26 个监控面板可借鉴[24]。

🧭 结论 5："标准化控制平面，不标准化 agent" + 2027 工程师 = Orchestrator 🟢 多源

2026 正在成型的架构主张：让开发者各用各的 CLI，但所有 agent 都过同一个 gateway hop，统一拿可观测/成本/审计/策略[23]。这正是你的 Agentic OS 该采用的原则。而"管理 agent = 未来核心技能"已被 Karpathy、Cognition（"Devin 管 Devin"）、Cursor 多方背书[25][26]——你做的不是工具，是"一个人当一支队伍"的操作系统。

一句话路线建议

Wave 当"终端侧 agent OS 外壳"（呈现 + 进程托管），Mission Control 当"编排大脑"（任务依赖 + 状态机 + 抹平层 adapter），监控直接嵌 OTEL Collector + SigNoz/Langfuse。第一步先用 Claude Code 一个 agent 在 Wave 里把"启动 block + badge 状态灯 + MC 任务回写"这条最窄链路跑通，再加 Codex、再加 Gemini。详见第 11 章决策树。

🔬 跨模型审查说明（这份报告被 Codex 审过一轮）

本报告由 Claude 写稿后，经 Codex (GPT-5.5) 四维度对抗审查（事实 / 深度 / 缺失 / 角度）。最大修正：初稿把"Codex / Gemini 有没有 lifecycle hooks"列为项目最大未知（标 🔴），Codex 作为当事方核查后纠正——三家都有 hook 机制（Gemini 成熟[46]、Codex 引擎演进中[47]、Claude 最全），项目最大工程风险因此下调。这正是异源跨模型审查的价值：同源模型查不出自己的盲点。

Codex 提出、本版有意未展开的"阶段二待深化"清单（现在先跑通最窄链路，避免过度工程）：

  1. hook 安全 / 信任边界——hooks 执行本地命令，untrusted repo 的 hook config 是供应链风险
  2. 进程恢复模型——block 死 / agent 退出未触发 hook / Collector 宕机时的 reconciliation、心跳、孤儿清理
  3. telemetry 隐私——OTEL 可能含 prompt / 文件路径 / 代码片段，需 redaction + local-only 档
  4. license 商用分析——AGPL / FSL / 闭源各异，要分清能 embed / 能 fork / 仅参考
  5. 状态机契约——hook 事件 → running/waiting/approval/done/error 的精确映射 + agent profile schema
  6. 命名——严格说这是 control plane + 进程监管 + 终端外壳，"操作系统"是修辞

02概念拆层：什么是 "Agent OS for Code Sessions"▼

先把概念焊清楚，后面所有对比才有坐标。阿杰要做的东西 = 一个统一的容器/控制层，把 N 个独立 CLI coding agent（Claude Code、Codex、Gemini…）的启动、状态、产出、成本统管起来，让一个人能像"操作系统调度进程"一样调度 agent。它要同时解决三大能力 + 一个硬约束。

2.1 三大能力定义

① Workflow 编排（Orchestration）

把高层目标拆成任务、按依赖关系（depends_on）派给不同 agent、并行跑、在人审/merge 节点把关。2025-2026 范式已从"单 agent 结对（conductor）"转向"一个人编排 N 个 agent（orchestrator）"，瓶颈从生成转为验证[6]。

② 监控 / 可观测性（Observability）

一眼看全局：谁在跑、谁在等你输入、谁出错了、花了多少 token/钱。核心痛点不是启动而是"哪个 agent 卡住等我输入了"。状态总览要做 running / waiting / idle / error 四态检测[20]。

③ 多项目 / 多 session 管理

跨多个 repo / 项目隔离地跑 N 个 session 不打架。底层隔离范式收敛到两条：git worktree（轻量、共享本机环境、切换成本低）和 Docker 容器/microVM（强隔离、避免依赖污染、有冷启动成本）[18]。

2.2 硬约束：异构 agent 为什么是难点

⛔ 这是全篇的核心难点。阿杰要统管的是异构 agent——Claude Code、Codex CLI、Gemini CLI 是三家不同公司、三套不同的启动方式、配置、hook/事件机制、输出格式、鉴权。市面上真正 agent-agnostic 的工具是少数派：终端/TUI 类（cmux、Claude Squad、agent-deck）或 MCP 协议层（container-use）能做到，因为它们把 agent 抽象成"任意可启动的 CLI"或"任意 MCP server"；而图形桌面 app（Conductor/Sculptor/Nimbalyst）几乎都只支持 Claude Code + Codex 两家，覆盖不到 Gemini[19]。

💡 为什么会这样？桌面 app 要为每家 agent 做深度 UI 集成，成本高 → 收窄到 2 家。所以阿杰若坚持异构（含 Gemini CLI），只能走"CLI 抽象"或"MCP 抽象"路线，不能走深度集成桌面 app 路线——这条原则决定了后面所有选型。

2.3 学术界的六层栈（给你的能力地图）

MindStudio 提出的 Agentic OS 六层框架可以给你的 OS 做能力地图：Model / Memory / Tool-Integration / Orchestration / Workflow / Interface(人机交互与监控)[27]。它警告：多数早期部署只做了 Model + Workflow 两层，Memory 和 Orchestration 后补会成技术债。你既然要重做 OS，把这两层一开始就当一等公民。

⚠️ 学术映射的局限：ASPLOS 2026 的 AgenticOS workshop 把"OS 要为 agent 重新设计"写成共识（五大问题=资源管理/隔离/状态/可观测性/虚拟化）[28]，但学术原型（AIOS/Letta）管的是框架级 LLM agent，不是 Claude Code / Codex 这类终端 CLI agent，抽象层级和你的需求错位——只能当"OS 词汇表/记忆层设计"借鉴，不能直接拿来用（详见第 7 章）。

是什么：开源跨平台 AI 集成终端，核心是可拖拽平铺的 Block 系统（终端/Web/编辑器/AI chat 都是 block，MVVM + Jotai 管理，组织成 tab/workspace）[2]。后端经 RPC（CreateBlockCommand 等）管理 block 生命周期，配 SQLite。

3.1 三大能力如何映射到 Wave 原语

你要的能力Wave 现成原语怎么用
① 编排wsh run + RPCMission Control shell 调 wsh run --cwd <项目> -- claude/codex/gemini ... 脚本化拉起任意 agent 的 block，wsh setvar 跨 block 传数据[3]
② 监控wsh badge + badge rollup抄 Claude Code badge 范式：每个 agent session 一个 block，hook→wsh badge 亮状态（等审批/完成/出错），tab badge rollup 一眼看全局[5]
③ 多项目workspace / tabworkspace/tab 天然隔离多项目；workspace-scoped widgets（widgets.json 按 workspace 显隐）[3]

3.2 优势（为什么选 Wave 对）

✅ Apache-2.0 自由 fork + 扩展点清晰：可自由在上面搭私有层；repo 有 CLAUDE.md + skill guides 教怎么加 RPC/view/wsh 命令[1]。自定义 widget 通过 widgets.json 的 cmd/shell controller 可拉起任意 CLI（含持久交互式 shell）——任何终端 CLI agent 都能配成可点击启动的 widget/block[3]。

✅ 已踩出 Claude Code 集成路线 + 跨平台远程：官方 badge hooks 模式可直接抄给其它 agent；跨平台 + 远程 SSH durable session 适合一人管多机多项目[5]。block controller（进程生命周期管理）+ Tsunami widget 框架正好是"每个 agent 一个 block + 统一面板"的原生能力，不用自己造终端多路复用。

3.3 弱点与必须自己补的窟窿

⛔ 官方 Claude Code 集成是 Claude 专属：统管 Codex/Gemini 的"抹平层"要你自己写——三家都有 hook 机制（Claude lifecycle hooks[5] / Gemini settings.json hooks[46] / Codex hooks.json，演进中[47]），但事件名与配置各不同，要各写一个薄 adapter 把它们统一成 MC 状态。Wave 不像 Warp 那样开箱原生抹平多 agent。

⚠️ Wave 自身的 agentic 能力还在愿望清单：Wave AI（内置助手）尚未原生支持 MCP（discussion #2691，2025-12 提出，无 maintainer 响应）[7]；"Wave Agent Mode"（issue #2168，2025-05）仍 open/triage 未落地[8]。别指望 Wave 官方很快给出 agent-agnostic 编排，你的"大脑"应该是 Mission Control + 各 CLI agent，Wave 只当编排+可视化外壳。

⚠️ 无 wsh layout 命令 + 重量级 Electron：精确网格定位能力有限（只能 setmeta 定位到 block/tab/this，平铺布局靠 UI/拖拽）；自动平铺得靠 UI 或自己补 RPC[4]。自定义只到 widgets.json 配置级 + 改源码加 view，没有轻量第三方插件市场。

⚠️ 待补研究：Wave 是否有 headless/无 GUI 模式（影响能否在服务器无人值守跑 agent 集群）未确认；wsh run 指定目标 tab/workspace 的精确语法靠文档镜像推断，建议本地 wsh run --help / wsh setmeta --help 实测。

04Workflow 编排方案横评▼

编排是三大能力里最核心的一块。这章横评编排多个 coding agent 的工具，重点标出"是否 agent-agnostic"这个硬约束。

范式已收敛：每个 task 一个 git worktree（或容器）做隔离 + 并行跑 + 人在 review/merge 节点把关。Addy Osmani《The Code Agent Orchestra》原话："You used to pair with one AI. Now you manage an agent team" / "The bottleneck is no longer generation. It is verification" / "Your spec is the leverage"[6]。并明确主张 tool-agnostic 优于 vendor lock-in。

4.2 异构覆盖最广的活跃方案

✅ Emdash (generalaction/emdash, YC W26)：2.4k★、v0.4.41、3108 commits、81 releases，是横评里多后端覆盖最广（27 个 CLI agent）、最活跃的桌面方案[11]。明确以"异构 multi-agent 未来"为核心论点；支持 SSH 远程跑 agent + ticket(Linear/GitHub/Jira/Asana)直喂；worktree 隔离让多 agent 同改一文件不冲突。建议阿杰装来感受 agnostic 交互。弱点：没有显式跨任务依赖图，不是可嵌入 Wave 的库。

🔌 container-use (dagger/container-use)：3.8k★、v0.4.2(2025-08，更新偏慢、early development)。最干净的"隔离执行层"底座：作为 MCP server，"works with any MCP-compatible agent"[16]。容器隔离比 git worktree 更强（agent 砸不到宿主）。但只管隔离不含编排/看板/依赖图——需上层（MC）拼。

4.3 避坑名单（不要当长期底座）

⛔ Vibe Kanban (BloopAI)：26.6k★ 人气最高、多 agent(10+)，但母公司 Bloop 已于 2026-04-10 宣布关停、转纯社区维护，远程服务 30 天后只剩本地架构[14]。只能当设计参考（"任务卡拖到 In Progress 即起 worktree+分支"映射值得学），不能依赖。

⛔ 锁 Claude 系的：Conductor(闭源 macOS，仅 CC+Codex，不支持 Gemini)、Crystal(2026-02 已 deprecated)/Nimbalyst(仅 CC+Codex)、sketch(已死，纯 Claude)——都违背异构硬约束，不适合长期底座[15]。

4.4 工业级 HITL（人审节点）的参考

💡 durable-execution 引擎：Temporal/Inngest/Trigger.dev 把 HITL 直接映射到 suspend/resume 原语——可暂停数小时/天等审批而不丢状态[17]。但对单人开发者偏重（over-engineering），且不含 worktree/diff/dashboard 等 coding 专用件。单人不必上整套重型引擎，借鉴其 suspend/resume 思路即可。

⚠️ Wave 本身不做编排：它是 20.9k★ 的可视化终端壳，原生无多 agent 协调（Wave Agent Mode 仍是 open issue #2168）[1]。在 Wave 上做编排 = 自己写编排逻辑（MC），Wave 只当 UI/监控外壳。

05监控 / 可观测性方案横评▼

这一路有个"天降标准"的好消息，直接改变选型逻辑。

✅ 关键发现：三大 CLI agent 都内置 OpenTelemetry，agent-agnostic 监控的根本是 OTEL 标准 🟢 多源

Claude Code、OpenAI Codex CLI、Google Gemini CLI 都内置 OTLP 导出，可指向同一个 Collector endpoint，且都向 OTEL GenAI gen_ai.* 语义约定靠拢[12]。三者用法：CC 用 CLAUDE_CODE_ENABLE_TELEMETRY=1 + OTEL_EXPORTER_OTLP_ENDPOINT；Codex 用 ~/.codex/config.toml [otel] 段；Gemini 用 .gemini/settings.json。VictoriaMetrics 实测一个 Collector 同时吃 CC/Codex/Gemini/Qwen[13]。所以选型重点从"这个平台支不支持我的 agent"转为"这个后端是不是 OTLP-native"。

5.1 落地架构：在 Wave 里嵌一个 OTEL Collector

具体做法：① 给每个 session/项目设 OTEL_SERVICE_NAME + OTEL_RESOURCE_ATTRIBUTES（如 project=X, agent=claude-code, session=...），后端就能按项目/agent/session 三维过滤，正好对接 Mission Control 多项目管理。② Claude Code 用 session.id 属性天然支持 session 级 trace（claude_code.interaction span 套 llm_request/tool span，subagent 自动嵌套成一条 trace）[21]——这是做可观测性的金矿。③ 编排器派出去的每个 agent 进程注入 OTEL env 即可。

06多项目 / 多 session 管理横评▼

"一个人跑 N 个 agent 不乱"已经形成成熟工具品类。这章重点是阿杰的头号参考/竞品 cmux，以及隔离范式的取舍。

🪞
cmux — 你 Wave 路线的镜子
18.8k★ · libghostty · Swift/AppKit · macOS only
头号参考/竞品

基于 libghostty 的"为并行 AI agent 多任务而生的原生 macOS 终端"（非 Electron）[36]。垂直 tab 显示每 session 的 git 分支/工作目录/端口/通知；agent 需注意时给 pane 画 notification ring + 角标 + macOS 通知；内置可编程浏览器；带 socket/CLI API 可自动化。完全 agent-agnostic：任何能在终端启动的 agent 开箱即用（CC/Codex/Gemini/Aider/Goose/Amp/Cline/Cursor Agent 等）。

一个 18.8k★、完全 agnostic 的"为并行 agent 而生的终端"已经存在。你必须先把 cmux 跑一遍、读源码，搞清你在 Wave 上做的事和它的差异点——你的差异化应该是 Mission Control 这层任务/看板编排，而不是终端层 session 呈现（那层 cmux/Claude Squad 已做透）。

6.1 其它 agent-agnostic 终端/TUI 类

✅ Claude Squad (7.7k★, v1.0.18, AGPL-3.0)：tmux 隔离 session + git worktree，支持 CC/Codex/Gemini/Aider/OpenCode/Amp（用 cs -p 切后端）[37]。架构简单可直接抄。注意：agnostic 是"换后端"而非"同界面混跑"。

✅ agent-deck (2.6k★, v1.9.43/2026-05-28 极新)：单 TUI 统一管理多 agent，招牌是智能状态检测（running/waiting/idle/error）+ 单键跳转到 waiting 的 session[20]。这正是"谁在等输入"这个第一痛点的现成范式，必抄。还有 fork+resume 上下文管理。

6.2 隔离范式的取舍：worktree vs 容器

范式代表工具优点缺点
git worktreeClaude Squad / cmux / Emdash / Vibe Kanban轻量、共享本机环境、切换成本最低依赖共享问题；大型 repo 磁盘膨胀 + dev-server 端口冲突

💡 给阿杰：单人轻量场景 git worktree 起步（切换成本最低），只在要跑不可信代码时再上容器（container-use 用 dagger 把容器+worktree 叠加）[18]。沙箱最佳实践：只挂项目目录、默认无出网、CPU/内存/磁盘硬上限、用完自毁。

6.3 实用并行上限：个位数

⚠️ N 的现实区间是 3-8 个，不是几十个：实测并行 agent 实用上限是 2-4 个（受内存/CPU/API rate limit 约束），Cursor 上限设到 8[38]；Claude Code agent-teams 官方建议 3-5 个 teammate。设计 MC 面板时按"同屏一眼看完 3-8 个 session 状态"来设计信息密度最合适🟡 单源。

6.4 Claude Code 原生 agent-teams：反例但协调原语可抄

⛔ 只能编排 Claude 自己（homogeneous）：v2.1.32+ 实验功能，无法管 Codex/Gemini——对异构需求是反例[39]。但它的 shared task list + mailbox + 任务依赖自动解锁 + file-locking 抢任务 + TaskCreated/Completed hooks 这套协调原语正是 MC 可直接照搬的设计，state 存 ~/.claude/teams 和 ~/.claude/tasks（外部可读，利于监控）。Wave 特定坑：CC agent-teams 的 split-pane 不支持 Ghostty 类终端，Wave 是自建终端，要做多 pane 得自己实现，别想白嫖 CC 的 tmux 模式。

07Agentic OS 概念与现有尝试（AIOS / Letta / Mission Control 同名项目）▼

"Agentic Operating System"在 2026 已从概念走到学术 + 工业双重落地。这章给你词汇表 + 可直接借鉴的现成项目。

7.1 学术锚点（借词汇表，不直接用）

AIOS (agiresearch/AIOS, 5.8k★, v0.3.0/2026-01, COLM 2025 论文)：把 LLM 嵌入 OS，提供 agent kernel——调度/内存管理/上下文切换/存储/工具管理/访问控制[40]。概念权威，可借词汇表给你的 OS 命名分层。但管的是通用 LLM agent（框架级），不是 Claude Code/Codex 这类终端 CLI agent，抽象层级错位——更像理念来源而非可直接用的面板。

Letta (formerly MemGPT, 23k★, Apache-2.0)："LLM as operating system" 范式代表，核心是 memory blocks + 上下文管理 + agent server + ADE 图形界面[41]。记忆/上下文这层做得最深，但本质是建 agent 的框架不是管现有异构 CLI agent 的面板，可借鉴的是它的 memory/context OS 抽象。

7.2 同名 "Mission Control" 开源面板（可直接抄）

✅ builderz-labs/mission-control (5.1k★, MIT, v2.0.1/2026-03)：和阿杰项目同名同形——26 个监控面板覆盖 tasks/agents/logs/tokens/memory/cron/alerts/webhooks/pipelines，SQLite 零依赖单命令启动，内置 adapter 层（OpenClaw/CrewAI/LangGraph/AutoGen/Claude SDK + generic fallback）[24]。Next.js 16/React 19/TS 栈。可借走 adapter 抽象 + 监控面板设计。⚠️ 注意：是否"直连 CC/Codex 无需 gateway"两处来源口径冲突（README 说能直连，另一对比文说 gateway-dependent 且 alpha），需实测验证。

✅ wolverin0/clawtrol (39★, MIT, Ruby/Rails8/PG)：对异构多模型支持最直白——persona 系统允许 Opus/Codex/Gemini/GLM/Sonnet/Flash 各配不同模型同台运行，任意能调 REST API 的 agent 都能接入[42]。还有 live agent streaming terminal、factory loop（find→improve→test→commit 自主循环）。persona+多模型正是管异构 agent 的现成参考。弱点：仅 39★ 社区小、Ruby 栈移植成本。

crshdn/mission-control (Autensa, 2.1k★, MIT)："Autonomous Product Engine"，convoy mode（带依赖图的并行子任务 + 自动恢复）+ crash recovery（checkpoint 续跑）+ 80+ REST API + git worktree 隔离[43]。这套"一人撬动 N agent"工程模式最成熟。弱点：强绑 OpenClaw Gateway 架构、定位偏全自动产品流水线比"session OS"更重。

7.3 顶层架构原则 + 竞品缺口

🧭 "标准化控制平面，不标准化 agent"（Futurum 2026 gateway field guide 原话）："The right reflex is to standardize the control plane, not the agent. Let developers keep their chosen surface; make every agent answer to the same gateway hop."[23] OpenClaw 的"gateway as single source of truth"架构（所有 session/路由/channel 都过一个 Gateway）成为个人 AI agent 蓝图[44]。启示：在 Wave 上也应有一个等价的"单一 gateway/session 真相源"，所有异构 agent 的 IO/事件/成本/状态都汇报到它，监控和编排才有统一抓手。

⚠️ 最该补的竞品缺口：amux.io 自称 "The Agent Control Plane"，与阿杰目标几乎同名，但官网返回 403 抓不到，是否开源、支持哪些 CLI、star/版本均未知🔴 待补研究[45]。建议阿杰直接访问 amux.io 及其 GitHub。另外 "OpenClaw" 这个共同 gateway 后端究竟是真实项目还是搜索层对某个被改名项目的抽象，未完全证实。

⚠️ 待补研究：各工具对 Codex CLI / Gemini CLI 的接入是否真顺滑（声称支持 vs 实际可用常有差距，尤其鉴权/输出解析）；把 Codex/Gemini 的 OTLP 同时指向同后端时 trace 能否干净按 agent 区分（service.name/属性命名是否冲突）——都建议阿杰真跑一遍验证。

✅ 阶段 0（最窄，先跑通）：一个 Claude Code 在 Wave 里全链路

🟡 阶段 1（监控免费午餐）：嵌 OTEL Collector + SigNoz

给 Claude Code 注入 OTEL env，在 SigNoz 看到 session trace + token/cost。验证三维过滤（project/agent/session）。这一步几乎是抄 claude-code-otel 模板[32]。

🎯 阶段 2（异构第一次落地）：加 Codex CLI

写 MC 的第一个非 Claude agent profile。Codex 的 OTLP 指向同一个 Collector（监控免费统一），状态灯优先用 Codex 原生 hooks（hooks.json），加载路径未落地的部分用 OTEL 事件兜底。这一步会暴露抹平层的真实工作量，是整个项目的风险验证点。

🔭 阶段 3（异构补全）：加 Gemini CLI + 多项目 workspace

Gemini OTEL metrics 最全，监控好接。用 Wave workspace/tab 隔离多项目。此时已是完整的"一人撬动 N 个异构 agent"OS。

⏭️ 阶段 4（可选，按需）：完整编排引擎

只有当真有"任务依赖图 + 并行 + 人审 merge"的复杂需求时再做。抄 agent-kanban + Bernstein。隔离需要更强时上 container-use。别提前做，会过度工程。

11.3 第一步具体动作（今天就能做）

1）本地装 Wave，跑 wsh run --help / wsh badge --help / wsh setmeta --help 摸清精确语法（文档只到 TOC，必须实测）。2）读 Wave repo 的 CLAUDE.md + skill guides，确认加 RPC/view/wsh 命令的扩展上限。3）装 cmux 跑一遍，看你的差异化（MC 编排层）到底在哪。4）读 agent-kanban 源码的数据模型，决定对标抄 or fork。5）验证 builderz-labs/mission-control 的"直连无 gateway"口径冲突（实测能不能直连 CC/Codex）。

12风险与坑▼

⛔ 坑 1：异构抹平层是真活儿，不是配置

Wave 官方只给 Claude 专属集成，Codex/Gemini 的状态灯要自写 adapter。好在三家都有 hook 机制（Gemini 成熟[46] / Codex 演进中[47] / Claude 最全），所以这是"把各家 hook 事件统一映射成 MC 状态"的明确工作量，不再是"有没有 hooks"的未知。真正待验证的是 Codex hooks.json 加载路径的完整度，建议阶段 2 实测。

⛔ 坑 2：Codex exec 无 OTEL metrics

无人值守批跑最常用的 codex exec 不出 metrics[33]，统一成本看板对 Codex 这路会缺数据，需从 log 反推或单独处理。跨 agent 成本 metric 映射目前无现成配置。

⚠️ 坑 3：别把 Wave 当大脑

Wave AI/Agent Mode/MCP 都还在 open 愿望阶段无路线图（issue #2168/#2791、discussion #2691）[7][8]。指望 Wave 官方很快给 agent-agnostic 编排会落空，你的大脑必须是 MC。

⚠️ 坑 4：选错底座工具会被弃坑/锁死

Vibe Kanban(母公司已关停)、sketch(已死)、Conductor/Crystal/Nimbalyst(锁 Claude 系)都不适合当长期底座[14][15]。只能借设计，别依赖。

⚠️ 坑 5：Wave 多 pane / headless 能力未坐实

无 wsh layout 命令，精确网格布局受限[4]；CC agent-teams 的 split-pane 不支持 Ghostty 类终端，Wave 自建终端要做多 pane 得自己实现[39]；Wave 是否有 headless 模式（无人值守跑 agent 集群）未确认🔴 待补研究。

⚠️ 坑 6：国内可用性 + 鉴权未覆盖

各工具在"用户在国内"场景下 Gemini CLI/Codex/Claude 的网络可达性与鉴权本研究未深挖，这直接影响异构混跑的实际落地🔴 待补研究。

13FAQ▼

QWave Terminal 到底能不能当这个 OS 的地基？+

能，可行性高。它的 Block + wsh + badge 三件套天然覆盖编排/监控/多项目三大能力[1]。但它给的是原语不是成品——编排逻辑和异构抹平层得你自己在 Mission Control 里写。把 Wave 定位成"终端侧 agent OS 外壳"（呈现 + 进程托管），别指望它当大脑。

Q为什么"统管异构 agent"这么难？+

因为 CC/Codex/Gemini 是三家不同公司、三套不同的启动/配置/hook/输出/鉴权。真正 agent-agnostic 的工具只在两种架构下成立：把 agent 抽象成"任意可启动的 CLI"或"任意 MCP server"[19]。深度集成桌面 app（Conductor/Sculptor）注定收窄到 CC+Codex、丢掉 Gemini。

Q监控异构 agent 是不是要给每家找一个监控平台？+

不用。三大 CLI agent 都内置 OpenTelemetry，监控的正确做法是在 Wave 里嵌一个 OTEL Collector，把三个 agent 的 OTLP 都指向同一个自托管后端（SigNoz/Langfuse）[12][13]。监控层别自己造轮子。

Q第一步应该先跑通什么？+

最窄链路：一个 Claude Code 在 Wave 里走完"MC 任务 → wsh run 拉 block → lifecycle hooks → wsh badge 亮状态 → 回写 MC"。先不碰异构，验证 Wave 原语够不够用。打通后再嵌 OTEL，再加 Codex（异构第一次落地、风险验证点），再加 Gemini。见第 11 章决策树。

QMission Control 要从零设计编排逻辑吗？+

不要。agent-kanban 几乎就是 MC 的开源同构物（leader-worker + depends_on 环检测 + 子任务 + SSE 监控 + 人审 merge）[9]；CC agent-teams 的 shared task list + file-locking 抢任务 + TaskCreated/Completed hooks 也可直接照搬[39]。先读透它们的数据模型再决定对标抄 or fork。

Q隔离用 git worktree 还是容器？+

单人轻量起步用 git worktree（切换成本最低，cmux/Claude Squad/Emdash 都这么做），只在要跑不可信代码时再上容器（container-use 容器隔离比 worktree 强，agent 砸不到宿主）[18]。注意大型 repo 的 worktree 磁盘膨胀 + dev-server 端口冲突要自己管理。

Qcmux 既然已经做了这件事，我还有必要在 Wave 上做吗？+

有，但你的差异化必须想清楚。cmux（18.8k★）已把终端层多 agent session 呈现做透了[36]。你的差异化应该是 Mission Control 这层任务/看板编排 + Agentic OS 理念，而不是再造一个终端。先把 cmux 跑一遍读源码，确认你要补的是它没做的编排层。cmux 还只支持 macOS，Wave 跨平台是一个潜在差异点。

QN 个 agent 的 N 现实能到多少？+

个位数。实测并行实用上限 2-4 个（受内存/CPU/API rate limit 约束），Cursor 设到 8，CC agent-teams 官方建议 3-5 个[38]。设计 MC 面板按"同屏一眼看完 3-8 个 session 状态"的信息密度，别按几十个设计。

Q状态总览最该先做哪个功能？+

"哪个 agent 卡住等我输入了"——running/waiting/idle/error 四态检测 + 一键跳到等输入的 session。这是单人跑 N 个 agent 的第一痛点，agent-deck 把它做成头等公民、cmux 用 notification ring[20]。直接抄这个范式。

Q学术界的 AIOS / Letta 能直接拿来用吗？+

不能直接用。AIOS/Letta 管的是框架级 LLM agent，不是 Claude Code/Codex 这类终端 CLI agent，抽象层级错位[40][41]。只能借它们的"OS 词汇表（调度/上下文切换/访问控制）"和 memory layer 设计。Memory/Orchestration 层一开始就当一等公民，别后补成技术债[27]。

Q顶层架构原则用一句话概括？+

"标准化控制平面，而不是标准化 agent"[23]。让 CC/Codex/Gemini 各自原样跑，但全部把 IO/事件/成本/状态汇报到一个统一 hop（你的 MC = 单一 session 真相源）。这是管异构 agent 唯一可扩展的姿势。

Q"管理 agent 是未来核心技能"这个叙事站得住吗？+

站得住。Karpathy 把 agentic engineering 定义为"orchestrating agents + oversight"；Cognition 已落地"Devin 管 Devin"（15 人团队管一个 Devin 舰队）；Cursor 3.2 把 IDE 重构成 agent execution runtime、统一 sidebar 管 8 个并行 agent；业界普遍预测 2027 工程师 = AI Orchestrator[25][26]。你做的不是工具，是"一个人当一支队伍"的操作系统。

Q最该先去验证的竞品/疑点是什么？+

① amux.io（自称 "The Agent Control Plane"，与你目标几乎同名，但 403 抓不到，开源/CLI 支持/star 全未知）[45]；② builderz-labs/mission-control 的"直连无 gateway"口径冲突；③ Codex hooks.json 的 plugin 加载路径完整度（Gemini hooks 已成熟[46]、Codex 引擎在演进[47]，三家都有 hooks、badge 范式可复用已确认）。这三个都建议阿杰亲自跑一遍验证。
