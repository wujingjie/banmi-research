claudepot-app 的好功能怎么搬进你的 MC

📅 2026-05-30 🔍 无忌 Deep Research · 双源码深读合并 🎯 claudepot=会话可视化 · MC=任务治理 🧩 互补不重叠 🇨🇳 全程中文白话
一句话：你的 MC 强在任务治理（review gate / 依赖 / handoff / 多 executor 开工命令 / Context Pack / Obsidian 关联），但把 session 只当一行元数据——transcript_path 字段存在却从不被读取[2]。claudepot-app（李笑来做的 Claude Code session 管理 GUI）恰好补上你最缺的三块：① 看每个真实 session 在干啥（live + 历史回放）② skill/agent/command 管理 ③ 账号/用量管理[1]。两边几乎零重叠，是教科书级的「我有治理、你有可视化」互补。本报告把两份源码深读合并成一份可落地的搬运方案：哪些搬、怎么搬、先搬哪个、坑在哪。最该先搬的是「真实 session 回放」——你已经存了 transcript_path，只差把它读出来渲染这一环。

01执行摘要：最该搬的几个功能 + 一句话怎么搬▼

两份源码深读（claudepot-app 源码 + 你的 MC 源码）收敛出的核心判断。每条独立成块，方便扫。

✅ 搬运 1（最高性价比）：真实 session 回放——你只差「读 transcript」这最后一环 🟢 双源确认

MC 已经在 AgentSession 里存了 transcript_path 字段，但全代码库没有任何代码读取/serve/渲染它——SessionsPage 列表项不可点击，没有详情视图[2]。claudepot 的核心能力就是把这条 .jsonl transcript 真正读出来按对话/工具调用渲染[1]。怎么搬：Go 后端加一个 GET /api/sessions/{id}/transcript 端点，按行读 transcript_path 指向的 jsonl、流式吐给前端；前端给 SessionsPage 卡片加点击路由到详情页渲染。这是 MC 最大缺口、且基础设施（字段+列表）已就位，投入最小、补的洞最大。

🎯 搬运 2：Live Session 实时状态（busy / waiting / errored）——比你现在的「30s 心跳判活」细一个量级 🟢 claudepot 高可借鉴

claudepot 不读历史 jsonl，而是扫 ~/.claude/sessions 下每进程一个 PID json（含 status）+ sysinfo 探活，再对活 session tail transcript，用状态机跟踪「未闭合的 tool_use（by id）」判断是 busy 还是 waiting[1]。MC 现在只能靠 hook 发的 run_started/run_ended + 30s staleness watcher 粗判「running / stale」[2]。怎么搬：借鉴 claudepot 的 session_live/status.rs 状态机逻辑（追踪未闭合 tool_use id）——但 MC 是 Go，不必照搬 Rust tick 循环，可在读 transcript 时顺便算出当前状态塞进 SSE 事件。建议搬「状态机判定逻辑」，不搬「PID 文件扫描数据源」（见第 7 章数据源差异）。

💡 搬运 3：Skill / Agent / Command 管理——MC 完全没有，claudepot 有成熟的 disable/trash/restore 🟢 MC 全缺

MC 没有任何 skill 实体/表/端点/页面[2]。claudepot 把 skill/agent/command 三类统一做生命周期管理：发现靠扫含 SKILL.md 的子目录，disable 用原子 rename 到 .disabled，trash 是两阶段带 manifest 保留 30 天、可 restore[1]。怎么搬：新建一张 skills 表 + 一个 GET /api/skills（扫 ~/.claude/skills 和项目 .claude/skills）+ 一个 SkillsPage。其中「trash 带 manifest + TTL 可逆删除」这套设计还能反过来用在 MC 自己的危险操作上（删任务/删 session）。

🧭 搬运 4（选搬）：用量快照 usage-snapshot.json——契合 MC 的无人执行 session 🟡 部分借鉴

claudepot 的多账号切换对 MC 借鉴价值低（MC 不管多账号），但它的 usage-snapshot.json 模式值得抄：GUI 每 5 分钟原子写一个 0600 的 json（含 5h/7d 各窗口 utilization），供 cron/Bash 读[1]。MC 的 Usage 页现在是 "coming soon" 占位[2]，而 MC 大量跑无人执行 session——一个定期落地的用量快照正好能让 watcher/dispatcher 在额度紧张时降速。怎么搬：不必搬账号管理，只搬「定期原子写一份 0600 用量 json」这个轻量产物。

⚠️ 最该记的一条：搬「设计/逻辑」，别照搬「Rust 代码/数据源」 🟡 跨技术栈

claudepot 是 Rust + Tauri 桌面应用，MC 是 Go server + React web[1][2]。Rust 的 runtime.rs/registry.rs/status.rs 没法直接 copy 进 Go。真正能搬的是三样东西：① 数据源知识（transcript jsonl 长什么样、PID 文件在哪）② 状态机逻辑（怎么从事件流判断 busy/waiting）③ 产品设计（详情页怎么渲染、skill 生命周期怎么设计）。代码层面是「重写」不是「复制」。凡涉及 evidence 未覆盖的实现细节，本报告标 ⚠️ 不臆造。

一句话路线建议（给阿杰）

【先做】搬运 1（transcript 回放）——基础设施已就位，一个读端点 + 一个详情页就能把 MC 最大缺口补上。【再做】搬运 3（skill 管理）——纯新增、不动现有流水线、风险低。【然后】搬运 2（live 细粒度状态）——价值高但要碰 SSE 和状态机，复杂度中。【选做】搬运 4（用量快照）——配合无人执行很香，但非紧急。【纪律】搬逻辑和设计，不搬 Rust 代码；MC 是 Go 后端，所有「读文件」的活都在 server 侧做、经 SSE/REST 给前端。详见第 6/8 章。

本报告由无忌合并两份源码深读而成，只用这两份 evidence 的内容，未覆盖处标 ⚠️。可信度标记：🟢 双源确认 / 单源码深读直接读到的事实；🟡 基于源码事实的迁移推断 / 跨技术栈如何落地的设计建议；🔴 待核。claudepot 侧事实来自其源码深读 confidence=high 的条目；MC 侧事实带具体文件行号（如 models.go:92）均为深读直接读到。涉及「Go 该怎么写」的实现是无忌的迁移建议（🟡），落地时以真实代码为准。

02claudepot-app 是什么 + 架构/技术栈▼

claudepot-app 是李笑来做的 Claude Code session 管理 GUI——一个桌面应用，核心是「让你看到本机所有 Claude Code session 在干啥，并管理 skill/agent/command 和多账号」[1]。它和 MC 是两个物种：MC 是任务编排平台，claudepot 是会话可视化工具。

架构一句话

Rust 后端（Tauri）+ 前端（TS/React，useSyncExternalStore + RAF）。数据源不走 MC 那种「应用自己的 DB 记一行」，而是直接读 Claude Code 在磁盘上的原生产物：~/.claude/sessions 下的 PID json、~/.claude/projects/*.jsonl transcript、~/.claude/skills 目录。这是它和 MC 最根本的设计差异——claudepot 是「外部观察者」，MC 是「内部登记者」[1]。

2.1 claudepot 的几个核心模块（源码深读所见）

模块干啥关键文件

为什么 claudepot 的设计对 MC 有参考价值

claudepot 把「真实运行态的 Claude Code 是什么样」摸得很透——它知道 session 状态藏在 PID 文件、对话内容藏在 transcript jsonl、skill 藏在含 SKILL.md 的目录。MC 因为是「自己登记」的设计，从没去读过这些原生产物。把 claudepot 的「数据源知识 + 渲染设计」搬过来，MC 就能从「只知道 session 存在」升级到「知道 session 在干啥、说了啥」[1][2]。

03claudepot 三大可借鉴功能深拆（含 howImplemented）▼

这一章把 claudepot 最值得搬的三块按「干啥 / 怎么实现 / 可借鉴度」拆开。第 6 章再讲具体怎么搬进 MC。

3.1 Live Session 实时发现 + 可视化 对 MC 最有价值

干啥：实时看每个正在跑的 Claude session 是 busy（在干活）/ waiting（等输入）/ errored（卡住）[1]。

怎么实现（howImplemented）：数据源不是历史 jsonl，而是扫 ~/.claude/sessions 下每进程一个 PID json 文件（含 status），用 sysinfo 探活确认进程还在；再对活 session tail 对应 projects 下的 transcript jsonl。runtime.rs 的 LiveRuntime 每 500ms tick 一次，status.rs 是状态机——核心技巧是跟踪「未闭合的 tool_use（by id）」：发出 tool_use 但还没收到对应 tool_result，就是 busy；都闭合了在等用户就是 waiting。bus 发 delta，live_activity_bridge.rs emit Tauri event，前端 useSessionLive.ts 用 useSyncExternalStore + RAF 合并渲染[1]。

可借鉴度：高。关键文件 session_live/runtime.rs / registry.rs / status.rs / hooks/useSessionLive.ts。MC 可搬整条链路的设计：发现 → tail → 状态机 → 推事件 → 前端合并渲染。⚠️ Rust tick 循环不必照搬，Go 侧可用 fsnotify/轮询 + 在已有 SSE hub 上加 per-session 通道（见第 6/7 章）。

3.2 历史 Session 浏览 + 跨项目搜索

干啥：列每个项目的所有 session，跨项目搜 prompt，过滤，导出前剥 token[1]。

怎么实现：session_index 用 sessions.db（SQLite WAL，权限 0600），每个 jsonl 一行缓存做 fold（折叠成摘要）；判断是否需要重扫用 size + mtime + inode 三元组 做 guard（任一变了才重扫）；冷启动全量扫用 rayon 并行[1]。

可借鉴度：中。这是标准做法，而 MC 已经有自己的 SQLite DB，不必照搬整个 index 层。值得借鉴的是「size+mtime+inode 三元组判断 transcript 是否变了」这个增量扫描小技巧，避免每次全量读。关键文件 session_index/mod.rs / schema.rs / session.rs。

3.3 Skill / Agent / Command 管理（artifact-lifecycle）

干啥：把 skill / agent / command 三类统一做 disable / trash / restore。skill 发现 = 扫 skills 目录下含 SKILL.md 的子目录[1]。

怎么实现：artifact_lifecycle 定义 ArtifactKind 三种，映射到 skills / agents / commands 三个目录。disable = atomic rename 到 .disabled（瞬间生效、可逆）；trash = 两阶段带 manifest，保留 30 天（先移到回收区 + 写一份 manifest 记录原位置，过期才真删，期间可 restore）。入口先 classify_path 返回三元组判断这是什么 artifact，plugin / managed-policy 的会被拒绝（不让动托管的）[1]。

可借鉴度：中。「三元组 + classify 守门 + 生命周期」对 MC 管任务模板有参考；「trash 带 manifest + TTL 可逆删除」这套可直接用在 MC 自己的危险操作（删任务/删 session）上，给个后悔药。关键文件 artifact_lifecycle/paths.rs / disable.rs / trash.rs。

3.4 账号管理（多账号切换 + 额度轮换）对 MC 借鉴低

干啥：管多个 Claude 账号，CLI/Desktop 两槽位各自切换；读 5h/7d 各窗口 utilization，越阈值按规则切到备用账号；每 5 分钟写 usage-snapshot.json（0600）[1]。

怎么实现：元数据存 accounts.db（SQLite 0600）；CC 凭证用 /usr/bin/security 子进程读写 keychain（不直接调 SecItem）；swap.rs 原子读旧写新 + verify + 回滚；rotation/eval.rs 是纯函数求值器（注入 now，输出含护栏的 PendingSwap）[1]。

可借鉴度：账号切换本身低（MC 不管多账号），但 usage-snapshot.json 模式高：「GUI 定期原子写 0600 json 供 cron/Bash 读」非常契合 MC 的无人执行场景。关键文件 oauth/usage.rs / services/usage_snapshot.rs。

04你的 MC 现状（session 管理 + mc-web 到哪了）▼

先讲清楚 MC 现在是什么、强在哪、弱在哪，才知道该往哪补。一句话：MC 是任务编排 + 治理平台，session 管理只是这条流水线的一个轻量副产品[2]。

技术栈

后端 Go + gorilla/mux + SQLite（pkg/mcstore），端口 3001。前端 Vite 8 + React 19 + TypeScript 6 + Tailwind v4，端口 3003，Vite proxy /api→3001 注入 Bearer。实时走原生 SSE（GET /api/events/stream + EventSource，浏览器自动重连）+ 30s ping。UI 全 inline-style 暗色（#0d1117 GitHub 配色），无 UI 组件库。打包进 Electron。鉴权单一 MC_AUTH_KEY（Bearer header 或 ?auth= query 供 SSE 用）[2]。⚠️ react-router-dom 7 已装但 App.tsx 实际用 useState 手写切页，未用 router。

4.1 MC 的 session 是怎么管的

  • AgentSession 数据模型：每个 agent 运行登记一行——provider(claude/codex/gemini)、cwd、command、status、task_id/run_id、transcript_path、tab_id、area_id、started_at/last_seen_at。状态机 8 态：starting/running/waiting_input/needs_approval/stale/done/failed/cancelled（models.go:82-97，状态常量 models.go:29-36）[2]。
  • Hook 驱动的生命周期：靠 Claude Code 的 SessionStart/Stop hook 自动建/关 session（纯 bash+curl+python3），/tmp 下 idfile 做幂等。SessionStart→建 session + 发 run_started + 顺手把 task 推到 doing；Stop→发 run_ended + 把 session 标 done[2]。
  • Staleness watcher：后台每 30s 扫一次，超时未心跳的 running session 标 stale 并 publish 事件；session 自身有 /heartbeat 端点供 worker 续命[2]。
  • 前端两个视图：SessionsPage（按 project/status 过滤的列表，卡片不可点进、无详情）+ LogsPage（结构化治理事件流：run_started/handoff_written/guardrail_passed 等带颜色的事件条）[2]。

❌ MC 最大的缺口：transcript_path 存了，但从不被读

这是整份报告的核心发现：transcript_path 字段在 models.go:92 和 insert SQL 里存在，但全代码库 grep 下来，除了 model 定义和 insert，没有任何代码读取/serve/渲染它[2]。意味着 MC「看 session 在干啥」只能靠两个间接视图——元数据列表（不可点进）+ 治理事件流（粒度是编排事件，不是对话/工具调用）。MC 没有任何「看真实会话内容/回放」的能力。这正是 claudepot 的差异化切入点，也是最该补的洞。

4.2 MC 真正的强项（别动这些，要保护）

MC 强在任务治理，不在 session：review gate（doing 不能直达 done，只能 →review/blocked）、depends_on 依赖、TaskRun/handoff/VerifierResult 流水线模型、多 executor 开工命令生成（为 claude/codex/gemini 生成可复制命令，注入 MC_API_URL/MC_AUTH_KEY/MC_TASK_ID）、Context Pack（project+task+area+docs+guardrails 拼成 markdown）、Intent 邮箱（claim/lease）、Obsidian 文档关联[2]。搬 claudepot 功能时，这些治理能力是 MC 的护城河，只做加法、不要碰。

⚠️ Usage 页 / Skill 全空：MC 的 Usage 页是 "coming soon" 纯占位（App.tsx:189），无 token/cost/account 模型；也没有任何 skill 实体/表/端点/页面[2]。这两块 + transcript 回放，正好是 claudepot 的三个差异化补位点。

06⭐ 结合方案：哪些搬、怎么搬▼

这是核心章。每个功能给「搬什么 / 不搬什么 / 落地路径」。总纪律：搬设计和逻辑，所有读文件的活在 Go server 侧做，经 REST/SSE 给前端；不照搬 Rust 代码。

6.1 ⭐ 搬运 1：真实 session 回放（最高优先）

搬什么：把 transcript_path 指向的 .jsonl 读出来、按对话/工具调用渲染的能力（这是 MC 缺的那一环）[2]。不搬：claudepot 的 SQLite index 层（MC 已有 DB）。

落地路径（Go 侧 🟡 无忌建议）：

  1. 后端新增 GET /api/sessions/{id}/transcript：从 DB 取该 session 的 transcript_path → 按行读 jsonl → 解析每行（user/assistant/tool_use/tool_result）→ 返回结构化数组（或流式分页，大文件别一次性读）。
  2. 前端 SessionsPage 卡片加点击→ 路由到 SessionDetail 页（react-router-dom 已装，正好顺势启用，或继续 useState 切页）。
  3. SessionDetail 渲染对话气泡 + 工具调用折叠块，复用 MC 现有 inline-style 暗色风格。

为什么先做这个：① 它是 MC 最大缺口 ② 基础设施已就位（字段 + 列表都有，只差读+渲染）③ 不碰治理流水线，风险低 ④ 一旦能读 transcript，跨项目搜 prompt、live 状态判定都建立在同一份数据上，是后续两块的地基。

6.2 搬运 2：Live 细粒度状态（busy/waiting/errored）

搬什么：claudepot status.rs 的状态机判定逻辑——跟踪「未闭合的 tool_use（by id）」来区分 busy（有未闭合 tool_use）vs waiting（都闭合了在等输入）vs errored[1]。不搬：claudepot 的 PID 文件数据源 + 500ms Rust tick 循环（见第 7 章，MC 数据源不同）。

落地路径（🟡 无忌建议）：MC 既然要读 transcript（搬运 1），就在读的时候顺手跑一遍状态机算出当前状态，比 30s staleness 粗判细得多。把算出的细粒度状态塞进现有 SSE 事件（session.updated）。⚠️ 若要真正「实时 tail」而非按需读，MC 的全局 SSE hub 可能需要加 per-session 通道（深读指出现有 hub 广播全部事件 + 客户端全量 refetch，不适合高频）。

6.3 搬运 3：Skill / Agent / Command 管理

搬什么：① 发现逻辑（扫含 SKILL.md 的子目录）② disable=rename 到 .disabled ③ trash 两阶段带 manifest + 30 天 TTL + restore ④ classify 守门（拒绝动 plugin/managed）[1]。不搬：Rust 的 ArtifactKind 枚举实现细节，按 Go 重写。

落地路径（🟡 无忌建议）：

  1. 新建 skills 表（或不入库、纯实时扫）+ GET /api/skills：扫 ~/.claude/skills 和项目 .claude/skills 下含 SKILL.md 的目录，读 YAML name/description。
  2. POST /api/skills/{name}/disable|restore：disable=原子 rename，restore=反向。
  3. 新建 SkillsPage（沿用 inline-style 暗色），列 skill + enable/disable 开关 + trash。
  4. 顺带福利：把 trash+manifest+TTL 这套抽成 MC 通用「可逆删除」，用在删任务/删 session。

为什么风险低：纯新增模块，不碰 AgentSession / TaskRun / 治理流水线。失败也只影响 skill 面板，不影响任务执行。

6.4 搬运 4（选搬）：用量快照

搬什么：只搬 usage-snapshot.json 模式——定期原子写一份 0600 的用量 json 供 cron/Bash 读[1]。不搬：多账号切换 + keychain + rotation（MC 不管多账号）。落地：MC 后台加个定时任务，把当前用量/额度（⚠️ 数据来源 MC 侧 evidence 未覆盖，需另定）原子写到一个 0600 json；无人执行的 watcher/dispatcher 读它，额度紧时降速。把 Usage 页从 "coming soon" 接上这份快照。

07技术对接细节：数据源 + MC 怎么接▼

这一章讲两边数据源的具体差异，以及 MC（Go）怎么接同样的数据源。这是搬运能不能落地的关键。

7.1 claudepot 读的三个数据源

数据源路径claudepot 拿它干啥
PID json~/.claude/sessions/*（每进程一个，含 status）发现活 session + 探活[1]
transcript jsonl~/.claude/projects/*.jsonl读对话/工具调用内容、tail 算状态[1]
skill 目录~/.claude/skills/*/SKILL.md（+ 项目 .claude/skills）发现 skill[1]

关键差异：MC 已经有 transcript_path，不必自己去猜路径

claudepot 因为是外部观察者，要自己去 ~/.claude/projects 找 transcript。MC 不一样——它的 AgentSession 已经存了 transcript_path 字段（Claude Code 的 SessionStart hook 登记时就能拿到）[2]。所以 MC 读 transcript比 claudepot 还简单：直接拿字段里的路径去读，不用扫目录、不用匹配项目。这是 MC 的现成优势，让搬运 1 更省事。

7.2 Live 状态：MC 该用 hook 数据源，不该照搬 PID 扫描

claudepot 扫 PID 文件是因为它没有别的发现机制。MC 已经有更可靠的发现机制：hook 驱动的自动登记（SessionStart 建、Stop 关）[2]。所以 MC 不需要搬 PID 扫描——它已经知道哪些 session 活着。MC 要搬的只是 claudepot 的状态机逻辑（怎么从 transcript 事件流判 busy/waiting）。结论：发现机制用 MC 自己的 hook，状态判定借 claudepot 的状态机，数据用 MC 已存的 transcript_path——三者各取所长。

7.3 实时推送：MC 的 SSE hub 局限

MC 用极简自写 SSE hub（cmd/mcserver/sse.go，map[chan]bool，满则丢弃），前端原生 EventSource，收事件即全量 refetch[2]。这对低频 task/session 元数据变更够用，但不适合高频/大量的 live transcript 流式。若搬运 2 要做「实时 tail transcript 逐行推」，⚠️ 现有 hub 可能要加 per-session channel（claudepot 用的是 per-session tail）。务实做法：先做「点进详情按需读全量 transcript」（搬运 1），不做实时 tail，避开 SSE 改造；等真有需求再上 per-session 流。

7.4 增量扫描小技巧（来自 claudepot index）

若 MC 要缓存 transcript 摘要（比如做跨项目搜），可借 claudepot 的 size+mtime+inode 三元组 guard：只有这三个任一变了才重读 jsonl，避免每次全量扫[1]。Go 的 os.Stat 拿得到 size/mtime，inode 在 syscall.Stat_t 里。

08落地优先级排序：先搬哪个性价比高▼

按「补的洞大小 × 投入小 × 风险低」排。决策很清晰。

第 1 步：transcript 回放（搬运 1）— 字段已有，只差读+渲染
↓ 地基铺好，transcript 能读了
第 2 步：Skill 管理（搬运 3）— 纯新增，不碰流水线，风险最低
↓ 低风险先攒一个完整新模块
第 3 步：Live 细粒度状态（搬运 2）— 价值高但要碰状态机/SSE，复杂度中
↓ 行有余力
第 4 步：用量快照（搬运 4）— 配合无人执行香，非紧急，数据源待定
搬运补洞投入风险顺序
1 transcript 回放大小低第 1
3 skill 管理中中低第 2
2 live 状态中中中第 3
4 用量快照小小低选做

性价比之王是搬运 1。理由：MC 已经存了 transcript_path 却从不读——这是「已经买了菜没下锅」的状态，补这一环投入最小、价值最大，且它是搬运 2、跨项目搜的共同地基。从这里开第一刀。

09风险 / 坑▼

❌ 坑 1：想直接 copy Rust 代码进 Go

claudepot 是 Rust+Tauri，MC 是 Go+React，两边代码不能互拷[1][2]。能搬的是数据源知识 + 状态机逻辑 + 产品设计，代码层面是重写。别指望贴文件。

❌ 坑 2：用现有全局 SSE hub 硬推实时 transcript

MC 的 SSE hub 广播全部事件 + 客户端全量 refetch，扛不住高频 live transcript 流[2]。先做「按需读全量」，别一上来就上实时 tail，否则要先改 SSE 架构（per-session channel），投入翻倍。

⚠️ 坑 3：transcript jsonl 可能很大 + 含敏感 token

一次性读整个 jsonl 进内存渲染会卡。claudepot 的 index 用 fold 缓存摘要、导出前剥 token[1]——MC 也该分页/流式读 + 渲染前考虑剥 token（transcript 里可能有 API key 等）。⚠️ MC 侧具体脱敏策略 evidence 未覆盖，需自定。

⚠️ 坑 4：别碰 MC 的治理流水线

review gate / depends_on / handoff / Context Pack 是 MC 护城河[2]。搬 claudepot 功能全程只做加法（新端点、新页面、新表），不要改 AgentSession 状态机或 TaskRun 逻辑，否则可能波及无人执行流程。

⚠️ 坑 5：classify 守门别漏——别让用户 disable 掉托管的 skill

claudepot 的 artifact_lifecycle 入口会 classify_path 拒绝动 plugin/managed-policy 的[1]。MC 搬 skill 管理时要照抄这个守门，否则可能误删/误禁系统级 skill 把执行环境搞坏。

ℹ️ 待深化（evidence 未覆盖，落地前补）

① MC 侧用量/额度的真实数据来源（搬运 4 依赖它）⚠️ ② transcript jsonl 的精确每行 schema（user/assistant/tool_use/tool_result 字段名）——claudepot 读了但深读未列字段细节，落地时直接看一份真实 jsonl ⚠️ ③ MC 的 .mc-runner/live 目录是否已持有 transcript 实体（深读 gap 提到疑似，未确认）⚠️ ④ MC pipeline.go / mailbox-runner 是否涉及 session 自动 spawn（本次未展开）⚠️。

10FAQ▼

Q一句话，claudepot 最该搬进 MC 的是什么？+

真实 session 回放——把 MC 已存的 transcript_path 指向的 jsonl 读出来渲染。MC 字段已有、列表已有，只差「读+渲染」这一环，投入最小、补的洞最大[1][2]。

Qclaudepot 是 Rust，MC 是 Go，代码能直接抄吗？+

不能。能搬的是数据源知识（transcript/PID/skill 路径）、状态机逻辑（怎么判 busy/waiting）、产品设计（详情页/skill 生命周期）。代码层面是按 Go 重写，不是复制粘贴[1][2]。

QMC 要不要照搬 claudepot 的 PID 文件扫描来发现 session？+

不用。claudepot 扫 PID 是因为它没别的发现机制；MC 有更可靠的 hook 自动登记（SessionStart/Stop）。MC 用自己的 hook 发现 + 借 claudepot 状态机判活 + 读自己存的 transcript_path，三者各取所长[2]。

Q搬这些会不会影响 MC 现在的任务治理流程？+

不会，只要全程做加法。transcript 回放/skill 管理/用量快照都是新端点+新页面+新表，不动 AgentSession 状态机和 TaskRun 流水线。两边能力零重叠，互补不冲突[2]。

Q能做到像 claudepot 那样实时 tail 看 session 逐行刷新吗？+

能，但要先改 SSE。MC 现有 SSE hub 广播全部事件+客户端全量 refetch，扛不住高频流。务实做法：先做「点进详情按需读全量」，要真正实时 tail 再上 per-session channel[2]。

Qclaudepot 的账号管理值得搬吗？+

多账号切换借鉴低（MC 不管多账号）。但 usage-snapshot.json 模式（定期原子写 0600 json 供 cron 读）很契合 MC 的无人执行——只搬这个轻量产物，让额度紧时降速[1]。

Qtrash+manifest+TTL 那套除了管 skill 还能干啥？+

能抽成 MC 通用「可逆删除」，用在删任务/删 session——两阶段移到回收区+记 manifest，30 天内可 restore，给危险操作一颗后悔药[1]。

Q读 transcript 有什么安全要注意的？+

jsonl 可能很大（分页/流式读）+ 含敏感 token（渲染/导出前考虑剥）。claudepot 的 index 用 fold 缓存摘要、导出前剥 token，可借鉴。⚠️ MC 具体脱敏策略 evidence 未覆盖，需自定[1]。

Q先搬哪个？+

1) transcript 回放（地基+最大缺口+投入最小）→ 2) skill 管理（纯新增低风险）→ 3) live 细粒度状态（价值高复杂度中）→ 选做用量快照。见第 8 章[1][2]。
