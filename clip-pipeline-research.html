5 条结论

① 真切片 vs iframe 的差异本质不是"技术"，是"风险"
iframe（昨天的方案）= 把"指针"放在 banmi DB，视频文件留 YouTube，YouTube 自带 Content ID 兜底，banmi 0 法律风险。真切片 = banmi 自己下载 + 切割 + 重新分发，每一份 mp4 都是"未经授权的复制+传播"。法律边界从 YouTube 转到了 banmi。
② Content ID 不是只扫公开视频 —— unlisted 也扫
阿杰的"上传 unlisted 当免费存储"假设走不通。YouTube 官方文档明确：unlisted 视频和 public 视频走同一套 Content ID 扫描，音频指纹 + 视觉识别 + 元数据三路对比，秒级触发。把别人 SciShow Kids 的片段重传 99% 被检出，下场是 muted / 强制下架 / 频道警告 / 多次后封号。
③ 国内访问决定一切：R2 / B2 / S3 全部不能直接覆盖国内
Cloudflare R2 不能在中国大陆建 bucket，标准 R2 域名走境外 PoP 被 GFW 干扰。Backblaze B2 / AWS S3 同理。要覆盖国内必须走双桶：境外用户 R2 / B2，国内用户阿里云 OSS 或腾讯云 COS，OSS 必须配 ICP 备案的域名，备案周期 3-22 工作日（实际平均 7-15 天）。
④ ffmpeg 切片本身很便宜，贵的是合规 + 运营
50k 片段处理在 1 台 Hetzner CX32（€6.80/月 / 4vCPU / 8GB）上跑 24-48 小时就完事，-c copy 零重编码秒级一条。真正烧钱的是：①CC-BY 频道清单维护（人工）②DMCA 响应（必须 24h 内删）③双桶同步流量（国内出口 0.24-0.50 元/GB）④备案 + 公安备案的法务时间。
⑤ 给阿杰的最终建议（50 学员档）
不做真切片。继续昨天的 iframe 跳 timestamp 方案 + Layer 1 用 YouGlish 公开 widget。把"真切片"留作 V0.4 候选，触发条件：(a) 学员 ≥ 500，且 (b) YouGlish 不够用，且 (c) 法务能投入 0.5 人月办备案和清 CC 白名单。在那之前每个月的真切片研究时间换成"AI 选句算法 + 用户使用数据收集"投入产出比高 10 倍。

02iframe vs 真切片 · 8 维度并排▼

昨天报告（youglish-tech.html）讲的是 iframe 路线：banmi 自建字幕索引，但视频文件留 YouTube，前端嵌 YouTube IFrame Player 跳 timestamp 播放。今天讨论的真切片路线是另一回事 —— 整段下载到自己服务器，ffmpeg 切成独立 mp4，自家 CDN 分发，前端 <video> 标签直接播。从外部看两者用户体验相似（都是"输入词 → 出片段 → 播 5 秒"），但内部从工程到法律完全不同。

维度iframe（昨天）真切片（今天）判定

🎯 一句话总结：iframe 路线把所有难题外包给 YouTube（版权 / 存储 / 带宽），代价是国内不可达 + 体验稍差。真切片把这些拿回到 banmi 手里，代价是变成内容平台，承担版权 / 存储 / 带宽 / 备案的全部责任。这不是"哪个技术好"，是"banmi 想做工具还是想做内容平台"。

3.2 他们为什么不切片 —— 三个克制理由

① 版权外包。YouGlish 不存视频文件，理论上不构成"复制"或"传播"，DMCA 只能找上传者，找不到 YouGlish。这是他们能扛到 1 亿+ 片段不被关停的根本原因。
② 带宽外包。1 亿片段 × 月均 3 次点击 × 平均 8 秒 × 1Mbps ≈ 900 PB/月 的带宽，自托管在任何云上都是天文数字（即便 R2 零出口费，源站 IO 也撑不住）。让 YouTube 自己消化这个流量是唯一可持续做法。
③ 内容增量外包。YouTube 每天新增 720k 小时视频，YouGlish 写个 cron 拉新视频字幕就行；自切片就要每天 ffmpeg 几万次，pipeline 永远在跑。
对 banmi 的镜像启示：YouGlish 选 iframe 是看了 1 亿规模的账本。banmi 规模就算 5000 学员 × 每人每天 30 词 ≈ 15 万次播放/天，仍然远不够"自托管划算"的临界点。真正促成切片决定的不应是"想自建酷"，而应是"iframe 真的提供不了的体验"（比如循环、慢速、字幕高亮 —— 但这些 iframe 也都能做）。

04谁在做"真切片" · 8 家产品深挖▼

这一节把"真切片"路线上活下来的产品逐家拆。重点不是"他们怎么做"，是"他们做完之后命运如何"——版权 / 商业模式 / 现状。

① PlayPhrase.me — 真切片的最纯粹代表

仍在运营 Patreon 资助

做什么：输入英文短语，返回电影/电视剧里说过这句话的真实片段，能直接看演员怎么说、表情怎么动。截至 2026 年中数据库 3800 万+ 短语，覆盖几千部电影电视剧，每天新增 2000-5000 条。这是真切片，每个 clip 都是单独的视频文件，硬性上限 8 秒。

怎么活下来的：他们的 fair-use 公告写得极其谨慎：① 每段硬限 8 秒 ② 链回 IMDb 引流原作 ③ 禁止 API 访问，禁止商用 ④ 仅靠 Patreon 收捐款，不卖订阅、不卖广告 ⑤ 收到 DMCA 24 小时内删。整套策略本质是"我穷且非盈利且学术 → 别告我"，靠美国合理使用四要素第 4 条（不影响原作市场）。

有没有被告：公开记录里搜不到针对 PlayPhrase 的正式诉讼，多年 DMCA 删除记录倒是有。这说明 fair-use 论点在实践中扛住了 majors（华纳/迪士尼）的审查 —— 但前提是不商业化、不规模化。

技术栈推测：自动 ASR + 字幕对齐 + 自动切片 + S3 风格对象存储（看视频 URL 多半 CloudFront）。8 秒 × 3800 万 ≈ 60TB 存储，年成本 $5-10k 量级，完全可由 Patreon 覆盖。

真切片 + 公益化 + 硬上限 8 秒 + 禁 API + 链回原作 = 教科书级"如何让 fair-use 站住"。但 banmi 是商业产品，照抄不了这套。

② Yarn (getyarn.io) — 切片 + GIF + 内容引流

仍在运营 商用

做什么：电影 / 电视 / 音乐短语搜索，能下载 GIF 或视频 clip 分享到社交。商业化比 PlayPhrase 更深，2015 年 TechCrunch 报道时已经有 app + 内嵌 iMessage / Twitter 分享。

他们的法律论点：在 ToS 里写明 —— 不实际托管原片，"只托管 tiny clips and metadata"，把 clip 描述成"广告片"，引流回原作。和 PlayPhrase 类似但更激进，允许下载 GIF / clip 给社交媒体二次创作。

怎么活下来：和内容公司谈"导流合作"（pilot 阶段），把自己定位成"trailer / 引流方"而不是"竞争平台"。和 YouTube 的关系比 PlayPhrase 紧密，受众更年轻。

商业模式：B2B SaaS 卖给媒体公司做内部"视频内容搜索"工具（"我们这套搜索引擎也可以帮你搜你自己的视频库"），to-C 端免费引流。

B2B 把工具卖给版权方自己 = 把法律对手变成客户。banmi 长大后可以借鉴：把切片技术卖给国内出版社（新东方 / 学而思）做内部词典工具。

③ FluentU — 名义上"用 YouTube"，实际是 iframe + 自制

混合模式 订阅 $30/月

真相：FluentU 早期宣传"YouTube 视频学语言"，但他们的开源项目 fluentu-youtube-facade（GitHub 上能看到）暴露了真实做法 —— 用 facade 占位图 + 延迟加载 YouTube iframe。这就是 iframe 模式，不是真切片。

当前库存：~2261 视频/音频片段，6 个难度级，12 种内容类型。视频平均小于 5 分钟。比起 YouGlish 的 1 亿+ 是个小库，因为他们做了"精选 + 加交互层"。

怎么处理版权：① 大量内容是 FluentU 团队自制（特别是低级别学生用的）② YouTube 部分用 iframe 不下载 ③ 字幕和互动注释是他们自己加的 —— 这部分他们持有版权。

商业上算成功吗：订阅 $30/月，10+ 年没倒。但用户评价"内容更新慢"——这正是"精选 + iframe"路线的代价：每加一个视频都要人工标注。

FluentU 是"iframe + 精选 + 自家注释层"的标杆。banmi 完全可以照抄：iframe 播 + banmi 自己加字幕高亮 / 中文翻译 / 词卡 → 这部分是 banmi 独家版权。

④ Lingopie — Netflix 学语言，正规授权路线

仍在运营 授权制

做什么：Netflix 风格语言学习，目标语原创剧集 + Lingopie 自制内容。2026 年 4 月推出 Chrome 扩展，让你直接在 Netflix 网页上点字幕查词 + 存生词本。

关键事实：他们不切片，也不下载 Netflix 视频，扩展只是给 Netflix 现有页面注入翻译/词典 UI。这避开了 Netflix DRM 和版权问题。库里"Lingopie 自家"的剧集都是正规拍摄或正规授权，不是抓的 YouTube。

商业模式：$12/月订阅，5000+ 小时内容，11+ 语言。融了几轮 VC，明显走"正规授权 → IPO"路线。

想做"严肃"切片库就要付授权费，Lingopie 这套对 banmi 50 学员阶段太重，但 V0.5+ 切到"自制 + 部分授权"是可能的演进路径。

⑤ Voscreen — 短剧切片 + 游戏化测试

活但小 免费

做什么：从电影 / 电视剧 / 音乐 MV 选 10-30 秒短片，让用户听 → 选正确翻译。游戏化、按语法点（"现在时" / "名词从句"）分类。

切片性质：每条都是切好的独立短片，这是真切片。土耳其团队做的，库不大（几千条），运营多年没被告。

怎么活下来：① 完全免费 ② 学术合作引用了好几篇论文（"learn through videos"） ③ 单条 10-30 秒 ④ 没有完整剧集回放，只能"测试"不能"看片"。

"按语法点切片" + "强制选择题答完才看下一条" = 把内容包装成测试，单条永远短，从体验上让用户不可能"看完整剧"。这套包装把"消费"伪装成"学习"，是真切片产品自保的标准动作。

⑥ Reverso Context — 文本为主，视频是 iframe

仍在运营 大公司

做什么：双语例句词典，每个词组返回 50+ 上下文翻译。主要数据是字幕和文献的文本。"视频"部分是 Chrome 扩展在 Netflix 字幕上注入翻译，不是托管视频。

切片性质：实质上不切片，只切"字幕文本"。这是另一种"绕开版权"的玩法 —— 字幕作为汇编作品的法律地位比视频本体宽松得多。

"只切字幕文本不切视频" 是 banmi 还没充分挖掘的路线 —— 词卡显示句子（文字）+ iframe 跳秒看原片，比真切片轻得多，前端体验也接近。

⑦ Subadub / Subreader 等字幕工具

浏览器扩展

都是浏览器扩展或独立播放器，不存储任何视频，只增强现有播放器（Netflix / 本地 mp4 / VLC）的字幕功能 —— 例如 Subadub 让你在 Netflix 上单击字幕查词、复制句子。版权策略：扩展不分发内容，分发"用户体验增强"。Subreader 在欧洲法庭被告过，但赢了，理由是不复制原作。

如果 banmi 哪天敢做"在用户自己看 Netflix 时给翻译"，就走扩展路线，不碰视频本体。法律最干净，但前提是用户已经付了 Netflix。

⑧ YouGlish — 当成参照系，再强调一遍

市占率第一 iframe

1 亿+ 片段，22 种语言，纯 iframe。F12 检查任何片段都是 youtube.com/embed/...。他们的 fair-use 不是论点是事实 —— 他们根本不持有内容。这是 banmi 的默认路线，需要离开它必须有强理由。

市占率第一的产品在最关键的技术选择上选了 iframe，这是最大的信号。

6.2 ffmpeg 三种切片策略

推荐 95%

策略 A：精确切（重编码）

# 精确到毫秒，padding 前 0.5s + 后 1s（避免说到一半切断）
ffmpeg -y \
  -ss 00:01:23.500 \           # 起点 (sentence_start - 0.5s)
  -i raw/voa/abc.mp4 \
  -t 8.500 \                   # 长度 = duration + 1.5s padding
  -c:v libx264 -preset veryfast -crf 23 \
  -c:a aac -b:a 96k \
  -movflags +faststart \            # mp4 web 优化（moov 移到开头）
  -vf "scale=854:480" \           # 降到 480p 省流量
  out/clips/${clip_id}.mp4

毫秒精度对齐句子边界；web 友好（faststart）；480p 一段 5-8s 约 500-800KB；CPU 成本 1 段 ~0.5s 在 Hetzner CX32 上。

每段重编码，5 万段 ~7 小时 CPU 时间。

仅用于预览

策略 B：零重编码快切

ffmpeg -ss 00:01:23 -i in.mp4 -t 8 -c copy out.mp4

毫秒级速度（1 段 < 100ms），CPU 0%；适合做"批量预览版"快速验证选句质量。

起点对齐最近的关键帧（每 2-5s 一个），实际起点可能提前 0-5s；某些播放器开头黑屏几帧；不适合最终产品。

双 -ss 技巧

策略 C：seek 加速精切

ffmpeg -ss 00:01:22 -i in.mp4 -ss 1.5 -t 8 -c:v libx264 ...

第一个 -ss 在 -i 前 → 快速 seek 到大致位置（不解码）；第二个 -ss 在后 → 精确再走 1.5s（解码）。比策略 A 快 30-50%（特别是视频很长时）。

命令复杂，易写错；策略 A 在 banmi 量级已经够快。

11YouTube unlisted 当存储 · Content ID 死局▼

阿杰提的这个方案听起来太美：YouTube 免费存视频 + 自带 CDN + 全球分发，banmi 只用 iframe 嵌入自己上传的 unlisted 视频。如果跑得通，前面 Ch8 / Ch9 的整个 OSS 选型都不用了。但跑不通，这一节把死局拆透。

11.1 Content ID 是什么

YouTube 的版权保护系统，建于 2007 年，全球最先进的视频/音频指纹技术。每个新上传视频在处理阶段就被三路扫描：

  1. 音频指纹：哪怕音轨被略调速 / 变调 / 加杂音，还能匹配出原作，例如把电影台词加上背景音乐重发，仍被识别
  2. 视觉识别：画面像素级指纹，logo / 卡通形象 / 特殊字幕样式都能匹配
  3. 元数据匹配：标题 / 描述 / tag 与已知版权作品对比

11.2 关键事实：unlisted 也扫

YouTube 官方文档原文（Help 2797370）：
"YouTube uses Content ID to automatically detect copyrighted material in videos — even if they're set to private or unlisted."

换句话说，unlisted 不是法外之地。Content ID 在视频上传完处理流水线就开扫，与 visibility 设置无关。

11.3 命中 Content ID 的下场

触发结果概率对 banmi 影响
视频被静音（mute audio）10%（音乐版权）banmi 学员听不到原句，废

11.4 频道累积风险

  • 3 次 Content ID 命中：可能触发频道警告（每次有 7 天异议窗口）
  • 3 次 DMCA 实证警告（不同于 Content ID）：直接封号
  • 同一 IP 多个账号反复上传被检测内容：YouTube 反作弊封 IP
  • 每天上传量级：API 默认 quota 10000 units/天 + 频道实际上传日上限 ~100 个视频（非官方但社区共识），banmi 切 5 万段 → 500 天才传完，显然不现实

11.5 YouTube ToS 第一条

YouTube Terms of Service Section 5 明确禁止："You are not allowed to: access, reproduce, download, distribute, transmit, broadcast, display, sell, license, alter, modify or otherwise use any part of the Service or any Content except as expressly authorized by the Service."

"用 YouTube 当 SaaS 存储后端"是明确违反 ToS 的商业行为。即使 Content ID 全过（不可能），banmi 也是在 YouTube ToS 红线上跑，随时可能被人工运营介入封号。

11.6 国内打不开

就算上面所有问题都解决，YouTube 在国内不可达。banmi K12 学员 99% 在国内，要么放弃这个方案，要么同时建一套自托管（双重存储成本，比 OSS 单桶更贵）。

11.7 例外：什么情况能用 YouTube unlisted

✅ 唯一可行的子场景：banmi 自制原创视频（半米拍的教师讲解 / 词卡动画），上传到自己的 YouTube 频道做海外用户备份分发（不依赖 unlisted 当主存储，主存储仍是 OSS / R2）。这种情况：① Content ID 不命中（自己的内容） ② 不违反 ToS（自己有版权）③ 海外用户可达。

但这个场景下，YouTube 的角色是"二级 CDN"而不是"主存储"，作用有限。
🚫 死局明确结论：把别人 YouTube 视频切片后重传 unlisted 当 banmi 存储 = 三条死路（Content ID + ToS + GFW）合三为一。这条路完全堵死，不再考虑。

12法律风险红黄绿 + CC-BY 安全清单▼

这节给 banmi 一个可操作的版权决策矩阵。每个频道 / 内容来源进 banmi 切片库之前，先按这套绿/黄/红打标签。

12.1 三档安全清单

🟢 绿区：可以切，无任何法律风险

  • 美国公版（Public Domain）：VOA Learning English（美国政府作品，全球公版，允许商用，只需 credit "learningenglish.voanews.com"）
  • banmi 自制视频（教师讲解 / 自录场景）：banmi 持有完整版权
  • CC0 频道：Wikimedia Commons 部分内容、NASA / NIH 等政府教育视频、维基百科上的 OER 视频
  • 已购买独家授权：和某出版社或 YouTube 创作者签的 banmi 独家使用协议

操作要求：在 clips 表标 license='public-domain' 或 'own' 或 'licensed'；前端片段下角标注源；不需要担心 DMCA。

🟡 黄区：可以切，但需小心 + 限制

  • CC BY-NC-SA：Khan Academy 大部分课程视频（非商业 + 同样授权 + 署名）
  • CC BY 4.0 国际：部分 TED-Ed 课程、部分 Crash Course Kids（看每个视频底栏标识）
  • 开放教育资源（OER）：MIT OCW、Open University 等

关键陷阱：① Khan Academy 是 NC（非商业）—— banmi 收钱后切 Khan Academy 内容违反 CC license。这是 banmi 商业化后最大的"红 vs 黄"灰色地带。② SA（同样授权）意味着 banmi 自己加的字幕高亮 / 翻译也得 CC 同样许可，这影响 banmi 的"自家增值"商业逻辑。

操作建议：banmi 50 学员阶段如果定价偏教育性（非营利或微利）可以走 NC 灰色地带；500+ 商业化后必须切到只用 BY（无 NC）授权。

🔴 红区：禁切，违法风险高

  • 电影 / 电视剧（华纳、迪士尼、Netflix 等）：完全没合理使用空间，DMCA 必送
  • 音乐 MV：UMG / Sony / Warner Music 旗下，秒被 Content ID 检测
  • SciShow（标准频道）/ TED 主站：默认版权保留（all rights reserved），即使是教育内容也不能切重传，只能 iframe
  • BBC / NHK / CNN 新闻：政府新闻可能 fair use，但版权方激进
  • 所有标"All Rights Reserved"的 YouTube 视频（YouTube 默认）

操作要求：直接黑名单，pipeline 入库时 license 校验 = "standard YouTube" 的跳过。这些内容只走 iframe 路线（昨天方案）。

12.4 DMCA 操作 SOP

  1. 邮箱设置：dmca@banmi.app，专人监控（运营 / 法务）

13.1 Next.js API route 代码（50 行复刻 banmi clips API）

// app/api/clips/route.ts
import { NextRequest } from 'next/server';
import { db } from '@/lib/db';
import { redis } from '@/lib/redis';

export const runtime = 'edge';
export const revalidate = 3600;

export async function GET(req: NextRequest) {
  const { searchParams } = new URL(req.url);
  const lemma = searchParams.get('lemma')?.toLowerCase().trim();
  if (!lemma) return Response.json({ error: 'lemma required' }, { status: 400 });

  // 1. 检测用户区域（决定走 R2 还是 OSS）
  const country = req.headers.get('cf-ipcountry') ?? 'XX';
  const isChina = country === 'CN';
  const cdnBase = isChina
    ? 'https://cdn-cn.banmi.app'     // 国内阿里云 / 七牛
    : 'https://r2.banmi.app';        // 海外 Cloudflare R2

  // 2. Redis 缓存（热门词 24h）
  const cacheKey = `clips:${lemma}:${isChina ? 'cn' : 'g'}`;
  const cached = await redis.get(cacheKey);
  if (cached) return Response.json(JSON.parse(cached));

  // 3. 主查询：按 quality_score 取 top 5，排除 takedown
  const rows = await db.sql`
    SELECT id, channel, sentence_text, start_ms, end_ms,
           ${isChina ? db.sql`oss_key` : db.sql`r2_key`} AS key,
           quality_score, cefr, license, video_id
    FROM clips
    WHERE word_lemma = ${lemma}
      AND takedown_at IS NULL
      AND has_profanity = FALSE
    ORDER BY quality_score DESC
    LIMIT 5
  `;

  // 4. 拼装 cdn 完整 url
  const clips = rows.map((r) => ({
    id: r.id,
    channel: r.channel,
    text: r.sentence_text,
    duration_ms: r.end_ms - r.start_ms,
    cefr: r.cefr,
    license: r.license,
    src: `${cdnBase}/${r.key}`,
    score: Math.round(r.quality_score * 100) / 100,
  }));

  const body = { lemma, count: clips.length, region: isChina ? 'cn' : 'global', clips };
  await redis.setex(cacheKey, 86400, JSON.stringify(body));
  return Response.json(body);
}

'use client';
import { useRef, useEffect, useState } from 'react';

export function ClipPlayer({ clip }: { clip: Clip }) {
  const ref = useRef<HTMLVideoElement>(null);
  const [loop, setLoop] = useState(true);
  const [rate, setRate] = useState(1);

    v.play().catch(() => {});  // iOS 需 user gesture，第一次会 fail

      <video
        ref={ref}
        src={clip.src}
        muted
        playsInline    /* iOS Safari 必加 */
        controls={false}
        loop={loop}
        autoPlay
        onCanPlay={() => ref.current?.play()}

        </button>
        <button onClick={() => ref.current?.play()}>▶️ 重播</button>
      </div>
      <p className="clip-meta">
        {clip.channel} · {clip.license} · 质量 {clip.score}
      </p>
    </div>
  );

15FAQ · 12 条阿杰可能想问的▼

Q150 学员阶段值不值得做真切片？+
不值得。理由：① ROI 算不过来（成本 ¥80/月 + 一次性 ¥150k + 0.5 人月备案，对比 iframe ¥0/月 + 0 一次性） ② 国内可达对 50 学员是"nice to have"不是"必须"，可以让早期学员翻墙看 demo ③ 时间应该花在"AI 选句质量"和"词卡 UX"上，那些是 banmi 独门，切片是别人也能做的。
Q2iOS Safari 上 mp4 自动播放限制怎么解？+
三个属性必加：muted + autoplay + playsinline。muted 是 Safari 自动播放的强制条件（iOS 10+ 政策）；playsinline 让视频在页面内播不强进全屏（这是 banmi 词卡场景的关键）；autoplay 触发自动播。还有一条隐藏限制：iOS 在低电量模式下永远不自动播 —— 这没办法绕，前端要写降级 fallback（"点击播放"按钮）。
Q3字幕版权和视频版权分开吗？+
法律上是分开的。字幕作为汇编作品 / 翻译作品有独立版权，归字幕制作者所有（YouTube 自动字幕是 Google ASR 生成，但 YouTube ToS 把使用权授给上传者）。banmi 把字幕索引化（"哪句话在哪个视频的几秒"）相对安全，PlayPhrase / Reverso 都用这个论点。但你抓字幕全文 + 重新发布就构成字幕复制（仍违法）。banmi 只内部索引、前端展示句子片段（合理使用 fragments）是相对安全的灰区。
Q4DMCA takedown 实际多久收到？怎么应对？+
根据 YouTube 数据，DMCA 收到后主流 24-72h 内处理，部分 case 一周内。banmi 不是 YouTube 量级，初期收到的频率会很低（每月 0-2 件预估）。响应 SOP：① 收件箱 dmca@banmi.app 配企业邮箱告警 ② 24h 内删 mp4 + 设 clips.takedown_at ③ 邮件回复确认 ④ 月底 review 找规律（哪些频道反复来）。一年内累积 > 50 件就要重新评估"真切片"路线值不值得。
Q5Whisper 重抓字幕比 YouTube 自动字幕好多少？+
Whisper Large-v3 在 LibriSpeech ~2.7% WER，真实英语 8-12% WER。YouTube 自动字幕在清晰录音 5-15% WER（标点 / 专有名词差很多）、嘈杂场景 30%+。核心差异不在 WER 本身，在标点和句边界 —— Whisper 给完整标点和句子，YouTube auto 几乎没有标点。banmi 切片要求知道"句子在哪里开始/结束"，YouTube auto 几乎不可用，必须 LLM 加标点 or Whisper 重抓。

Whisper 重抓成本：5000 视频 × 平均 10 分钟 × Whisper-large-v3 在 RTX 4090 ~5x realtime → ~17 小时 GPU 时间 ≈ ¥50。划算。
Q6为什么 PlayPhrase 没被告？banmi 能复制吗？+
PlayPhrase 没被告的理由不是法律站得住，是它没有商业利益：纯 Patreon 捐款、无 API、无订阅、单段 ≤ 8s、链回 IMDb。版权方告它没 ROI（赢了拿不到钱）。banmi 是商业 SaaS K12 收费产品，有钱可拿，版权方告 banmi 的动力远高于告 PlayPhrase。所以 PlayPhrase 模式 banmi 不能完全复制，但可以借鉴它的"硬限 8s + 引流 + 多 license 标识"这套姿态降低风险。
Q7国内 ICP 备案下来要多久？卡点在哪？+
官方周期 3-22 工作日，实际平均 7-15 天。三大卡点：① 法人手机号要在工信部 24h 内接电话核验，错过 → 重来 ② 新注册域名要等 2-3 天才能提交备案（域名入库延迟）③ 部分省份管局严格，地址 / 公司经营范围不匹配会被驳回（这个最坑，可能多花 1-2 周）。

实操建议：找阿里云 / 腾讯云的"备案管家"（一般打包卖，¥0-500），他们熟悉本地管局规则。
Q8YouTube 不允许 yt-dlp 下载，banmi 用了不会被告吗？+
YouTube ToS 第 5 条明确禁止下载，但实际从未起诉过任何使用 yt-dlp 的项目。RIAA 在 2020 年试图让 GitHub 下架 youtube-dl，被推回（GitHub 用 fair use 论据复活了仓库）。Google 实际维权是 IP-level 限速 / cookie 失效，不是法律层。banmi 用 yt-dlp 抓字幕是行业默认操作（YouGlish / PlayPhrase 都这样），用 yt-dlp 抓完整视频本体风险更高 —— 抓回来切片后重新分发才是真违规，单纯下载到自己机器还能解释成"个人备份"。banmi 应该把切片机当短驻处理盘，切完即删原视频，降低法律暴露。
Q9如果 5000 学员阶段决定做真切片，最早什么时候开始备案？+
提前 6 个月。备案 + 公安备案 + 域名 + 服务器 + 域名解析 + CDN 接入 + DMCA SOP + 法律咨询 + pipeline 开发 = 串行做大约 4-5 个月。从 V0.3 进入 V0.4 之间的过渡期就要启动，避免"500 学员里有 200 个在抱怨国内卡了"再来临时抱佛脚。

另：备案企业主体可以提前一年办（banmi 已经是企业了应该已有），手续不复杂，办了不亏。
Q10切片精度差 0.5s 用户能感觉到吗？+
能。词卡场景下学员重点听目标词那两个音节（200-400ms），片段开头如果切掉前 200ms 就没了上下文（"My cousin significantly improved" 切成 "icantly improved"），重听 3-5 次后学员会困惑。所以 banmi 必须用 ffmpeg 精切（重编码） + 前 0.5s padding，不能用 -c copy 快切。这是真切片相比 iframe 的核心质量优势 —— iframe 的 YouTube IFrame API seekTo 精度只有 ±0.5s，无法保证。
Q11如果 R2 / 阿里云一家挂了，怎么 fallback？+
双桶天然提供 fallback —— 前端拿不到主 CDN 后立即试备用： 
const trySrc = async (clip) => {
  for (const base of [primary, fallback]) {
    try {
      const ok = await fetch(base + clip.key,
        { method: 'HEAD', signal: AbortSignal.timeout(800) });
      if (ok.ok) return base + clip.key;
    } catch {}
  }
  // 最后兜底：iframe YouTube 原视频 timestamp（昨天方案）
  return youtubeFallback(clip.video_id, clip.start_ms);
};
多层降级：主 CDN → 备 CDN → iframe YouTube。这是为什么 banmi 永远要保留 iframe 路线，不能把 V0.3 之前的索引数据废掉。
Q12阿杰最该警惕的"坑"是什么？+
"我已经投了 50k 开发，不能止损"陷阱。真切片 pipeline 一旦开发出来，阿杰 / 三丰会有"既然写了就用满"的冲动，开始切灰区 / 红区频道（"反正没人告过"）。这是路线性失败模式。

对冲方法：① 立项时定明文 SOP，红区频道直接 channels.yaml 黑名单，pipeline 入库时硬卡 license 校验 ② 每月人工 review 一次实际切的频道清单 ③ 律师季度审一次 ④ DMCA 累积超过预设阈值（每月 > 5 件）自动触发"切片暂停"评估会议。

另一个常见坑：把"切片体验"过度包装成卖点，让运营 / 销售对外宣传"banmi 有 5 万独家视频片段" → 这就是版权方搜索关键词。低调，切片是后端实现细节，不是营销话术。
