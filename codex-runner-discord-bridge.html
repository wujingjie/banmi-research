后台 Coding Agent Runner 对接 Discord：实时通知 + 一个 Bot 双向驱动

📅 2026-05-30 🔍 无忌 Deep Research · 5 路并行 🤖 Codex runner · Claude Code · Gemini 📐 出站易 · 入站难 🌍 海外视角
一句话：把 Wave 里全天跑的 Codex runner（Codex 调 Claude Code 跑 + 自审）接到 Discord，要分清两件难度天差地别的事——① 出站通知（runner→Discord，单向，今晚就能上）极简，一个 webhook 就够[1]；② 入站驱动（Discord 发指令→触发后台 runner，双向）才是真功夫，需要一个常驻 Bot 进程长连监听[9]。出站建议先上 codex exec --json 事件流管道推 webhook[2]；入站建议直接用现成 gateway（OpenClaw / cc-connect / OpenACP）而非从零自建——Codex 没有原生 channels 必须搭桥，但桥已经有人造好了[4]。本报告给 A/B/C 三梯度方案，从「最省事单向通知」到「一个 Bot 统一驱动 Codex+CC+Gemini」。

01执行摘要：5 条最硬结论▼

5 路并行调研（现状拆解 / Claude Code channels+通知 / Codex 桥接 / 统一 Bot 架构 / 完整方案落地）收敛出的核心判断，每条独立成块，方便扫。

✅ 结论 1：出站通知今晚就能上——webhook + codex exec --json 是零依赖最快路径 🟢 官方机制

codex exec --json 把 stdout 变成 JSONL 事件流，逐行吐 thread.started / turn.started / item.completed / turn.completed（item 含命令执行、文件改动、plan 更新、token 用量），这是把后台进度实时推 Discord 的天然事件源[2]。串一个极简脚本把感兴趣的事件 curl 到一个 Discord incoming webhook（频道设置里 1 分钟建好、免写 bot）就成[1]。这一步与现状零冲突、不需要 bot token、不需要公网，是回报最快的一步[20]。

🎯 结论 2：出站易、入站难——这是全篇最该先记住的分界线 🟢 边界判断

出站（进度→Discord）极简：webhook 即可，单向、零依赖[1]。入站（Discord 发指令→触发 runner）才是难点：webhook 做不到，必须有一个常驻 Bot 进程（gateway 长连）去监听 Discord 消息再 spawn runner[9]。把两件事拆开、分阶段做，比一上来想"一个 bot 全包"更稳——很多人卡住就是因为把"看进度"和"派任务"混成一件事[20]。

💡 结论 3：Codex 没有原生 channels，但桥已造好——不用从零搭 🟢 已知事实+现成方案

Anthropic 官方 Claude Code Channels 只能遥控 Claude Code 自己（无忌正用这套），驱动不了 Codex[7]。但 Codex 接 Discord 完全可行：现成统一 gateway 里 cc-connect（~11.1k star、Go、Discord 走 Gateway 无需公网 IP、Codex+CC 同一个 bot、流式回推）[4]、OpenClaw ACP（一个 gateway spawn 多 harness、逍遥已在用）[13]、OpenACP（中立 gateway、带 REST API 可被外部脚本触发）[11]三者都把 Codex 纳入了同一个 bot——阿杰说的"一个 Bot 驱动所有任务"是现成的[10]。

🧭 结论 4：自审循环别动，但全天编排别让 Codex 当 orchestrator 🟡 方向判断

「Codex 调 CC 跑 + 自审」这条跨模型自审循环本身保持不动（这正是阿杰全局 CLAUDE.md 里那套 SOP，业界主流做法）[5]。但"全天任务编排 + Discord 驱动"这一层不要交给 Codex 当总控——Codex 没内建队列/并发/状态，它的 scheduled 走桌面 App 的 Review inbox（攒着事后看），不适合 Discord 实时驱动[6]。编排交给 CC channels（最熟）或 OpenClaw（最强统一），由它 fire-and-forget 拉起 Codex runner——即"上层 CC/OpenClaw 驱动，下层 Codex 跑 + 自审"[22]。

⚠️ 结论 5：Wave 只是壳，别指望它做远程通知；安全是入站的硬门槛 🟢 文档证实

Wave Terminal 在这套里只是"跑 runner 的容器 + 持久化输出"，wsh notify 只发本机桌面通知，到不了手机 Discord——真正的 Discord 对接发生在 runner 命令层，跟 Wave 解耦，换掉 Wave 方案照样成立[3]。另一条硬门槛：一旦做入站驱动，"在 Discord 发指令就能让你机器跑命令"等于把 shell 开放给了一个聊天频道——必须上白名单（per-channel opt-in / admin_from）+ 权限模式（yolo vs 逐条审批），别让任意人驱动你的机器[8]。

一句话路线建议（给阿杰）

【第 0 步·今晚】Wave 里 runner 不动，启动命令从 codex exec 改成 codex exec --json | notify.py，notify.py 挑 item.completed / turn.completed 推一个 Discord webhook——立刻"不盯电脑看全天进度"[2]。【第 1 步·这周末】要双向驱动就选 gateway：想统一 Codex+CC+Gemini（逍遥也在）走 OpenClaw ACP（沉没成本最低）[13]；想最快最稳走 cc-connect（11k star、支持 Codex、无需公网）[4]；想用最熟的退路走 CC channels 当调度员（无忌已验证）fire-and-forget 拉 Codex[9]。【不动】Codex 调 CC 自审循环保留。【上白名单】入站第一天就锁 allowlist。详见第 7、12 章。

⚠️ 最大不确定性：现成桥的"流式粒度"和"嵌套自审进度归属"都需本地实测 🟡 待核

几个最该谨慎的 gap：① cc-connect 对 codex exec --json 流的解析到底推到 item 级还是只 turn 级，文档只说"streaming"，需本地跑一次验证[4]。② Codex 调 CC 自审时，子 agent(CC) 的进度是否冒泡进 Codex 的 --json 流 / hooks未确认，可能 CC 那侧要单独挂 Stop hook[2]。③ codex-marketplace 的 Discord 通知插件成熟度低（仅 1 upvote），未验证 2026-05 最新 Codex 上是否仍可用[14]。④ 没有任何工具能 attach 到 Wave 里已手动起跑的 runner 进程接管其进度流——所有 gateway 都是 gateway 自己 spawn agent；要双向驱动只能让 gateway 接管 spawn，Wave 退回偶尔手动调试用[12]。

02需求拆层：通知（单向·易）vs Bot 驱动（双向·难）▼

把心智模型钉死：阿杰的两个需求难度差一个量级，混在一起想会卡住。先拆清，后面所有章节都按这条主线走。

① 需求一：实时进度通知（出站 · 单向 · 易）

"不盯电脑也能看 runner 进度"。数据流向：runner → Discord。

  • 用 Incoming Webhook 即可，不需要 bot token、不需要 bot 在线、不需要公网 IP[1]
  • runner 里一行 curl POST 就发出去了[10]
  • 5 分钟能跑通，与现状零冲突[20]

② 需求二：一个 Bot 驱动所有任务（入站 · 双向 · 难）

"在 Discord 发指令 → 触发后台 runner → 进度回推"。数据流向：Discord ⇄ runner。

  • webhook 做不到入站——它只能往 Discord 发，收不了消息[9]
  • 必须一个常驻 Bot 进程（Gateway 长连）监听 Discord 消息[4]
  • 还要 spawn 进程、解析输出回推、管权限、管多任务状态——这是 gateway 的全部活[9]

为什么 webhook 收不了消息？

Discord Incoming Webhook 本质是"一个对外开放的发消息 URL"——你 POST 给它，它替你在频道发条消息。它是纯出站的，没有任何"监听用户发了什么"的能力[1]。要"听见"用户在 Discord 说什么，必须有一个 bot 用 Gateway（WebSocket 长连）挂在 Discord 上，这就是为什么入站一定需要常驻进程[4]。

🎯 拆层后的落地顺序（本报告的主轴）

先吃下出站（需求一）——立刻见效、零风险、不动现有架构。再啃入站（需求二）——选一个现成 gateway，别自建。两步之间没有强依赖，出站做完照样独立可用。第 12 章给完整分阶段路线。

03现状拆解：Wave + Codex runner +「调 CC 跑 + 自审」到底是什么▼

阿杰这套现状的每一块都查清楚了——每一块都已经有可直接利用的"出事件 / 推通知"接口，不需要从零搭桥[2]。三层拆解。

3.1 Wave Terminal —— 只是"跑 runner 的壳"

Wave 里一切都是 block。wsh run 把命令跑在新 block 里（-m 放大、-x 跑完关），block 输出由 Block Controller 持久化、跨 session 保留；v0.14 加了 Durable Sessions（SSH 断线重连不丢）[3]。Wave 自带 wsh notify "Build complete"——但这只是本机桌面通知，到不了手机 Discord[3]。

关键结论：Wave 本身只是"能跑常驻命令 + 持久化输出 + 本机桌面通知"的容器，它不负责把消息推到 Discord——这一步要靠跑在 block 里的那条命令自己做。换句话说，Discord 对接发生在 runner 命令层，跟 Wave 解耦，就算以后不用 Wave，方案照样成立[3]。

3.2 Codex CLI runner —— 三个对接金钥匙

核心是 codex exec（headless / 非交互，无 TUI、无审批），适合 cron / CI / 脚本；官方说全天跑后台任务的路径就是 cron + codex exec[6]。三个对接接口：

接口是什么适合
codex exec --jsonstdout 变 JSONL 事件流，逐行吐 thread/turn/item 事件（含命令执行、文件改动、plan 更新、token 用量）最丰富的实时进度源[2]
Hooks 系统SessionStart/PreToolUse/PostToolUse/Stop 等生命周期 hook，从 stdin 收 JSON，可跑任意脚本细粒度：每步工具调用/每轮结束播报[21]
notify（legacy）config.toml 顶部 notify=[...]，只在 agent-turn-complete 触发一次最简的"完成了"提醒（官方已推荐改 hooks）[16]

⚠️ 一个关键限制：Codex 的 hook 只在 turn 边界触发（turn 开始/结束），没有 mid-task 进度 hook——所以"实时进度"不能靠 hook，要靠 --json 事件流[22]。这是为什么本报告通知层首推 codex exec --json 而非 hooks。

3.3「Codex 后台调 Claude Code 跑 + 自审」是什么

这是当前最成熟、有现成实现的跨模型工作流，两种方向，阿杰这套大概率是其组合：

跨模型自审（最稳）：Claude 实现 → commit → Codex 作为审查方跑 git diff HEAD → 返回结构化 verdict（APPROVED / WARNING / BLOCKED）→ Claude 修 CRITICAL/HIGH → 重审，最多 3 轮。现成实现 ching-kuo/claude-codex（把 Codex 当 MCP server，codex 自己跑 diff 只回 verdict 省 token）——这跟阿杰 CLAUDE.md 里"Codex 跨模型审查"的 SOP 完全一致[5]。

Codex 当 orchestrator 调 CC 当 worker：codex-subagents-mcp（每次调用开干净 context + AGENTS.md 注入 persona + codex exec --profile <agent>），或 claude -p headless 被 codex exec 当子进程 fan-out（各自独立 git worktree）。Codex 已 GA subagents（manager 拆任务最多 8 个并行云沙箱，2026-03-14），3-16 CLI 也上了 sub-agent[18]。

⚠️ 待确认：阿杰"Codex 后台调 CC"的精确方向（orchestrator→worker 还是主→审，抑或双向）未由本人确认。两种现成实现都查到了，但落地脚本需按他实际方向适配 🟡[18]。

04Claude Code channels + 通知机制（无忌就是活例子）▼

Claude Code 在 Discord 对接上有两条官方原生路径，无忌正用其中一条——但能力边界很关键，搞错了就会"卡住不回 Discord"。

4.1 Channels 模式（无忌正在跑的）

Channels 是 research preview（需 v2.1.80+）：channel 本质是一个跑在本机、Claude Code 以子进程通过 stdio 拉起的 MCP server。它把外部事件 push 进一个【已经开着的】Claude Code session，官方 Discord 插件双向：Claude 用 reply/react/edit_message/fetch_messages/download_attachment 回推 Discord[9]。启动靠 claude --channels plugin:discord@claude-plugins-official[17]。

⚠️ 能力边界（三条硬伤，决定它适合做什么）

① 必须有一个 live session 才收得到消息，session 不开时消息【永久丢失、无离线队列】——always-on 要 tmux/screen + --dangerously-skip-permissions，关终端即掉线[9]。② 一个 session = 一个上下文，channels 是"把消息喂进我这个会话"，不是"每条消息开一个新任务"的调度器[9]。③ research preview，--channels 语法/协议可能变[9]。

这正是无忌（阿杰=channels 用户）已验证的活例子：无忌跑在 --channels plugin:discord 上，所以它的 CLAUDE.md 明确禁用 AskUserQuestion 等 TUI 控件——因为 TUI 框只在 tmux 里弹、Discord 端渲染不出来，会卡住等回答导致"不回 Discord"。这条经验直接说明：channels 适合"我跟一个 always-on 助手聊天派活"，不适合"派 N 个互不干扰的后台任务"[9]。

4.2 Hooks 做"实时进度通知"（不依赖 channels）

settings.json 里 Stop / Notification / SessionEnd / SubagentStop / PostToolUse 等事件都支持 command 类型 hook，可执行任意 shell（直接 curl Discord webhook），还有 http 类型 hook 直接打 webhook URL[19]。

这是最轻量、最可靠的进度推送方式：不依赖 channels、不依赖订阅类型，对 Codex 调起的 Claude Code 子进程同样生效（hooks 是 CC 自己的，谁调它都触发）[19]。如果阿杰的自审循环里 CC 那侧也想播报，这条直接挂上即可。

4.3 Headless / claude -p 后台 runner

claude -p + --output-format stream-json --verbose --include-partial-messages 拿实时事件流；--resume <session_id> 续接；--dangerously-skip-permissions / --permission-mode acceptEdits 无人值守[15]。

⚠️ 一个要提前知道的坑：2026-06-15 起订阅版 claude -p / Agent SDK 走【独立的 Agent SDK 月度额度】，跟交互额度分开算——阿杰要全天跑 headless runner，这条直接影响成本/额度规划，建议早确认 Pro/Max 计划下这块额度多大[15]。具体配额数字未查到 ⚠️。

4.4 现成参考：ebibibi/claude-code-discord-bridge（与阿杰愿景几乎 1:1）

自建 Discord bot 调 claude -p --output-format stream-json：每个 thread 映射一个独立子进程（各自 cwd/git worktree），REST POST /api/spawn 非阻塞起任务、POST /api/tasks 注册定时任务、SchedulerCog 30s 轮询，emoji/embed 实时回推进度，v3 支持 /backend claude|codex 运行时切后端——直接覆盖阿杰"Bot 驱动 + Codex runner"两点[10]。可直接抄架构或 fork。

5.1 ①【最佳·实时进度】codex exec --json 自建管道

不靠现成 Bot，直接管道。官方给出的范式：

codex exec --json "$TASK" \
  | jq -rc 'select(.type=="item.completed" or .type=="turn.completed")' \
  | while read e; do
      curl -sX POST "$DISCORD_WEBHOOK" -d "{\"content\": ...}"
    done

事件类型：thread.started / turn.started / item.started / item.completed / turn.completed；item 子类型含 command_execution / file_change / agent_message / reasoning / mcp_tool_call / web_search / plan_update[2]。强：实时进度最强、零依赖、完全可控、能精确选哪些事件推（如只推 plan 和命令执行避免刷屏）[2]。

5.2 ②【native·细粒度】Codex hooks.json（2026-04 上线）

现代生命周期钩子系统（取代旧 notify）。~/.codex/hooks.json 或 config.toml [hooks]，事件含 SessionStart/PreToolUse/PostToolUse/SubagentStart/SubagentStop/Stop 等，每个 hook 从 stdin 收 JSON（session_id, tool_name, tool_input, tool_response），跑命令即可 POST Discord webhook，exit 0 成功 / exit 2 阻断[21]。比 notify 粒度细、有 schema 校验，但钩子在 turn/tool 边界触发，非"每 token"流式[22]。

5.3 ③【最简·完成通知】legacy notify + Marketplace 一键插件

旧 notify：config.toml 顶部 notify=["python3","/path/notify.py"]，只在 agent-turn-complete 触发一次，传单 JSON arg（含 last-assistant-message）[16]。Codex Marketplace 有现成插件一行装：npx codex-marketplace add am-will/codex-skills/hooks/aitmpl-codex/automation/discord-notifications --hook，设 DISCORD_WEBHOOK_URL 即可——Codex 完成时触发[14]。⚠️ 该插件仅 1 upvote、成熟度未知，未验证最新 Codex 兼容性 🟡[14]。

6.2 三个 gateway 详解

🧩
OpenACP (Open-ACP)
MIT · TS · ~404★ · 中立 ACP gateway

想要"干净中立 gateway + 外部脚本/CI 触发 session"，这是最贴的。
🦅

逍遥在用 · 一 gateway 多 harness
沉没成本最低

弱：Discord 侧是"一个 agent 一个 bot account/token"（不是单 bot 多 agent，要给每个 agent 建 Discord 应用）；配置项多、上手曲线陡；多 gateway 实例要 slash_commands:false 防注册冲突[27]。

🌉

Go · ~11.1k★ · 最成熟 bridge daemon
最快最稳

星最多的 self-hosted bridge daemon，一进程多项目，明确支持 Codex+CC+Gemini+Cursor 10+，Discord 走 Gateway 无需公网 IP；/list /switch 管多 session（30 分钟闲置 rotate）；/mode yolo 自动批准 vs /mode default 逐条确认；admin_from 限特权用户、run_as_user 跑不同 Unix 用户做 OS 级隔离；支持自然语言 cron[4]。

弱：多 agent 是"多项目各自一个组合"偏个人遥控，不是 Discord 里多 thread 同时并行编排；无明确 REST API 触发（对"外部 runner 触发"不如 OpenACP 直给）[4]。

只想要最成熟、个人手机遥控、不追求多 agent 同屏并行——上手最快最稳。

7B.1 MC 现状：一个已运行的本地 Go 服务（本地实情）

阿杰的 MC = 本地 Go 服务，代码在 /Users/jay/Projects/mission-control，server 监听端口 3001。它不是设想、是已经在跑的服务，已具备：

7B.3 三个现成对接接口（本地实情）

① REST API → 驱动

Discord bot 收到指令后直接 POST / PATCH http://127.0.0.1:3001/api/tasks（带 MC_AUTH_KEY）即可建任务 / 改状态 / 查列表——零改 MC 代码。这就是第 9 章"驱动层"在阿杰这边最省事的落点。

② SSE /api/events/stream → 通知源

一个独立小进程订阅这条流，task 状态变更 / merge / review 结果直接推 Discord——零改 runner。这是第 8 章"通知层"在阿杰这边的天然出站事件源（比 codex exec --json 更高层、更干净）。

③ runner.log → 进度事件

逐行 tail：[runner] launch... / [merge-gate] fast-forwarded main / verdict=needs_fix 等。尤其 verdict=blocked 和"2 次失败封顶"最该 ping 阿杰——这俩是真正需要人介入的点，其余可静默。

7B.4 两个关键约束

⚠️ 约束 1：MC 纯本地 127.0.0.1、无 remote

MC 只监听本机回环，没有公网入口 → Discord bot 必须跑在同一台机器上（或同网段内能打到 3001 的机器）。这跟本报告"Gateway 长连无需公网"的结论不冲突——bot 的出站 Gateway 连接不用公网，但 bot 进程本身得贴着 MC 跑。

❌ 约束 2：阿杰的 v2 协议有两条硬红线，别踩

① agent 不能直接 PATCH status=done——只能推到 review，done 由 verification + reviewer 投影出来。Discord bot 同理：让它建任务 / 推到 review 可以，别让它代写 done。

② v2 协议把"外部服务 / 代用户发消息"列为 stop condition。所以：让 runner 主动推 Discord 必须阿杰显式授权，且要做成 runner 外挂的独立 watcher（读 log / 订 SSE 后再推），绝不要把"发 Discord"塞进 agent 的 prompt——否则会触发 agent 自己的安全停机，整条循环卡死。这是本章最该记住的一条。

08通知层怎么做（webhook / hooks 具体）▼

出站三选一，建议先上事件流管道。三条路可叠加。

  • 能精确筛事件类型（如只推命令执行+plan）

路 ②：Codex hooks.json（细粒度）

给 Codex 配 Stop + PostToolUse hook，从 stdin 收 JSON（含 tool_name / exit_code），脚本 curl webhook，每步工具调用都能播报[21]。

8.1 防刷屏：节流 + Discord 限速

⚠️ Discord 限速：实时推每个 PostToolUse 可能触发 429 限流（Discord 约 30 req/min + 单条 2000 字符上限），实操要 batch / 节流[20]。用 WebhookClient 会自动处理 429 重试，发 webhook 不需 bot token；shell 端 discord.sh 仅需 curl+jq[20]。未实测：高频事件下的具体限流阈值需自己跑一次确认 ⚠️[2]。

阿杰是 Codex 调 CC 自审。CC 那侧想播报，最干净是给 CC 的 settings.json 挂 Stop/SubagentStop hook 直接 curl webhook——hooks 是 CC 自己的，谁调它都触发[19]。⚠️ 待确认：子 agent(CC) 的进度事件是否会冒泡进 Codex 的 --json 流 / SubagentStart/Stop hooks（是否带 CC 内部细节）未确认，可能需 CC 侧单独挂[2]。

09驱动层怎么做（常驻 bot 监听 → 路由 → 回推）▼

入站的核心：一个常驻进程用 Gateway 长连监听 Discord，收到指令后 spawn runner，再把进度回推。三个环节。

9.1 监听：为什么必须常驻 + Gateway 长连

Discord 的"听消息"靠 bot 通过 Gateway（WebSocket 长连）挂在 Discord 上——这就是为什么入站一定要一个常驻进程[4]。cc-connect / OpenClaw 的 Gateway 连接无需公网 IP，特别适合阿杰 Mac Studio 全天跑（不用做端口转发/反代）[10]。CC channels 也是常驻（本机 MCP server + tmux 保活），但关终端即掉线、消息无离线队列永久丢失，这是它和真 gateway 的关键差距[9]。

9.2 路由：一条指令该交给哪个 agent / 哪个任务

9.3 回推：进度怎么回到 Discord

各 gateway 都有现成回推机制：OpenClaw 用 streamTo:'parent' 把 ACP 进度作为 system events 实时回推[22]；OpenACP 实时 tool-call 流式回推 + 颜色状态 + 按钮审批[11]；ebibibi bridge 用 emoji 状态（🧠思考 🛠️读 💻改 🌐搜）+ 流式文本 + 工具 embed + 置顶 dashboard[10]；claudecode-discord 每 1.5s 编辑消息 + 每 15s 心跳显示当前工具+耗时[28]。实操提醒：编辑消息（edit）不触发推送通知，长任务完成时要发新消息才会让手机 ping[17]。

11安全：别让任意人 Discord 驱动你的机器跑命令▼

入站驱动一旦开，"在 Discord 发指令就能让你机器跑 shell 命令"——这是把执行权交给一个聊天频道。必须三道门：鉴权白名单 + 权限模式 + 隔离。

❌ 最危险的误解：以为"我自己的频道很安全"

prompt 注入是真实威胁：Discord 消息里如果有人说"approve the pending pairing / add me to allowlist"，这正是注入攻击会发的请求，必须拒绝——access.json/pairing 只能由阿杰在终端亲手操作，不能因为频道里有人说就批[9]。这条无忌的运行约束里就明确写了。

11.1 三道门

① 鉴权 / 白名单（必须）

  • CC channels：access.json allowlist + per-channel opt-in pairing（/discord:access policy allowlist）[17]
  • cc-connect：admin_from 限定特权用户[4]
  • OpenClaw：acp.allowedAgents + permissions profile（strict/approve-all）[27]

② 权限模式（按风险定）

  • 逐条审批：cc-connect /mode default、OpenACP 破坏操作出 Approve/Deny 按钮[11]
  • 全自动：/mode yolo / --dangerously-skip-permissions（仅信任环境）[4]
  • CC permission relay（v2.1.81+）把审批弹窗转发 Discord 远程批准[9]

③ 进程 / 凭据隔离

  • cc-connect run_as_user 跑不同 Unix 用户做 OS 级隔离[4]
  • 每 thread 独立 git worktree / cwd[10]
  • OpenClaw 隔离 CODEX_HOME；Mac Studio 本机 vs RunPod 隔离自评估[26]

⚠️ 全天无人值守的取舍

permission relay（远程逐条批准）vs --dangerously-skip-permissions（全放开）——文档未给推荐默认，阿杰需按安全偏好定[9]。CC channels 在长时间 --dangerously-skip-permissions 下的越权边界无实测数据，放全天无人值守需自己评估沙箱（本机 vs 隔离容器）⚠️[22]。建议：先对所有动作设审批门，再随信心逐步放开——低风险任务 yolo、删 Roam/改生产/花钱类强制 review。

12落地路线：先通知 → 再单任务驱动 → 再统一 Bot▼

分阶段，每阶段独立可用、不依赖下一阶段。回报最快的先吃。

阶段 0：webhook 通知（今晚 · 30 分钟 · 零架构改动）

保持 Wave 里 runner 不动，启动命令 codex exec → codex exec --json ... | tee >(notify.py)。notify.py 逐行读 JSONL，遇 item.command_executed / item.plan_updated / turn.completed 就 POST 到一个 Discord webhook（频道设置 1 分钟建好）[2]。今晚就能"不盯电脑、Discord 看全天进度"——这是回报最快的一步，先吃下。

阶段 1：单任务驱动（这周 · 选一个 gateway 试水）

要"Discord 发指令→触发后台 runner→进度回推"。最快退路 = CC channels 当调度员（方案 B）：tmux 常驻一个 claude --channels plugin:discord --dangerously-skip-permissions，你发指令它 Bash 里 fire-and-forget 拉起 codex exec --json | notify.py，自己继续待命[9]。或最稳 = cc-connect（11k★、支持 Codex、无需公网，上手最快）[4]。第一天就锁 allowlist（第 11 章）。

阶段 2：统一 Bot（这周末评估 · 一劳永逸）

要"一个 Bot 管全部 agent（Codex+CC+Gemini 逍遥都进来）" = OpenClaw ACP（方案 C）。因为逍遥已经在 OpenClaw 上，把 Codex runner 也搬进同一个 gateway 一劳永逸[13]。关键提醒：所有 gateway 都倾向由 gateway 自己 spawn agent——要双向驱动，最干净是把"起 runner"交给 gateway spawn，而不是在 Wave 手起再 attach（后者没有现成工具支持）[12]。所以阶段 2 本质是"让 gateway 接管 Codex 启动"，Wave 退回偶尔手动调试用。先起 daemon 跑一个 Codex thread 实测嵌套自审是否稳[11]。

三阶段一句话

阶段 0（今晚）webhook 单向通知立刻见效 → 阶段 1（这周）CC channels 或 cc-connect 试单任务驱动 → 阶段 2（周末）OpenClaw 统一所有 agent。自审循环全程不动（Codex 调 CC 跨模型审查保留）[5]。

13坑与风险▼

❌ 坑 1：以为 wsh notify 能远程通知

Wave 的 wsh notify 只发本机桌面通知，到不了手机 Discord。远程通知必须靠 runner 命令层自己 curl webhook[3]。

❌ 坑 2：以为 webhook 能做入站驱动

webhook 纯出站，收不了消息。入站必须常驻 bot Gateway 长连——混淆这点会卡住整个"Bot 驱动"需求[9]。

❌ 坑 3：用 Composio Discord MCP 让 Codex 自己发消息

Composio Discord MCP 对 Codex 是只读（无 send message），发不出去，这条路别走[25]。

❌ 坑 4：想 attach 到 Wave 里已手动起跑的 runner 接管进度流

没有任何工具能做到——所有 gateway 都是 gateway 自己 spawn agent。坚持 Wave 手起只能走 webhook/hook 旁路通知；双向驱动必须让 gateway 接管 spawn ⚠️[12]。

⚠️ 坑 5：高频事件刷屏 + Discord 429 限流

实时推每个工具调用可能触发 Discord 限速（约 30 req/min + 2000 字符上限），需 batch/节流，只推 turn 级或筛事件类型[20]。具体阈值未实测 ⚠️[2]。

⚠️ 坑 6：CC channels 关终端消息永久丢失

channels 无离线队列，session 不开消息丢失（Discord 在 bot 离线期间会 queue 一部分、Telegram 直接丢），要 tmux/screen 常驻[9]。

⚠️ 坑 7：6-15 起 claude -p / Agent SDK 独立额度

2026-06-15 起订阅版 headless 走独立 Agent SDK 月度额度，全天跑成本要重算，配额数字未查到，按 Pro/Max 计划确认 ⚠️[15]。

⚠️ 坑 8：社区桥成熟度低 + 嵌套自审进度归属未知

discord-codex-bot(8★)/link-codex-to-discord(3★，自称 sanitized) 生产前务必审代码；codex-marketplace 插件仅 1 upvote 兼容性未验；Codex 调 CC 时子 agent 进度是否冒泡进 --json/hooks 无文档实测 ⚠️[23]。

14FAQ▼

Q最快能上的是哪个？今晚就想看到进度。+

webhook + codex exec --json。Wave 里 runner 不动，启动命令加 --json 管道给一个几十行脚本，挑 turn.completed 等事件 curl 到一个 Discord incoming webhook（频道设置 1 分钟建好，免写 bot）。零依赖、无需公网、5 分钟跑通[2]。

QCodex 有没有像 Claude Code channels 那样的原生 Discord？+

没有。截至 2026-05 Codex 无原生 channels，必须搭桥（exec --json 出站 / gateway 双向）。Anthropic 官方 channels 只能遥控 Claude Code 自己，驱动不了 Codex[7]。

Qwebhook 能不能让我在 Discord 发指令触发任务？+

不能。webhook 纯出站（只能往 Discord 发），收不了消息。入站驱动必须一个常驻 bot 用 Gateway 长连监听[9]。

Q一个 Bot 真能同时管 Codex + Claude Code + Gemini 吗？+

能，但开箱即用的只有 OpenClaw ACP / OpenACP / cc-connect 这几个。OpenClaw 是逍遥已在用的，把 Codex 也搬进去一劳永逸；OpenACP 带 REST API 可被外部脚本触发；cc-connect 最成熟最稳[13]。注意 OpenClaw 的 Discord 侧是"每 agent 一 bot account"[27]。

Q那个"Codex 调 CC 自审"还要改吗？+

不改。跨模型自审循环本身保持 Codex 调 CC（这正是阿杰全局 CLAUDE.md 那套 SOP，业界主流）。要改的只是上面的"编排/Discord 驱动"层——那层别让 Codex 当 orchestrator，交给 CC channels 或 OpenClaw[5]。

Q为什么不让 Codex 自己当总控调度所有任务？+

Codex 没内建队列/并发/状态，它的 scheduled 走桌面 App 的 Review inbox（攒着事后看），不适合 Discord 实时驱动。Codex 的强项是单次 exec 一锤子任务 + 干净 worktree 隔离[6]。

Q海外环境要不要梯子 / 公网 IP？+

都不要。webhook / Gateway 长连在海外环境都直连，cc-connect 和 OpenClaw 的 Gateway 连接无需公网 IP，特别适合 Mac Studio 全天跑（不用端口转发/反代）[10]。

Q怎么防止别人在 Discord 驱动我机器跑命令？+

三道门：① 白名单/allowlist（CC channels access.json / cc-connect admin_from）；② 权限模式（危险操作逐条审批，低风险才 yolo）；③ 进程/凭据隔离（run_as_user / worktree / 隔离 CODEX_HOME）。且 access.json/pairing 只能你在终端亲手批，频道里有人喊"approve me"必须拒绝（注入）[8]。

QCC channels 能不能直接当那个"统一 Bot"？+

不太行。channels 是"一个常驻 session 一个上下文"，不是任务调度器；session 一断消息丢、无离线队列。适合"我跟一个 always-on 助手聊天派活"，不适合"派 N 个互不干扰的后台任务"。可以让它当调度员 fire-and-forget 拉 runner（方案 B），但重活要甩后台[9]。

Q实时进度推每一步会不会刷屏？+

会，所以要筛事件 + 节流。建议只推 turn.completed / turn.failed，或在 notifier 里 batch；Discord 约 30 req/min + 单条 2000 字符上限，高频推 PostToolUse 会触发 429[20]。

Q有没有跟我愿景几乎一样的现成开源项目？+

有。ebibibi/claude-code-discord-bridge：自建 bot 调 claude -p stream-json，每 thread 一独立子进程，REST /api/spawn 起任务 + /api/tasks 定时，emoji+embed 实时回推，v3 已内建 /backend claude|codex 运行时切后端——直接覆盖"Bot 驱动 + Codex"两点，可 fork[10]。

QWave 以后还用得上吗？+

用得上但角色变了。出站方案里 Wave 是"跑 runner 的壳 + 本机桌面提醒兜底"；入站统一后 runner 由 gateway spawn，Wave 退回"偶尔手动调试"。整套 Discord 对接跟 Wave 解耦，换掉 Wave 方案照样成立[3]。
