搭建个人知识库系统：RSS · 文章/视频/播客三库 · 微信转发入库 · 一步步落地

📅 2026-06-21 🔍 ~60 次检索 + 5 个搜证包交叉核查 🧩 文章 × 视频 × 播客 × 微信 🌏 立场：人在马来西亚、订大量中文公众号的个人开发者

一句话定调：三个库（文章/视频/播客）别盲目自建——先用一个成品「一锅端」工具（Readwise Reader / Cubox / Raindrop）把需求跑通验证，再决定哪个库值得自建。真正难的不是技术，是微信公众号这堵墙：个人微信号没有 API、腾讯 2026-01 一次 DMCA 删了约 4195 个相关仓库[9]、2026-04 新规明文禁止用 AI/脚本/接口替代真人发布[10]。唯一可行的"转发就入库"入口是 Cubox 微信转发助手或自建 Playwright 中间层，agent 框架只能当 glue，穿不透墙。

本报告是操作手册，按"照着就能搭"的顺序展开：先破"搭 RSS 要不要 API"这个误解（Ch1）→ 总决策：三库分建 vs 成品一锅端（Ch2）→ 成品路线五款横评（Ch3）→ 自建 RSS 底座（Ch4）→ 文章库（Ch5）→ 重点章·微信入库（Ch6）→ 视频库（Ch7）→ 播客库（Ch8）→ 拼成一个系统：schema/去重/存储/编排（Ch9）→ Hermes/OpenClaw 的真实角色（Ch10）→ 给阿杰的路线建议三档方案（Ch11）→ 把这份研究变成你的 NotebookLM 研究库（Ch12）。每个库都给具体工具 + 具体步骤 + 三档方案。所有价格标访问日期 2026-06-21，标 🟢多源 / 🟡单源待核实 / 🔴高风险或估算。

01先破一个误解：搭 RSS 系统到底要不要 API？▾

很多人第一反应是"做 RSS 聚合是不是得申请一堆 API key、是不是要付费"。先把这个误解拆掉，否则后面整张地图都看歪。

核心事实：RSS/Atom 是开放协议（Atom 是 RFC 4287 标准[1]），订阅任何公开 feed 都不需要 API key、不需要付费、不需要授权。你只要拿到一个 https://xxx.com/feed.xml 这样的地址，任何阅读器都能直接拉。绝大多数博客、新闻站、播客、YouTube 频道本来就自带 feed。所以"搭 RSS 系统"的底座是免费的。

真正需要工具/可能花钱的，只有下面三种情况——把它们分清楚，你就知道每一分钱花在哪：

什么时候才需要额外工具解决的问题用什么要花钱吗
① 某个站没有 RSS（要"造 feed"）微博/X/B 站/知乎/微信这类站不提供 feed，或藏起来了RSSHub / RSS-Bridge / FreshRSS 的 XPath 抓取[6]自建免费
② feed 只给摘要（要"全文抓取"）很多 feed 只放前两段，正文要点进原文Miniflux 自带 fetch-original / FreshRSS Readable 插件 / FiveFilters[7]多数免费，托管版收费
③ 要在多端聚合管理（要"聚合器"）统一收所有 feed、标已读、跨端同步、给脚本调Miniflux / FreshRSS（自建）或 Inoreader / Feedbin（SaaS）自建免费，SaaS 收费

所以"API"这个词在 RSS 世界里有两层意思，别混：（A）拉 feed——不需要任何 API。（B）让你自己的脚本/agent 反过来读写聚合器里的内容（比如 n8n 定时把新文章拽出来入库）——这才需要聚合器提供 API。而是否提供 API、是否收费，是各家聚合器的差异点（Ch4 详表）。记住这条，你就不会被"Feedly API 要 $2400/月"这种企业定价吓到——那是给 B 端做舆情的，跟个人搭库无关[4]。

一句话收尾：RSS 底座本身免费且开放；你花的钱/精力只在"造 feed、抓全文、聚合管理"三件事上，且每件都有免费自建方案。下面所有章节都是在这个认知上展开。

02大决策：三库分开自建 vs 一个成品一锅端▾

在动手搭任何东西之前，先做这个总决策。它决定你是花一个下午开个账号，还是花两周搭一套 stack。

Q1 · 你现在是「想验证需求」还是「已经确定要长期自有数据」？
想先验证 / 还没想清楚✅ 走成品一锅端（Ch3）——Readwise Reader 或 Cubox，一个账号收齐三类内容，跑一个月看你真正在用哪个库
确定要数据自有 / 不想被 SaaS 锁死⚠️ 走自建，但分库优先级：先搭最痛的那一个，别一次全上（Ch4-8）
Q2（走自建）· 你最痛的库是哪个？
文章 / 公众号最多→ 先搭 RSS 底座（FreshRSS）+ 微信入库（Ch6），视频播客先用成品顶着
视频最多（学技术/看 YouTube）→ 先搭 yt-dlp + 频道原生 RSS（Ch7），文章用稍后读 app 顶着
播客最多（通勤听）→ 先搭 Audiobookshelf（Ch8），这是三库里最成熟的自托管
Q3 · 微信公众号是不是你的核心来源？
是🔴 先认清：这堵墙没有干净解（Ch6）。先用 Cubox 转发助手顶住，别指望全自动
否（主要看英文/技术内容）✅ 那你的系统会简单很多，标准 RSS + yt-dlp 就覆盖 90%

⚠️ 为什么默认推成品先行，而不是"工程师就该自建"

三个库各有各的维护负担：YouTube 2025 起要 PO Token（不装插件请求被降级，Ch7）[24]、微信反爬随时变、播客转写要 GPU、全文搜索引擎要单独跑 Docker。自建一整套不是搭完就完事，是每个环节都会偶尔坏、都要你修。而一个成品账号（Readwise $120/年）当天就能用、坏了有人修。判断标准很简单：你是想"拥有一套知识库系统"（那就花钱买时间用成品），还是"享受搭系统的过程 + 数据必须自有"（那才自建）。对阿杰这种单人全栈、时间是最稀缺资源的人，先成品验证再选点自建，几乎总是对的。

💡 第三条路最被低估：成品 + 局部自建的混合

不是非黑即白。最常见的成熟形态是：文章/微信用成品（Cubox 转发助手解决微信墙），视频用自建（yt-dlp 下原文件归档，这是成品做不到的"真正拥有文件"），播客用 Audiobookshelf 自托管。每个库用它最擅长的方案，再通过 export 到 Obsidian 汇到一处。Ch9 给这套混合架构的拼装图。本报告后面三档方案里，"半自建档"就是这条路。

选哪个？按你的最大需求一句话定

✅ 要"一个工具吃下全部三类内容 + 像 NotebookLM 一样跨库问 AI" → Readwise Reader

它是三类覆盖最全的：文章、YouTube（时间轴同步字幕、能划线）、播客（Spotify/Apple/RSS 触发转写）一网打尽，全文搜索含转写内容；Ghostreader AI 能跨整个库对话并给出来源链接[20]——这就是你想要的"问已有材料"能力（接 Ch12 NotebookLM）。还能把所有内容（含播客转写全文）导出到 Obsidian，等于成品当采集前端、Obsidian 当永久仓库。代价：$120/年最贵，播客只是"伴读"（有转写无音频播放器），视频仅限 YouTube。🟢

✅ 订大量中文公众号 + 想省事解决微信入库 → Cubox（Pro+AI $69/年）

Cubox 是这张表里唯一对微信有特化方案的：它有"微信转发助手"，绑定后在微信里把文章转发给一个企业微信号就自动入库（Ch6 详述）[11]。华人团队做的国际化产品，中文内容解析最顺。也有跨库 AI 问答（Library Insight）。代价：不支持播客、视频只存书签不转写、海外可用性 🟡 官方未明确背书（实测可用但你要自己确认）。🟡

✅ 数据要自有 + 开源可自托管 + 预算敏感 → Karakeep（自托管免费）

MIT 开源、22800+ stars，自托管永久免费；文章 + YouTube（yt-dlp 自动下载归档）+ 图片 OCR，全文搜索由 Meilisearch 驱动，AI 自动打标支持本地 Ollama（不把内容发给云）[36]。是"成品体验 + 开源自托管"的最佳折中。代价：不支持播客、没有跨库 AI 对话、公众号正文同样卡 JS 渲染（要配 Playwright，Ch6）。🟢

⚠️ Raindrop 和 Matter 的坑：先确认两件事再掏钱

Raindrop：书签管理是它强项，2026 年 Stella AI 加了跨库自然语言问答[21]，但不支持播客，且 Pro 年费有 $28 和 $38 两种说法，买前去 raindrop.io/pro/buy 核实当前价。Matter：三类全支持且播客转写做得好，但没有 Android 版（仅 iOS/Web）——阿杰如果用安卓这条直接出局；年费也有 $60/$80 两说待核实。这两个 🟡 标记的价格差异来自搜证时多源不一致，掏钱前自己看官网当前页。

顺带提两个老牌但功能窄的：Instapaper（只文章、Premium $59.99/年已提价、无跨库 AI）、Wallabag（开源自托管、只文章、无 AI、视频播客自 2016 issue #2149 至今未实现[35]）。它们活着但只解决"文章稍后读"单点，不适合做"三库一锅端"。

04自建路线 · RSS 采集底座（Miniflux / FreshRSS / RSSHub）▾

✅ 给阿杰的明确选择：FreshRSS

因为你订大量中文公众号、需要给"无 feed 的站造 feed"，FreshRSS 的原生 XPath scraping 是省事关键——很多中文站没有 feed，你用浏览器看一眼 HTML 结构，填几个 XPath 表达式就能把它变成 feed，不必为此单独跑 RSSHub[3]。它还自带 Readable 插件补全摘要 feed，Google Reader API 让 n8n / 手机 App 都能接。AGPL 完全免费，扛得住 50k+ 订阅。Miniflux 更极简稳定，但造 feed 要外挂 RSSHub，对你的中文场景多一道工序。🟢

造 feed 工具：RSSHub（给无 feed 的站造 feed）

RSSHub 是这套里最强的"万能 feed 工厂"——MIT 开源、1000+ 路由覆盖 YouTube/X/Bilibili/Weibo/Zhihu/TikTok/微信[6]。Docker 一行起：

1本地 Docker 一行起 RSSHub
docker run -d --name rsshub -p 1200:1200 diygod/rsshub —— 然后 http://localhost:1200/youtube/channel/UCxxx 这样的地址就是一个可订阅 feed[6]。
2千万别长期用公共实例 rsshub.app
公共实例被限流（120min 缓存 + IP quota 不稳），验证可以用，长期一定自建绕开。🟢
3把生成的 feed 喂进 FreshRSS
在 FreshRSS 里"添加订阅"，粘贴 RSSHub 的本地地址即可。部分路由支持 ?fulltext 参数直接出全文。

同类的 RSS-Bridge（公共域、主打欧美站 Reddit/YouTube/Bluesky、最新 2025-08-05[8]）也是一样思路，欧美站覆盖更好，同样建议自建避开公共实例限速。

全文抓取：摘要 feed 怎么补全

很多 feed 只给前两段。补全方式从省事到折腾：① Miniflux 自带 fetch-original（开关一开）② FreshRSS Readable 插件（Readability + Mercury 双引擎）③ FiveFilters Full-Text RSS（AGPL，自建或 $10/月托管，旧版 GitHub 免费[7]）④ Mercury Parser（原 Postlight 已归档，社区 mercury-parser-api 有 Docker 镜像）。给阿杰：直接用 FreshRSS Readable 插件，免费、免外挂。

SaaS 兜底：不想自建的话

如果连聚合器都不想自建，Inoreader（Pro $90/年含 API、2500 feeds、海外可达[4]）和 Feedbin（$70/年无免费层、newsletter→RSS 专属邮箱地址强[42]）是两个靠谱 SaaS。Feedly 个人版不要碰：API 只在 Enterprise Advanced（$2400/月起）才有，对个人不可行[4]。NewsBlur（MIT 可 Docker 自建、$36/年 Premium、有 API[41]）介于自建和 SaaS 之间，也是选项。

05文章库怎么搭（造 feed + 全文抓取的具体步骤）▾

文章库分两种来源：① 有 feed 的站（博客、新闻、Substack）——直接订阅，零成本；② 没 feed 的站——要造 feed。下面给完整操作流。

情况 A：站点有 feed（最简单）

1找 feed 地址
多数站在 /feed、/rss、/atom.xml、/feed.xml。找不到就把站点首页地址直接粘进 FreshRSS，它会自动探测 <link rel="alternate">。Substack 一律是 站名.substack.com/feed。
2订阅 + 分组打标
在 FreshRSS 里加订阅，按主题建 category（技术/英语/半米）。这一步决定后面入库时的 source_name 字段。
3开 Readable 插件补全摘要
遇到只给摘要的 feed，对该订阅勾选"获取全文"，FreshRSS 用 Readability 把原文正文抓回来。

情况 B：站点没有 feed（造 feed）

三种造法，按省事程度排：

最省事
FreshRSS XPath scraping：直接在 FreshRSS 里填规则，不用另起服务。看一眼目标页 HTML，填"文章列表选择器 / 标题 / 链接 / 正文"的 XPath，FreshRSS 就把它当 feed[3]
最全
RSSHub 路由：去 docs.rsshub.app 查目标站有没有现成路由（X/微博/知乎/B 站/TikTok 都有），有就直接用本地实例地址订阅[6]
欧美站
RSS-Bridge：Reddit、Bluesky、欧美小站覆盖更好，自建实例同理[8]

组合拳：FreshRSS（聚合 + XPath 造 feed + Readable 全文）一个工具基本就把"文章库"全包了。只有当某个站 XPath 太难写、或 RSSHub 已有现成路由时，才补一个 RSSHub Docker。这就是文章库的最小配置——一台小 VPS 上跑 FreshRSS + RSSHub 两个 Docker，月成本几美元。

剪藏：临时遇到的好文章怎么入库

RSS 是"订阅式"被动收，但你刷网页时随手遇到的文章需要"剪藏式"主动存。这块用 Wallabag（自托管、浏览器插件一键存 + iOS/Android app + REST API /api/entries 可被 n8n 轮询[33]）或直接用成品稍后读 app（Cubox/Readwise）。剪藏库和 RSS 库最后在 Ch9 归一化到同一个 schema。

⚠️ 坑：Wallabag 的抓取器是服务端 HTTP 请求，不带浏览器内核，所以它抓不了任何需要 JS 渲染的页面——微信公众号文章就是典型（Ch6）。剪藏普通网页没问题，剪藏 mp.weixin.qq.com 会失败。这是判断"某工具能不能吃微信"的通用试金石：抓取器是不是无头浏览器。

06【重点章】微信文章入库：最硬的墙 + 唯一可行的"转发就入库"入口▾

这是整份报告最重要、也最容易被网上教程骗的一章。阿杰订大量中文公众号，如果微信入库解决不了，整个知识库就缺了最大的一块。下面先把墙说透，再给唯一能落地的路径，每条都标封号风险。

① 墙有多硬：个人微信号根本没有官方 API，且反自动化信号在走强

微信对个人号的封闭是设计如此，不是技术难题。2017 年微信就封掉了网页版微信的自动化入口；个人号至今没有任何官方 API。2026 年的几个信号显示腾讯对自动化/逆向的打击在升级：腾讯 2026-01-08 对一个含约 4195 个仓库的 GitHub network 发起 DMCA[9]（核心是微信聊天记录导出/解密类工具——这条要诚实读：它不是直接删了所有公众号 RSS 工具，而是反映腾讯对"绕过保护、逆向数据"类项目的维权在加码，🟡 别外推成"公众号入库工具被团灭"）；微信公众平台的使用规范/ToS 长期禁止自动化抓取、逆向、爬虫（坊间有 2026-04 进一步禁止"AI/脚本替代真人发布"的说法，但官方条文未检索到，🟡 待核实，不作为硬论据）[10]。itchat/wechaty 这类 hook 框架仍然违反 ToS、有实打实的封号风险。🔴

② 技术障碍：mp.weixin.qq.com 文章是 JS 渲染 + 图片防盗链

就算你不碰个人号、只想抓单篇文章链接，也撞墙：公众号文章正文是 JS 渲染的，直接 HTTP GET 只返回标题，拿不到正文[14]。这就是为什么所有"服务端 HTTP 抓取"的工具（Wallabag、普通 RSS 全文抓取）对微信失效。而且文章里的图片有防盗链，referer 必须是 mp.weixin.qq.com，外部阅读器里图片会全部裂掉。唯一解法是用无头浏览器（Playwright/Puppeteer）真的"打开"页面，等 JS 渲染完再抓 HTML，并处理 lazy-load 图片。🟢

③ 自部署 RSS 方案大量阵亡：WeWeRSS 已 archived 停维护

很多 2024 教程推 WeWeRSS（cooderl/wewe-rss，基于微信读书账号生成 RSS，6500+ stars），但它 2026-05-11 已 archived 停止维护，README 自己警告"添加频率过高易被封控"[12]。它的继任 we-mp-rss（rachelos）还活着（v1.5.2，2026-04-16，3.6k stars），但同样是非官方接口 + 反爬对抗，自带"环境异常统计"，有封号风险[13]。这条路能用，但你赌的是一个可能随时被封的微信读书/公众号账号。🔴

那到底怎么办？四条可落地路径（按省事排序）

✅ 路径 A · Cubox 微信转发助手（最完整、最省事，推荐起步）

这是唯一不碰任何灰色技术、官方支持的"转发就入库"路径。操作：在 Cubox 设置里绑定微信 ID + 扫码加"Cubox 收藏助手"（一个企业微信号）→ 在微信里打开任意公众号文章 → 点分享 → 转发给这个助手 → Cubox 自动入库（正文解析 + 网页快照）[11]。因为是你本人手动转发，没有自动化、不违 ToS、不会封号。代价：① 2022-12-14 起这个功能需要 Cubox Pro 会员（$39+/年）② 是手动操作，量大时累 ③ 海外可用性 🟡 官方未明确背书（华人产品，实测可用但你要自己确认 Cubox 助手在马来西亚网络下能正常收转发）。Cubox 还有 API（POST {API_URL} 带 {"type":"url","content":"..."}，只接 URL，Premium 500 次/天[11]），可以接 iOS 快捷指令在分享 sheet 里触发。🟡

✅ 路径 B · Readwise Reader + 自建 Playwright 中间层（最可控、最灵活）

如果你要数据进自己掌控的 Readwise 库、且能接受搭个中间层，这是最强方案。原理：Readwise 的 save API（POST readwise.io/api/v3/save/）支持直传 html 参数——你可以把抓好的完整 HTML 直接塞给它，绕开它自己抓不了 JS 页面的问题[15]。关键参数：url（可自定义）+ html（直传内容）+ title/author/tags + should_clean_html，限速 50 次/分。2025-10 有现成实现案例：复制公众号链接 → 经 WeChat Work / 中间层 webhook → Playwright/Puppeteer 无头浏览器抓完整 HTML + 处理 lazy 图片 → POST html 参数入 Readwise[16]。代价：要自部署中间层 + 一台小服务器 + 一个企业微信号做触发入口（🟡 需要工程搭建，但比赌个人号封控干净）。🟢

⚠️ 路径 C · we-mp-rss 自部署（订阅固定公众号、接受封号风险）

如果你有一批固定要追的公众号、想要全自动 RSS 化、且能接受封号风险，we-mp-rss 是最活跃的自部署方案：QR 扫码授权 + web scraping 抓文章，支持 RSS/Webhook/Markdown/PDF 导出，输出标准 RSS 直接进 FreshRSS/n8n[13]。但它是非官方接口对抗反爬，README 自带封号警告。务必用一个小号（微信读书/公众号），降低添加频率，别绑你主微信。同类还有 wechat2rss（公共服务，免费列表 300+ 公众号、平均 6h 延迟、有图片视频代理；自部署收费年 ¥200[12b]），省去自己抓的麻烦但同样是第三方依赖。🔴

⚠️ 路径 D · RSSHub 微信路由（稳定性靠第三方，做不到全覆盖）

RSSHub 有几条微信路由，但都不是直接爬 mp.weixin.qq.com，而是绕第三方：/wechat/ce/:id（依赖第三方 CareerEngine careerengine.us）、/wechat/mp/msgalbum/:biz/:aid（公众号 tag 合集页，需要 biz=__biz 字段 + album_id，只有建了合集的号才有）、/newrank/wechat/:wxid（需 NEWRANK_COOKIE）[6]。__biz 从公众号分享链接 mp.weixin.qq.com/mp/homepage?__biz=XXX 里提取。这些路由稳定性都依赖第三方服务，🟡 时灵时不灵，只能当补充，做不到"任意公众号全自动"。

iOS 现实约束（必须知道，否则白搭）

⚠️ 微信内置浏览器不是 Safari，快捷指令在它的分享 sheet 里不出现。这意味着你无法在微信里"分享 → 跑个快捷指令 POST 到 API"。微信分享 sheet 里只出现有 share extension 的 app（Cubox 等）。实际可行的一键操作只有两种：① 微信"…"菜单 → 复制链接 → 切到目标 app 粘贴；② 用 iOS 自动化监测剪贴板出现 mp.weixin 链接 → 自动触发 POST。这就是为什么路径 A（Cubox 转发助手）体验最好——它走的是微信原生"转发给好友"，不依赖快捷指令。

💡 Agent 框架（Hermes/OpenClaw）在微信这块只能当 glue，穿不透墙

承接你之前那份《Hermes vs OpenClaw》研究：Hermes v0.9 确实有 WeChat adapter，HermesClaw 项目让两者共用微信账号轮询[34]。但这个 adapter 解决的是"agent 作为 bot 在微信里响应消息"，根本没解决"个人号没有 API"这个底层问题。agent 在这套里的真实角色只是调度 glue：收到一个链接 → 调 Playwright 抓 → 入库。接入层那堵墙，agent 解决不了，因为问题不在编排能力，在腾讯不给个人号开口子。别指望换个 agent 框架就能全自动吃微信。🟢（Ch10 展开 agent 的真实定位）

本章一句话结论 + 推荐优先级（阿杰、马来西亚、个人）：① 最省事 = Cubox 付费 Pro 微信转发助手（手动转发、零封号风险，先用这个跑起来）；② 最可控 = Readwise + 自建 Playwright 中间层（数据自有、工程量中等）；③ 订固定号 = we-mp-rss 自部署（用小号、接受封号风险）；④ Hermes/OpenClaw 只做收链接→调抓取→入库的 glue。不存在"零风险 + 全自动 + 任意公众号"的方案，这是腾讯设计的墙，不是你工具没选对。

07视频库怎么搭（yt-dlp + 频道原生 RSS + 增量 + PO Token）▾

视频库是三库里"自建反而比成品强"的一个——因为成品（Readwise/Matter）只存字幕和书签，yt-dlp 能下载真正的视频文件，让你"拥有"内容而不是依赖 YouTube 不下架。下面给完整入库流。

第一块：YouTube 每个频道都有原生 RSS（白嫖订阅）

关键事实：YouTube 每个公开频道都自带 Atom RSS，无需 API key。地址格式：youtube.com/feeds/videos.xml?channel_id=UC…[25]。把这个地址订进 FreshRSS，就能像追博客一样追频道更新。限制：每个 feed 只给最新 15 个视频。playlist 也有 feed（youtube.com/feeds/videos.xml?playlist_id=PL…），但稳定性和条数上限不如频道 feed，要追特定播放列表时可试、以实测为准 🟡。从频道 URL 提取 channel_id 的命令：yt-dlp --playlist-items 0 -O playlist:channel_url --print channel_url "$URL" | sed 's|channel/|feeds/videos.xml?channel_id=|'[29]。

第二块：yt-dlp 增量下载（频道同步核心）

视频库要"持续同步频道新视频、已下的不重复下"，核心是 --download-archive：下载后把 video ID 写进 archive 文件，下次自动跳过[26]。完整入库命令：

完整归档 flag（一条命令吃下视频+元数据+字幕+缩略图）：
yt-dlp --download-archive archive.txt --write-info-json --write-thumbnail --write-subs --write-auto-subs --sub-langs en --embed-metadata "https://youtube.com/@Channel/videos"
然后用 cron（mac 上是 launchd）定时跑这条命令，就是一个自动增量的频道库。[26]

⛔ 2025/2026 高频坑：遇到 403 / bot check / 格式缺失，先配 PO Token

2025 起 YouTube 在逐步推行 PO Token（Proof-of-Origin）。yt-dlp 默认仍会尝试不需要 token 的 client，但部分格式/功能可能缺失或触发 403、机器人校验——这是 2026 年很多"yt-dlp 突然下不动/报 Sign in to confirm"的常见根因。解法：装 bgutil-ytdlp-pot-provider 插件（pip 装，最新 1.3.1，2026-03-07），它后台自动生成 token 并注入[24]，并加 --cookies-from-browser firefox 带登录态。注意：PO Token 也不保证 100% 绕过 bot check（插件 README 自己也这么说），它降低被拦概率但不是万能钥匙。遇到下载报错时，先升级 yt-dlp 到最新版 + 配 PO Token，是最高命中率的两步。🟢

第三块：ytdl-sub 做"媒体库"级管理（可选进阶）

如果你下的视频多到要像 Netflix 一样组织，ytdl-sub 是 yt-dlp 上层封装：YAML 配订阅 → 按 TV Show 季/集结构组织 + 生成 NFO 元数据 + 封面，直接兼容 Jellyfin/Plex/Kodi/Emby（最新 2026.06.12，活跃[27]）。给阿杰：起步不用上 ytdl-sub，裸 yt-dlp + archive 已够；等视频库大到要影院级浏览体验再上。

第四块：转写入库（让视频可全文搜索）

视频要进"可搜索的知识库"，光有文件不够，要有文本。优先用 yt-dlp 已经下好的字幕（--write-subs）；没有官方字幕的，用 WhisperX 本地转写（Ch8 详述，large-v2 批处理 70x 实时[32]）。转写出的 SRT/VTT 文本就是你入库的 content_text 字段。

B 站怎么办：yt-dlp 能下 B 站（语法同 YouTube，高清/会员需 --cookies-from-browser），--download-archive 同样适用；批量下载用专门的 BBDown CLI 更顺。但 B 站没有原生频道 RSS，要追更新得靠 RSSHub 的 /bilibili/user/video/:uid 路由（Ch4）或轮询。B 站反爬随时变 🟡。

08播客库怎么搭（播客=RSS+enclosure + Audiobookshelf + 转写）▾

好消息：播客本质上就是 RSS，所以它是三库里最干净、最成熟的自托管对象。理解这个本质，整章就通了。

✅ 核心认知：播客 = RSS 2.0 + <enclosure> 音频直链

一个播客 feed 就是标准 RSS 2.0，每集用 <enclosure> 标签挂音频直链（url + length + type）[30]。带 <itunes:> namespace（封面/分类/show notes）。Podcasting 2.0 还定义了 <podcast:transcript> 标签——可以直接在 feed 里挂 VTT/SRT/JSON 转写文件[30]。这要和"平台内转写"分清：① 凡是 feed 里带 podcast:transcript 的播客，你能从开放 RSS 直接白嫖转写文本、连转录都省；② 但 Apple（2024 起）/Spotify（2025 起）在自家 App 里生成的自动转写，未必会暴露到开放 RSS 里，自建系统不一定拉得到。所以播客入库优先逻辑：先读 feed 里有没有 podcast:transcript，有就直接拉，没有才本地转写——别假设"大平台都转好了我直接拿"。🟡

自托管服务端：Audiobookshelf（最成熟）

Audiobookshelf 是最完整的自托管播客方案（Docker，5 万+ stars[31]）。操作流：

1Docker 起 Audiobookshelf
官方 docker-compose 一把起，Web UI 管理。
2输入播客 RSS URL → 选历史集数
把订阅设到 1990 年 + 无上限，就能把整个历史拉全（不只最新几集）[31]。
3自动追更 + 重导出 RSS 供手机听
它自动下载新集，还能重新导出一个 RSS，让你的手机播客 App（AntennaPod 等）连上来听，等于自建了一个播客中转站。show notes 从 <description> 拉。

⚠️ 诚实标注 ABS 两个不足：① Whisper 转写还没合并主线——是 2025 enhancement issue #2919，至今 still open，别以为开箱能转写[31]。② 全文搜索目前只按标题/播客名搜，搜不了转写正文内容。所以"播客可全文搜索"这个需求 ABS 自己满足不了，要靠下面的外部转写 + 写进你的主库。

客户端 App：手机上听用什么

纯听播客的客户端：AntennaPod（Android 开源 F-Droid，OPML 导入导出，gPodder 协议同步）、Podverse（iOS/Android/Web，支持 Podcasting 2.0 章节/转写）、gopodder（2025 中自托管同步服务器）[31b]。它们负责"听"，ABS 负责"归档 + 中转"。

转写入库：没有官方 transcript 时

✅ WhisperX 是播客/视频转写的最佳开源选择

large-v2 批处理达 70x 实时（1 分钟音频 <1 秒转完），输出 SRT/VTT/JSON 含词级时间戳，说话人识别需 HuggingFace token[32]。本地 M 系列芯片转一集 35-40 分钟节目约 15 分钟。配套 whisper-obsidian-plugin 能把转写直接落进 Markdown。不想自己跑 GPU 的话，OpenAI 转写 API（旧 whisper-1 名义价 $0.006/分钟；🟡 当前 dashboard 已转向新 audio/transcription 模型命名与价格，掏钱前核当前价[40]）——以旧价算一集 40 分钟节目约 $0.24，量小时仍比自建 GPU（≈$276/月）划算得多。🟢

播客库一句话搭法：Audiobookshelf 自托管做归档 + 重导出 RSS 给手机听；入库文本优先读 feed 里的 podcast:transcript，没有就 WhisperX 本地转（量小用 Whisper API）。转出的文本写进 Ch9 的主库，这才让播客"可全文搜索"。

09把它们拼成一个系统：schema + 去重 + 存储 + 编排▾

前面四个库（RSS 文章、微信、视频、播客）各自能采集，但它们是散的。这一章把它们拼成一个系统：统一 schema、去重、存储、编排。这是"知识库系统"和"一堆工具"的区别。

第一步：归一化 schema（所有来源进同一张表）

不管文章/微信/视频/播客，都映射到同一个 items 表。参考 Indaleko 论文的字段设计[38]：

字段含义作用
idSHA256(source_type + url)主键 + 第一道去重
url原文链接，UNIQUE去重键
title / author / published_at / saved_at基本元数据排序/展示
content_text全文（文章正文 / 视频播客转写）喂 FTS5 全文索引
summaryAI 摘要快速浏览
source_typerss_article｜wechat｜youtube｜podcast｜tweet｜book分类 + 跨库筛选
tagsJSON一库多标签（见融合）
media_url / raw_html_urlR2 上的媒体/原文件保存原件
checksumcontent 的 MD5第二道去重（内容变了才更新）

去重逻辑：先 WHERE url=?，命中再比 checksum——不同才更新，相同就跳过[38]。两道去重（url + 内容 MD5）保证同一篇文章从 RSS 和剪藏两条路进来也只存一份。

第二步：存储三件套（主库 + 媒体 + 笔记）

SQLite FTS5
主库。内置 BM25 排序、单用户无并发写冲突、备份=cp 一个文件、比 FTS3 快约 30%。是个人库最省力的起点[37]
Cloudflare R2
存媒体原件。S3 兼容、零 egress 费、AES-256、335 节点。视频/音频/原始 HTML 存这里，主库只存 URL 指针[39]
Obsidian MD
人读 + 双链。天然 git 版本控制 + 离线 + MCP 可读写。每条 item 写一个 MD 带 YAML frontmatter，用 [[wikilink]] 互联

⚠️ Meilisearch 什么时候才需要（别过早上）

很多教程一上来就推 Meilisearch，但个人库几十万条以内，SQLite FTS5 的全文搜索已经够用，不需要单独跑搜索引擎。Meilisearch（MIT、磁盘+内存映射不受 RAM 限、5 分钟跑起、中文自动分词[37b]）的价值在于typo 容错 + 即时搜索体验 + 超大量数据。判断线：内容超 ~5 万条、或你强需要拼错也能搜到，才单独起一个 Meilisearch Docker。Typesense（全量索引在内存 sub-50ms，但硬件成本随数据线性涨）只在数据能全放内存时才更快。给阿杰：起步坚决不上 Meilisearch。

⚠️ Obsidian 的搜索天花板：Obsidian 内置搜索在 2400+ 条笔记开始变慢（用户经验，无官方确认 🔴），Omnisearch 插件能补但需要 Obsidian 一直开着运行。所以别把 Obsidian 当搜索主库——搜索靠 SQLite FTS5，Obsidian 只做"人读 + 双链笔记"，两边通过 source_url 互查。这就是为什么架构里 SQLite 和 Obsidian 是双写而非二选一。

第三步：编排层（把采集→处理→入库串起来）

✅ 编排用 n8n（会写代码个人用户的最优 glue）

n8n 有 400+ 原生集成（含内置 RSS Feed Trigger 节点）+ 1100+ 总集成 + 可视化 + JS/Python 代码节点 + LangChain 原生，Docker 起、最低 4GB RAM[43]。标准管道模板（workflow #4503）：Schedule Trigger → RSS Feed Loop（时间过滤去重）→ AI 摘要 → 写存储 → 通知[43]。对比项：Huginn（Ruby/YAML 门槛高、2023 后开发放缓，不推荐新项目）、Node-RED（轻量适合 IoT，复杂 SaaS 管道不适合）。🟢

⚠️ n8n 的一个真实坑：没有内置 SQLite 节点。n8n 官方不提供直接写 SQLite 的节点，要么用 HTTP Request 对接 Datasette/LibSQL HTTP API，要么用 Execute Command 跑 Python 脚本写库——实战教程少，得自己摸 🔴。所以"n8n 直接写 SQLite"不是开箱即用，这是你搭管道时第一个会卡住的地方。变通：让 n8n 把归一化好的 JSON POST 给一个你自己写的小 Python/FastAPI 接口，由它落 SQLite。

推荐管道全图（会写代码个人）

采集层：FreshRSS / n8n RSS Trigger（文章）+ we-mp-rss 或 Cubox 转发（微信）+ yt-dlp + Whisper（视频）+ podcast:transcript / WhisperX（播客）+ Wallabag（剪藏）
编排层（n8n）：触发 → 抓全文 Readability → 归一化成 schema → URL hash 去重查 SQLite → 写 SQLite → 媒体上传 R2 → （可选 Meilisearch 索引）→ 写 Obsidian MD → Discord 通知
存储层：SQLite FTS5 主库 + R2 媒体 + Obsidian MD + Meilisearch（>5 万条才上）

💡 最小可行版（一周跑通，别一次全上）

FreshRSS + n8n + SQLite FTS5 + Obsidian，不上 Meilisearch/R2。工作量估算：n8n 管道 + schema 设计 2-4 天 / we-mp-rss 部署 2 小时 / Wallabag 1 小时 / Meilisearch 半天（可延后）[44]。先把"文章从 RSS 进 SQLite 并能全文搜 + 写一份 Obsidian MD"这条主干跑通，微信用 Cubox 顶着、视频播客先用成品顶着，验证完再逐块自建替换。⚠️ 工作量为基于证据包的估算。

10Hermes/OpenClaw 在这套系统里的真实角色▾

承接你之前的《Hermes vs OpenClaw》和《n8n vs LangGraph》两份研究——这里只回答一个问题：这套知识库系统里，agent 框架到底干什么、不干什么。说清楚省得你高估它。

💡 Agent 只做 glue 调度，不做核心采集/存储/搜索

知识库系统的核心是三块：① 采集（yt-dlp/Playwright/RSS）② 存储（SQLite/R2）③ 搜索（FTS5）。这三块都是确定性的工程组件，不需要 agent 的"智能"——一个 cron + 脚本就干完了，引入 agent 反而增加不确定性和成本。agent 真正有价值的位置只在两处：（A）需要判断的 glue——比如"这条内容该打什么标签、该归到哪个库、要不要摘要"；（B）对话式检索——你问"我之前存的关于 X 的内容里有什么观点"，这是 Ch12 NotebookLM 那一层。🟢

⛔ 重申：微信墙在接入层，换任何 agent 框架都解决不了

这是最容易被"agent 万能"幻觉骗的地方。Hermes 有 WeChat adapter、HermesClaw 能共用微信账号[34]，听起来像"agent 能搞定微信"。但 adapter 解决的是"让 agent 作为聊天机器人在微信里收发消息"，它依然跑在个人号上、依然没有官方 API、依然受 2026-04 自动化禁令约束。你的 agent 编排能力再强，也变不出一个腾讯不给的 API。所以 agent 在微信入库这块的角色，和 Ch6 说的一样：收链接 → 调 Playwright 抓 → 入库的 glue，墙它穿不透。🔴

结论：这套系统的"骨架"用 n8n + 脚本 + cron 搭（确定性、稳、便宜），agent（Claude Code / Hermes）只在"需要判断的打标摘要"和"对话式检索"两处出现。别把采集和存储交给 agent——那是用昂贵且不稳的东西干确定性脏活。这也呼应你《n8n vs LangGraph》的结论：n8n 在 glue 层，逻辑/判断才上 LLM。

11阿杰路线建议（决策树 + 三档方案 + 与现有库融合）▾

把前面所有东西收口成一张决策树 + 三档可执行方案。先回答"先搭哪个库跑通"，再回答"和你现有的推文库/书库怎么融合"。

Q1 · 你现在的首要目标是什么？
先验证"我到底要不要一个知识库系统"→ 极简成品档（Readwise Reader 一个账号，一个月）
想要数据自有，但时间有限→ 半自建档（成品解决微信 + 自建视频/播客 + Obsidian 汇总）
享受搭系统 + 数据必须全自有→ 完整自建档（FreshRSS+n8n+SQLite FTS5+R2）
Q2 · 先搭哪个库跑通（无论哪档都先搭这个）？
文章库✅ 它最简单、来源最多、立刻有正反馈。RSS 底座 1 天搭完，先尝到"统一收文章并能搜"的甜头
别先碰微信/视频⛔ 微信是最难的（Ch6 墙），视频要踩 PO Token 坑（Ch7）——先搭它们容易卡住放弃

三档可执行方案

✅ A 档 · 极简成品档（当天可用，$120/年，零运维）

怎么搭：开一个 Readwise Reader 账号。文章/YouTube/播客全丢进去；微信用 Cubox Pro 转发助手顶着（或 Readwise + 手动复制链接）；用 Ghostreader 做跨库问答。每周自动导出到 Obsidian 当永久仓库。适合：还没想清需求、时间最稀缺、要立刻能用。代价：数据在 SaaS 手里、微信体验一般、$120/年。这是默认推荐起点——先用一个月，搞清你真正在用哪个库、缺什么，再决定要不要往下走。🟢

✅ B 档 · 半自建档（每库用最优解，混合，推荐落点）

怎么搭：文章 = FreshRSS 自建（XPath 造 feed + Readable 全文）；微信 = Cubox 转发助手（不碰灰色技术）；视频 = yt-dlp + 频道原生 RSS + 增量归档（这是成品做不到的"真拥有文件"）；播客 = Audiobookshelf 自托管；最后全部 export 汇到 Obsidian，搜索用 SQLite FTS5。适合：要数据自有但时间有限、不想为每块都造轮子。这是大多数工程师的最终落点——每个库用它最擅长的方案，微信这块认怂用成品，视频这块吃自建红利。🟢

⚠️ C 档 · 完整自建档（全自有，2-4 天起步 + 长期维护）

怎么搭：FreshRSS + RSSHub（采集）+ we-mp-rss 小号（微信，接受封号险）+ yt-dlp + WhisperX（视频）+ Audiobookshelf + podcast:transcript（播客）→ n8n 编排归一化去重 → SQLite FTS5 主库 + R2 媒体 + Obsidian 双写 → Discord 通知。适合：数据必须 100% 自有、享受搭系统、能承担长期维护（PO Token 更新、微信封控、各组件偶发故障）。代价：这不是搭完就完事，是每个环节都会偶尔坏要你修。除非你真的享受这个过程，否则 B 档性价比高得多。🟡

和现有"推文库 / 书库"怎么融合：一库多标签 > 多库

原则：一库多标签优于多库。Obsidian flat vault + tag 比多 vault 更易跨类型检索[45]。具体到阿杰：你现有的推文库/书库在 Roam 里不要动（迁移成本高、风险大）；新增的"文章/视频/播客"走 SQLite + Obsidian MD 双写（SQLite 做搜索去重主库，Obsidian 写 [[wikilink]] 反链）；两套系统通过 source_url 互查、不强制迁移。等于在不动现有 Roam 体系的前提下，新长出一个搜索友好的采集库，需要时用 URL 在两边跳转。🟡

⚠️ 两个容易被收集冲动盖过的现实：分发权 + 反堆积

① "数据自有" ≠ "想怎么用都行"。yt-dlp 下的视频文件、Playwright 抓的公众号 HTML、Whisper 转的文本，你拥有的是本地副本，不等于拥有再分发权——原文/视频/音频的版权仍归原作者。自建库做"个人备份 + 个人检索"落在容忍区间；一旦公开重新发布（搭个网站给别人看、做成产品内容），就是另一回事。本报告讲的是"个人知识库"，请守住这条边界。② 知识库最大的失败模式不是搭不起来，是 hoarding（只存不看）。建议从第一天就加保留纪律：未读上限、每周清理、AI 摘要先过一遍只留值得读的，否则三个月后你会有一个 5000 条没人看的坟场。🟡

💡 最小可行版（一周跑通，给你最快的正反馈）

FreshRSS + n8n + SQLite FTS5 + Obsidian，不上 Meilisearch/R2，微信用 Cubox 顶着、视频播客先用 Readwise 顶着。先把"文章从 RSS 自动进 SQLite + 能全文搜 + 落一份 Obsidian MD"这条主干跑通（2-4 天[44]）。跑通后你会立刻知道这套系统对你有没有用——有用再逐块自建替换微信/视频/播客，没用就退回 A 档成品。这是"先挑一个窄的跑通"的标准打法，别一上来就铺完整 stack。

12把这份研究变成你的 NotebookLM 研究库▾

接你的实际需求：这份报告本身的 References 就是一份已经筛好的高质量 source 清单。这一章讲怎么把它（和你其它研究）变成 NotebookLM 知识库，以及 NotebookLM 在整套系统里的定位。

✅ References = 现成的 NotebookLM source 清单

报告末尾的每个 reference 都是一个被你核过、值得保留的来源 URL。把它们按主题导入 NotebookLM，建议分三个 notebook：「自动化工具」（RSSHub/n8n/yt-dlp/Readwise/Cubox 文档）、「英语学习」（你的 SciShow/词汇相关研究）、「半米」（产品/竞品研究）。每份研究报告产出后，把它的 References 批量喂进对应 notebook，时间一长就是一个你亲手筛过、可对话检索的研究底库。

⚠️ 关键认知：NotebookLM 适合"问已有材料"，不适合"发现新东西"

别把 NotebookLM 当搜索引擎或研究 agent 用。它的强项是source-grounded——只在你喂进去的材料里回答、给引用、几乎不幻觉。所以它回答"我之前那份 RSS 研究里推荐的微信方案是什么"完美，但回答"2026 年有没有新的微信入库工具"无能为力（它不会去网上找新东西）。定位：NotebookLM = 你已有知识的对话接口；发现新信息还是靠 WebSearch + 做新研究。这和 Ch3 里 Readwise Ghostreader / Cubox Library Insight 的"跨库 AI 问答"是同一类能力——都是"问已有材料"，区别只是材料在哪个库里。🟢

串起来看：你的知识库系统（Ch9）负责采集和存全文，NotebookLM（或 Readwise Ghostreader）负责对话式检索。两者互补：采集系统是"仓库"，NotebookLM 是"会查仓库的助理"。最顺的工作流是——采集系统把内容存进 Obsidian/SQLite，挑重要的批量导入 NotebookLM 当"可对话的精华子集"，需要写东西时先问 NotebookLM 调研已有材料，缺新信息再开 WebSearch。

13FAQ · 常见问题▾

Q1最关键的：搭这套到底要不要先会写代码？＋

分档看。A 档极简成品档完全不用写代码——开个 Readwise 账号就行，适合先验证。B/C 档自建要写代码：n8n 虽是可视化，但归一化 schema、对接 SQLite（n8n 没有内置 SQLite 节点，要自己写小接口，Ch9）、Playwright 抓微信，都需要工程能力。对阿杰这种单人全栈，B 档（半自建）门槛刚好——视频/播客自建是标准 CLI 活，微信认怂用成品，不必啃最硬的骨头。

Q2我人在马来西亚，这些工具都能用吗？＋

绝大多数能。RSS 类（FreshRSS/RSSHub/Miniflux）自托管、海外完全可达；成品里 Readwise/Raindrop/Karakeep/Matter 都是海外服务、可达。唯一要你自己确认的是 Cubox——华人团队产品、海外可用性官方未明确背书（🟡），微信转发助手在马来西亚网络下能不能正常收转发，建议先免费试一周再决定付费。微信本身（we-mp-rss/wechat2rss）是连微信服务器，海外也能连，但稳定性看你的网络。

Q3我订了很多公众号，有没有"全自动、零封号、任意号"的方案？＋

没有。这是本报告反复强调的现实：个人微信号没有官方 API、腾讯 2026-01 对逆向/解密类仓库的 DMCA 打击在升级[9]、微信 ToS 长期禁自动化[10]。"零封号"和"全自动"二选一：要零封号就用 Cubox 手动转发（路径 A）；要自动就上 we-mp-rss 小号、接受封号风险（路径 C）。"任意公众号"更难——RSSHub 路由只覆盖部分。最现实的组合：常追的固定号用 we-mp-rss 小号自动化，偶尔遇到的好文章手动 Cubox 转发。

Q4为什么不直接全用 Readwise，还折腾自建？＋

Readwise 很强，但有三个它做不到的：① 真正拥有视频文件——它只存 YouTube 字幕，YouTube 一删你就没了，yt-dlp 下的文件永久属于你；② 数据自有——内容在 Readwise 服务器，停服或涨价你被动；③ 微信——Readwise 直接存 mp.weixin 链接会因 JS 渲染失败（Ch6），要自建 Playwright 中间层。所以"A 档全用 Readwise"适合验证期，等你确定某个库是刚需、且在意上面三点，再对那个库做自建。别一开始就全自建，也别永远只靠 Readwise。

Q5Pocket 我一直在用，现在怎么办？＋

赶紧迁移——Pocket 2025-07-08 已永久关闭，数据 2025-11-12 起永久删除[17]，再不导出就没了。迁移目标按需求选：要 AI 问答 + 多类内容 → Readwise Reader；要开源自托管 → Karakeep；只要简单稍后读 → Raindrop（免费层无限书签）。Pocket 支持导出 HTML/CSV，这几个工具都能导入。

Q6yt-dlp 突然下不动了/报错，是被封了吗？＋

大概率不是封号，常见两个原因：① yt-dlp 版本旧（YouTube 改协议时 yt-dlp 跟进很快，先 pip install -U yt-dlp）；② PO Token——2025 起 YouTube 逐步推行 PO Token，缺它部分格式会缺失或触发 403/bot check[24]。解法：装 bgutil-ytdlp-pot-provider 插件 + 加 --cookies-from-browser firefox（Ch7）。注意 PO Token 不保证绕过所有 bot check，但"升级 + 配 token"是命中率最高的两步。

Q7播客那么多集，转写成本会不会很高？＋

先别转——优先读 feed 里的 podcast:transcript 标签，带这个标签的播客把转写直接挂在开放 RSS 里，是免费白嫖的[30]（注意：Apple/Spotify 在自家 App 里的自动转写未必暴露到 RSS，别假设大平台都帮你转好了）。没有 feed 转写才自己转：本地 WhisperX 跑 M 系列芯片免费（一集约 15 分钟）；不想占机器就用 OpenAI 转写 API（旧 whisper-1 名义 $0.006/分钟，但当前 dashboard 已转向新 audio 模型命名/价格，掏钱前核当前价 🟡）[40]。自建 GPU（≈$276/月）只在你每天转几十集时才划算。

Q8一定要上 Meilisearch / Cloudflare R2 吗？＋

起步都不用。Meilisearch：内容超 ~5 万条、或强需要 typo 容错才上，否则 SQLite FTS5 全文搜已够（Ch9）[37]。R2：只在你要存大量视频/音频原文件时才需要（存媒体、零 egress 费）；如果视频文件就放本地硬盘、库里只存 YouTube 链接，连 R2 都省了。最小可行版（FreshRSS+n8n+SQLite+Obsidian）这俩都不上，一周跑通先验证。

Q9n8n 和我已有的脚本/cron 比，值得引入吗？＋

看你舒服度。n8n 的甜点是可视化 + 内置 RSS Trigger + 重试/告警/1100+ 集成，少写很多胶水代码[43]。但它有真实摩擦：没内置 SQLite 节点（要自己写接口，Ch9）、本地 ASR 容易撞 AI 节点超时。如果你已经习惯写 Python + cron，纯脚本管道也完全能搭这套系统、更可控。判词（呼应你的 n8n vs LangGraph 研究）：n8n 价值在 glue 层（连服务、定时、告警），逻辑判断该留给代码/LLM。RSS 采集 + 通知这类 glue 用 n8n 真甜；核心去重/写库逻辑写脚本更稳。

Q10我现在的推文库/书库在 Roam，要迁过来吗？＋

不要迁。迁移成本高、风险大，且没必要。原则是"一库多标签、新旧通过 URL 互查、不强制迁移"（Ch11）[45]：Roam 里的推文库/书库保持不动，新增的文章/视频/播客走 SQLite + Obsidian，两套系统用 source_url 在需要时跳转。等于新长一个搜索友好的采集库，不动你已经经营好的 Roam 体系。

Q11Hermes/OpenClaw 能帮我自动搞定整个采集吗？＋

能做调度 glue，不能做核心。采集（yt-dlp/Playwright/RSS）、存储（SQLite/R2）、搜索（FTS5）都是确定性组件，用 cron + 脚本干更稳更便宜，不需要 agent（Ch10）。agent 有价值的地方是"需要判断的打标摘要"和"对话式检索"。尤其微信：agent 框架的 WeChat adapter 解决的是"agent 当 bot 收发消息"，不解决"个人号没 API"——墙在接入层，换框架也穿不透[34]。

Q12这套搭好后，怎么和我的研究/写作工作流结合？＋

采集系统当"仓库"，NotebookLM/Readwise Ghostreader 当"会查仓库的助理"（Ch12）。流程：内容自动采进 Obsidian/SQLite → 挑重要的批量导入 NotebookLM（按自动化工具/英语/半米分库）→ 写东西时先问 NotebookLM 调研已有材料、给引用 → 缺新信息再开 WebSearch 做新研究。注意 NotebookLM 只回答"已喂进去的材料"、不发现新东西[46]，所以它是检索层不是研究层。
