短视频库一条龙：抖音·TikTok·视频号·小红书·Twitter 下载 → 压缩 → 字幕 → 上传 R2 → 私人库

📅 2026-06-21 🔍 ~50 次检索 + 工具版本核查 🛠️ 下载 × 压缩 × 字幕 × 存储 × 检索 🌏 立场：人在马来西亚的会写代码个人用户

一句话定调：这不是一个工具能搞定的事——五个平台的下载工具各不相同（TikTok 用 yt-dlp、抖音用 TikTokDownloader、小红书用 XHS-Downloader、Twitter 用 yt-dlp+gallery-dl，而视频号只能 MITM 抓包、违微信 ToS 有封号风险 🔴）。下载之后的链路反而是标准化的：H.265 压缩省一半体积、字幕靠平台自带 caption + 本地 ASR（Mac 上中文口播首选 SenseVoice 不是 Whisper）、存 Cloudflare R2 零 egress、最后用 SQLite FTS5 建一个可全文检索的私人元数据库。

本报告是「照着就能搭」的操作手册：Ch1 给一条龙总览与三档方案速览；Ch2 是重点——逐平台最优下载工具 + 反爬难度 + 风险分级；Ch3 讲文案与字幕提取（自带 caption 抓取 + 没字幕时的 ASR 选型）；Ch4 是短视频压缩（H.264/H.265/AV1 对比 + 可直接复制的 ffmpeg 三档命令 + Mac 硬件加速）；Ch5 是上传与 R2 存储（定价 + rclone + presigned URL + Worker 鉴权）；Ch6 把它们拼成 pipeline（Python 主 + n8n 触发 + 完整 SQLite schema + 去重）；Ch7 讲私人库的检索与前端；Ch8 单独成章如实讲法律与封号边界；Ch9 给阿杰决策树与「先做哪一步」。本报告与姊妹篇 RSS 知识库系统共用 R2 / SQLite / 编排骨架，那篇讲文本/RSS，这篇是短视频专项。所有版本号、star 数、价格标注访问日期 2026-06-21，关键数据标 🟢多源 / 🟡单源 / ⚠️估算，风险标 🟢/🟡/🔴。

⚡ 3 条最关键发现（先看这个）

  1. 下载工具按平台分化，视频号是唯一的死结。TikTok / Twitter 用 yt-dlp 就能干净下载（公开内容低风险 🟢）；抖音 yt-dlp 持续破损[2]，要换 TikTokDownloader（14.8k stars[3]）；小红书 2026-04 改域名后 yt-dlp 残废，要换 XHS-Downloader（11.6k stars[4]）；视频号没有公开 HTTP 流，任何下载工具都必须 MITM 抓包解密微信流量，明确违反微信 ToS 有封号风险[6] 🔴。🟢
  2. 压缩省一半、存储零 egress，是这套库能长期养下去的两根支柱。H.265 CRF28 相比 H.264 同观感省 ~50% 体积（⚠️推算）[17]，Mac 上 -tag:v hvc1 必须加否则 iPhone 不认；存到 Cloudflare R2 是 $0.015/GB/月 + egress 全免费无上限[22]——同样 500GB/月下行 R2 约 $1.35 而 S3 约 $47[23]，视频这种「存得多、偶尔看」的场景 R2 是结构性最优。🟢
  3. Mac 上做中文口播字幕，SenseVoice 比 Whisper 快近一个数量级且更准。M4 Pro 实测：SenseVoice Small 处理 27 分钟中文播客只要 13.83 秒（118× 实时）CER 10.78%，而 Whisper Large V3 Turbo 同段要 2 分 04 秒（13.1× 实时）CER 12.55%[14]。有平台自带字幕（TikTok/抖音）就 yt-dlp 直接抓 SRT 不用跑 ASR；没字幕（小红书/视频号/Twitter）再上 ASR，本地首选 SenseVoice。（注：此对比是单篇 M4 Pro 单语料实测，方向可信、具体数字别当死值。）🟡

01全流程总览 + 三档方案速览▾

整条流水线五个环节，每一环都可以独立替换。先看架构，再看你这周该搭哪一档。

┌─ 1. 下载（逐平台不同工具）─────────────────────────┐
│  TikTok → yt-dlp        抖音 → TikTokDownloader      │
│  小红书 → XHS-Downloader  Twitter → yt-dlp+gallery-dl │
│  视频号 → MITM 抓包工具 🔴（违 ToS）                  │
│  产出：原视频 .mp4 + info.json（元数据）+ .srt（若有）│
└──────────────┬─────────────────────────────────────┘
               ▼
┌─ 2. 压缩（可选，短视频常不需要）───────────────────┐
│  ffmpeg libx265 CRF28 + hvc1  → 省 ~50% 体积         │
│  Mac 批量：hevc_videotoolbox 硬件加速 ~15×          │
└──────────────┬─────────────────────────────────────┘
               ▼
┌─ 3. 文案 + 字幕──────────────────────────────────┐
│  有自带 caption → yt-dlp --write-subs 抓 SRT        │
│  无 caption → ASR：SenseVoice(Mac中文) / faster-    │
│  whisper / WhisperX(词级)。softsub 存库不烧录       │
└──────────────┬─────────────────────────────────────┘
               ▼
┌─ 4. 上传 Cloudflare R2（零 egress）────────────────┐
│  rclone copy /local r2:bucket  增量同步             │
│  私有访问：presigned URL / Worker 鉴权             │
└──────────────┬─────────────────────────────────────┘
               ▼
┌─ 5. 建库 + 检索─────────────────────────────────┐
│  SQLite videos 表 + FTS5 全文索引(标题/文案/字幕)   │
│  --download-archive 去重；Datasette 当前端原型     │
└──────────────────────────────────────────────────┘

不是每一档都要全跑。按你的目标选起点：

档位包含环节工具栈适合谁 / 多久搭好
A. 极简手动档下载 → 存本地文件夹yt-dlp / TikTokDownloader 命令行，手动归类只想存几个平台的视频备份，当天就能用。没有检索、没有压缩。
B. 半自动脚本档 ★下载 → SQLite 元数据 →（按需压缩/字幕）Python 包一层 yt-dlp + 写 SQLite + FTS5 全文搜索★ 推荐起步。能按文案/字幕全文搜了，本地跑，一两个周末。
C. 完整 pipeline 档全五环 + 自动触发 + R2 + 前端Python 核心 + n8n 触发/通知 + R2 + Datasette/半米后台要长期养库、多设备访问、跟半米对接。持续迭代，别一上来就这个。

本章先给路线结论，后面各章给工具与命令：绝大多数人应该从 B 档起步——先把"一个平台下载 → 存本地 → 建 SQLite 元数据"这条最短链路跑通，验证你真的会回来检索这些视频，再决定要不要加压缩、字幕、R2 这些「锦上添花但有维护成本」的环节。Ch9 的决策树会把这个顺序说死。

02分平台下载工具：逐平台最优解 ★▾

这是全报告最重要的一章。没有一个工具能通吃五平台——每个平台的反爬机制、协议、去水印方式都不同。先看速查表，再逐平台拆。

平台最优工具是否需登录/cookie去水印反爬难度风险分级
TikTokyt-dlp（原生）公开视频不需要[1]内置优先无水印源（不保证）低公开内容私存 🟢
抖音TikTokDownloader需 cookie（浏览器提取，QR 已失效）[3]抓 CDN 无水印源高（yt-dlp 持续破损）违 ToS 小量私存 🟡
小红书XHS-Downloader不需登录也能下（配 cookie 解锁高清）[4]平台原始文件无硬水印中（签名逆向）私存低频 🟡
视频号MITM 抓包工具 🔴需装本地根 CA 证书拦截微信流量[6]抓解密后的源极高（无公开 HTTP 流）违微信 ToS 封号 🔴
Twitter/Xyt-dlp + gallery-dl公开视频不需要，NSFW/图集需 cookie[8]原始媒体无水印低（API 变更偶发 AuthError）公开内容 🟢

① TikTok = yt-dlp（最干净，首选）

yt-dlp 原生支持 TikTok（内置 tiktok.py extractor），公开视频无需登录即可下载，并优先尝试无水印源（但官方不保证一定拿到无水印版）[1]。基本命令：

# 单个视频，连带元数据 + 字幕一起下
yt-dlp --write-info-json --write-subs --write-auto-subs \
  --sub-lang zh,en --convert-subs srt \
  -o "%(uploader)s/%(id)s.%(ext)s" \
  "https://www.tiktok.com/@user/video/123456"

# 整个账号的发布（断点续传靠 archive）
yt-dlp --download-archive archive.txt \
  -o "%(uploader)s/%(id)s.%(ext)s" \
  "https://www.tiktok.com/@username"

为什么 TikTok 最省心：它是 yt-dlp 一等公民，extractor 维护活跃，公开内容不碰登录态，所以既不触发账号风险，下载链路也最稳。海外用户直接 pip install yt-dlp 就能跑，无需代理。这也是为什么「先跑通一个平台」建议从 TikTok 开始——它是整条链路里阻力最小的那个。

② 抖音 = TikTokDownloader（yt-dlp 在这儿已破损）

抖音是同公司产品但生态隔离，yt-dlp 对抖音的支持在 2025–2026 持续破损（多个 issue 报 cookie 错误 #16803 / #13382）[2]。最完整的开源替代是 TikTokDownloader（JoeanAmier，现名 DouK-Downloader），14.8k stars，最新正式 release V5.7（2025-08-19）[3]（更新的 beta 见仓库 tag/branch，发版较慢 🟡）。它能批量下账号的发布/喜欢/收藏/合集，支持 CSV/XLSX/SQLite 导出，去水印靠抓 CDN 无水印源，提供 CLI + Web API + Docker 三种用法，海外可访问。

⚠️ 坑：抖音必须先喂 cookie。TikTokDownloader 需要从浏览器提取 cookie（抖音的 QR 扫码登录方式已失效）[3]。另外它对抖音支持最完整，对国际版 TikTok 反而支持较少——所以是「抖音用它、TikTok 用 yt-dlp」分工。海外访问抖音国内版（douyin.com）需要代理；批量下务必加延迟限速——抖音风控严格，请求过密会触发 429/验证码（具体 QPS 阈值无官方公布数字，⚠️估算 50 次/秒量级，以实测为准）。

③ 小红书 = XHS-Downloader（不需登录就能下）

小红书图文 + 视频的最优工具是同作者的 XHS-Downloader，11.6k stars，2026-02 更新[4]。它最大的优点是不需账号登录（无 cookie 也能下，只是清晰度低；配 cookie 解锁高清），支持图文（PNG/WEBP/JPEG/HEIC）+ 视频 + Live Photo 批量下载，去水印靠抓平台原始无硬水印文件，提供 API + MCP server 模式。它逆向了 x-s / x-s-common 签名来绕过限制，并能在 7 天 cookie 失效时自动刷新。

为什么不用 yt-dlp 下小红书：小红书 2026-04-19 把主域名改成 rednote.com，引发 yt-dlp issue #16519，该修复 PR 至今（2026-06-21）未合并，清晰度/格式抓取不稳（issue 里有人能拿 direct 源、有人只剩压缩版）[5]。所以小红书直接上 XHS-Downloader，别在 yt-dlp 上耗时间。

④ 视频号 = 只能 MITM 抓包 🔴（最坑，单独警告）

视频号是五平台里唯一的死结。yt-dlp 完全不支持视频号——它没有公开的 HTTP 视频流，只走微信客户端内部的 finder 协议[1]。要下载只有一条路：MITM 中间人抓包，解密微信流量。这类工具有两个代表：

工具stars / 更新机制覆盖
qiye45/wechatVideoDownload5.3k，2026-05-10 commit[6]mitmdump MITM 代理 + HTTPS 解密拦截 + 需装本地根 CA 证书视频 / 直播回放 / 批量
putyy/res-downloader跨平台 GUI，Go+Wails[7]系统代理 127.0.0.1:8899 + 本地 CA视频号 / 小程序 / 抖音 / 小红书

🔴 视频号下载的本质风险（务必读）

MITM 解密微信流量明确违反微信 ToS，有账号风险[6]。装本地根 CA 证书来拦截 HTTPS，本身就是把你的设备置于「中间人攻击」状态——这不只是封号问题，也是安全问题（任何能用这张证书的程序都能看你所有 HTTPS 流量）。腾讯官方的「视频号助手」（channels.weixin.qq.com）只提供创作者后台管理，不提供任何下载功能。结论：视频号能不下就不下；非下不可就用一个不重要的微信小号、下完立刻删证书，绝不用主号。Ch8 法律章会再展开。

⑤ Twitter/X = yt-dlp（视频）+ gallery-dl（图集）

Twitter 的视频用 yt-dlp 原生下（公开视频可用，NSFW 需 cookie，--cookies-from-browser firefox 更可靠）[1]；而媒体图集批量首选 gallery-dl，18.6k stars，2026-06-13 release[8]。gallery-dl 用 cookie 认证，平台 API 变更时会报 AuthError（更新后恢复），它不支持 TikTok——所以是「gallery-dl 擅图集、yt-dlp 擅视频」两者配合。

# Twitter 视频
yt-dlp --cookies-from-browser firefox \
  -o "%(uploader)s/%(id)s.%(ext)s" "https://x.com/user/status/123"

# Twitter 媒体图集（含图片）
gallery-dl --cookies-from-browser firefox "https://x.com/username/media"

⚠️ 不推荐：MediaCrawler 与未核实工具

MediaCrawler（27k+ stars）用 Playwright 浏览器自动化爬多平台（小红书/抖音/快手/B站/微博），但它侧重评论数据而非纯下载，且是非官方 API 随时会被封 🔴[9]。另有 f2 等工具未能独立核实状态，本报告不背书。逐平台用上面列的「最优解」即可，不要为了「一个工具通吃」去赌不稳定的全平台爬虫。

03文案 + 字幕提取：自带 caption + ASR 选型▾

字幕和文案是整个库的「检索灵魂」——有了它们才能全文搜索、秒级定位到某句话出现的时间点。两条路：平台自带 caption 直接抓（免费、最准），没有的话才跑 ASR。先判断哪些平台有自带字幕。

第一步：抓平台自带文案 + 字幕

yt-dlp 的 --write-info-json 对 TikTok 能抓到完整文案元数据：描述、标题、标签、作者、互动数（view/like/comment/save）、音乐（track/album/artist），全部落在 info.json 里[10]。字幕方面，TikTok 有平台自带 caption，yt-dlp 通过三条路径提取（interaction_stickers / auto_video_caption_info / auto_captions API 端 + cla_info / caption_infos Feed 端 + subtitleInfos 网页端），SRT 首选[11]。各平台自带字幕情况：

平台自带文案元数据自带 CC 字幕怎么办
TikTok完整（info.json）[10]有（中/英 SRT/VTT 可下）[11]yt-dlp 一把抓
抖音有（同 extractor）有但反爬不稳（#14177）[12]抓到就用，抓不到跑 ASR
小红书有无 CC 系统（#12719）[12]必跑 ASR
视频号有限无自带字幕必跑 ASR
Twitter/X推文文本作 description（age-restricted 受限 #6763）无 CC 字幕必跑 ASR
 
# 有自带字幕的平台（TikTok/抖音）：直接拿 SRT
yt-dlp --write-info-json --write-subs --write-auto-subs \
  --sub-lang zh,en --convert-subs srt URL

第二步：没自带字幕的，跑 ASR——Mac 上中文口播首选 SenseVoice

这是本章最反直觉的结论。大多数人默认「中文 ASR 上 Whisper」，但在 Mac（Apple Silicon）上做中文口播，SenseVoice 又快又准：

★ SenseVoice vs Whisper（M4 Pro 实测）

SenseVoice Small（阿里 FunAudioLLM）处理 27 分钟中文播客只要 13.83 秒（118× 实时）CER 10.78%；同一段 Whisper Large V3 Turbo 要 2 分 04 秒（13.1× 实时）CER 12.55%[14]。SenseVoice 速度约是 Turbo 的 9 倍、精度还更好，靠的是 NAR（非自回归）架构并行解码，VRAM 占用 <1GB。对一个要批量转写几百条短视频的私人库，这个速度差直接决定了你愿不愿意跑全量字幕。⚠️ 这组数字来自单篇博客的单设备单语料实测，方向（SenseVoice 在 Mac 中文场景又快又准）可信，但具体倍数/CER 自己拿 10 条真实视频校准——不同口音、背景音、专业词会拉低准确率。

完整 ASR 选型优先级（按场景）：

1SenseVoice Small — 本地 Mac 中文口播首选
最快、CER 最低、VRAM<1GB[14]。唯一缺点：SRT 导出要自己写序列化（不像 WhisperX 一键 --output_format srt），多花 ~30 行 Python。
2faster-whisper large-v3-turbo — 通用快
CTranslate2 实现，比 OpenAI 原版快 4×，叠 VAD 批处理再 3×（≈12.5×）[24]。GPU fp16 下 13 分钟音频 19 秒（WER 1.9%），turbo ≈129× 实时[13]。马来/英语混说设 language=None 自动检测。
3WhisperX — 要词级时间戳/说话人时用
支持中文词级时间戳（DEFAULT_ALIGN_MODELS_HF 含 zh，用 wav2vec2-large-xlsr-53-chinese 对齐），可输出 SRT/VTT/TXT/TSV/JSON，--highlight_words 出词级高亮 SRT[15]。中文模型首次需联网拉 HF。中文 CER 无公开对比数据 🟡。
4OpenAI gpt-4o-mini-transcribe API — 无 GPU 兜底
$0.003/分（新推荐，同精度比 legacy whisper-1 的 $0.006/分便宜一半）[16]。实时转写另有更贵的 realtime 系列（按 token 或分钟计，以官方定价页当日为准）。无本地算力时用，按量付费。

第三步：softsub 存库，不烧录

hardsub vs softsub：存库一定选 softsub。hardsub 是像素级烧录进画面——任何播放器都兼容，但文件变大、不可关、不可改、不可检索；softsub 是独立 SRT track 内嵌进 MP4/MKV，可检索、可编辑、可切语言，是存库首选[18]。短视频存库建议：保留原视频 + 独立 .srt 文件（不内嵌也行，元数据库里存路径即可），需要发布时再单独生成 hardsub 版本。字幕入库的价值有三：① 全文搜索（字幕 tokenize 进 SQLite FTS 秒级定位时间点，SubTubular/Filmot 都基于此，字幕还覆盖 75% 的无声观看场景[19]）；② 二次创作（字幕时间戳是剪辑索引层，OpusClip 等切片工具靠它）；③ 学习（双语字幕 → 词表 pipeline）。

✅ 推荐字幕链（一条命令 + 兜底）

先 yt-dlp --write-info-json --write-subs --write-auto-subs --sub-lang zh,en --convert-subs srt 抓 TikTok/抖音自带 SRT；抓不到（小红书/视频号/Twitter）再跑 ASR：本地 Mac 上 SenseVoice Small > faster-whisper large-v3-turbo > WhisperX（要词级/说话人）> OpenAI gpt-4o-mini-transcribe（无 GPU）。Apple Silicon 也可用 MLX-Whisper；Whisply 这个 CLI 工具同时支持 faster-whisper + mlx-whisper，适合 Mac 批量[25]。

04短视频压缩：H.264/H.265/AV1 + ffmpeg 三档命令▾

压缩是「可选但很值」的环节——它把存储成本砍掉一半。先理解三种编码的取舍，再抄命令。

编码相对 H.264 省体积专利/授权兼容性Mac/iPhone 私存适配
H.264基准有授权费但已普及全绿通吃能播但占地方
H.265 (HEVC)省 25–50%[20]三专利池，个人私有归档无需缴费[21]Safari/iOS 硬解强；Chrome/FF 支持视 OS/硬件而定，需实测★ 最佳（+hvc1）
AV1省 ~50–60%（学界 28.1% vs H.265）[20]专利免费（AOMedia）[21]Chrome70+/FF67+/Safari17，老 iPhone 软解或不支持极致压缩用，CPU 软编很慢

编码效率排序：AV1 > H.265 > VP9 > H.264[20]。但效率不是唯一指标——压缩越狠 CPU 越慢、兼容性越差。对「存 R2 + Mac/iPhone 播放」这个具体场景，H.265 是甜点：省一半体积、iOS 硬解流畅、个人归档免授权费。要在浏览器里直接播或追求极致压缩（100GB→40GB）才上 AV1。注意 2025-11 起 Dell/HP 部分中低端笔记本因授权费上涨在 UEFI 禁了 HEVC 硬解[21]，但这不影响 Mac。

~30MB

ffmpeg 三档命令（可直接复制）

① 存档优先（Mac/iPhone 播放，省 ~50%）— 默认就用这条

ffmpeg -i in.mp4 -c:v libx265 -crf 28 -preset slow \
  -tag:v hvc1 -c:a aac -b:a 128k \
  -movflags +faststart -map_metadata 0 out.mp4

-tag:v hvc1 必须加，否则 Mac/iPhone 不认这个 HEVC 文件。-movflags +faststart 让网页边下边播，-map_metadata 0 保留原始元数据。

② 画质优先（极致压缩，AV1）

ffmpeg -i in.mp4 -c:v libsvtav1 -crf 24 -preset 4 \
  -svtav1-params keyint=10s:tune=0 -c:a aac -b:a 192k \
  -movflags +faststart out.mp4

SVT-AV1 软编，CPU 换存储费。SVT-AV1 官方说 CRF 模式不需要 two-pass[26]。

③ 兼容优先（任何浏览器/设备都能播，H.264）

ffmpeg -i in.mp4 -c:v libx264 -crf 23 -preset medium \
  -profile:v high -level 4.1 -c:a aac -b:a 128k \
  -movflags +faststart out.mp4

⚠️ Mac 硬件加速档（批量快跑，VideoToolbox）

ffmpeg -i in.mp4 -c:v hevc_videotoolbox -q:v 50 \
  -tag:v hvc1 -c:a aac -b:a 128k -movflags +faststart out.mp4

VideoToolbox 不支持 CRF，只有 -q:v（值越大画质越高），速度约软编 15× 但文件大 10–20%[17]。VideoToolbox 不支持 AV1 硬编——要 AV1 只能 libsvtav1 CPU 软编（很慢）。NVENC 显卡用 hevc_nvenc -preset p6。

批量脚本 + VMAF 验证

# 批量转码 + 第3秒截封面帧
for f in *.mp4 *.mov; do
  ffmpeg -i "$f" -c:v hevc_videotoolbox -q:v 50 -tag:v hvc1 \
    -c:a aac -b:a 128k -movflags +faststart "compressed_$f"
  ffmpeg -ss 3 -i "$f" -frames:v 1 -q:v 2 "thumb_${f%.*}.jpg"
done

# VMAF 验证画质（>93 透明 >80 良好 <70 劣化）
ffmpeg -i compressed.mp4 -i orig.mp4 \
  -filter_complex libvmaf=n_subsample=4 -f null -

阿杰场景结论：存 R2 + Mac/iPhone 播放 → 默认用存档档（libx265 CRF28 slow + hvc1，省 ~50%）。批量时先用 VideoToolbox 硬件加速快跑，再抽样用 VMAF 验 >85 确认没劣化。只有要把 100GB 库压到 40GB 这种极致需求才切 AV1 档（拿 CPU 时间换存储费）[27]。但记住：短视频本来就小，压缩是「锦上添花」不是「起步必做」——B 档可以先跳过这一环。

视频这种「存得多、看得少」的数据，存储成本的大头不是容量而是下行流量（egress）。R2 的杀手锏就是 egress 全免费。

对阿杰：直接用 R2 最优。同 500GB/月下行，R2 约 $1.35 vs S3 约 $47[23]。B2 存储更便宜（$6.95/TB ≈ $0.007/GB）但它的免费 egress 有条件（限月均存储的 3× 或走 Bandwidth Alliance/CDN），不是无条件全免，且要自己接 Cloudflare CDN 才落地，集成更繁。R2 跟 CF 的 Worker/CDN 原生打通，而且 CF 在吉隆坡/新加坡有 PoP，延迟低[29]。阿杰已有 R2 的话连选型都省了。

上传：rclone 批量同步（最优）

# ~/.config/rclone/rclone.conf 配置
[r2]
type = s3
provider = Cloudflare
access_key_id = <你的 R2 access key>
secret_access_key = <你的 R2 secret>
endpoint = https://<accountid>.r2.cloudflarestorage.com
acl = private
# 批量上传（文件>100M 自动 multipart，只重传失败分片）
rclone copy /local/videos r2:my-bucket \
  --transfers 8 --s3-upload-cutoff 100M --s3-chunk-size 64M

# 增量同步（只传新增/变化）
rclone sync /local/videos r2:my-bucket

rclone 是最优上传方式：单文件 PUT 不续传，但 multipart 模式下只重传失败的分片，rclone 在文件 >100M 时自动触发[28]。单文件上限 5TB（multipart ≤10000 parts）。注意 Wrangler 上限只有 315MB，不适合视频，别用它传。其他方式：aws s3 cp --endpoint-url、boto3 generate_presigned_url。

私有访问：三种方案

R2 bucket 默认私有。让你的私人库能被（且仅被）你访问，有三条路：

1Presigned URL（最简，脚本首选）
boto3 client(endpoint_url=R2).generate_presigned_url('get_object', ExpiresIn=3600) 生成 1 秒–7 天有效的临时链接[30]。缺点：不支持自定义域名，只能用 <accountid>.r2.cloudflarestorage.com。适合脚本/单人用。
2Cloudflare Access（组织成员登录）
用 Google/GitHub 登录验证，需自定义域 + Zero Trust[31]。适合团队内部，不适合匿名用户（体验差）🟡。
3Worker 鉴权（最灵活，长期推荐）
自定义域 + JWT/Cookie 验证 + env.R2_BUCKET.get(key) + 支持 Range 请求 seek + CDN 缓存[30]。能做精细权限、自定义域名、视频 seek。注意 Worker 返回的 R2 内容默认不缓存，需手动设 Cache-Control 🟡。

与半米后台对接架构

通用架构：视频走 R2，元数据走半米 DB。上传 = 后台生成 presigned PUT URL → 脚本/前端直传 R2 → 回调更新 DB；播放 = 前端请求后台 /api/video/:id → 验权 → 后台生成 presigned GET（1h 有效）→ 返回前端 <video src>[32]。命名用 lessons/{lesson_id}/videos/{uuid}.mp4 防 URL 猜测。R2 托管的视频 CF ToS 明确允许分发（不受旧 Section 2.8 限制），支持 HTTP Range（Accept-Ranges，seek 正常），私人小库用普通 MP4 progressive download 就够，HLS 是公开大流量才需要[29]。R2 presigned + Range seek 官方未明确，社区认为可行 🟡。

06拼成 pipeline：Python 主 + n8n 触发 + SQLite schema▾

对会写代码的个人用户，Python 脚本 + 直接调系统命令是最合适的编排基础——yt-dlp 有原生 Python API，--dump-json 直接吐完整元数据。n8n 当可视化补充（触发/调度/通知）有价值但有摩擦：云版不支持本地 binary，自托管可用 Execute Command 调 yt-dlp/ffmpeg/whisper；Celery 过重、bash+cron 错误处理弱[33]。结论：Python 核心逻辑 + n8n 触发/通知混用。

推荐 pipeline 流程

触发（A.手动丢链接 CLI / B.cron 定时从收藏增量）
  ↓
yt-dlp --dump-json 解析元数据 → 查 DB video_id 是否已存在
  ↓
yt-dlp -f best --download-archive archive.txt 去重下载
  ↓
ffmpeg 压缩（可选，短视频常跳过）
  ↓
ASR 批量转写 SRT/VTT（SenseVoice / faster-whisper）
  ↓
rclone/boto3 上传 R2（视频 + 字幕 + 缩略图）
  ↓
写 SQLite 元数据（R2 key + transcript 全文）
  ↓
Discord webhook 通知

n8n 可接管「触发层 + 通知层」，核心仍是 Python[33]。

去重：--download-archive 是主力

用 yt-dlp 自带的 --download-archive archive.txt 做主去重，每行 <extractor> <video_id>，跨 session 断点续传[34]。DB 层再加 UNIQUE(platform, video_id) 约束、下载前先查 DB 双保险。不要用内容 hash 去重——同一视频不同 bitrate 的 hash 不同（#7348），意义有限。批量回填历史用 --download-archive existing.txt。

SQLite 元数据 schema（完整 CREATE TABLE，可直接用）

CREATE TABLE videos (
  id            INTEGER PRIMARY KEY,
  platform      TEXT NOT NULL,        -- tiktok/douyin/xhs/wechat/twitter
  video_id      TEXT NOT NULL,
  original_url  TEXT,
  title         TEXT,
  description   TEXT,
  uploader      TEXT,
  uploader_id   TEXT,
  upload_date   TEXT,                 -- YYYYMMDD
  duration      REAL,
  width         INTEGER,
  height        INTEGER,
  view_count    INTEGER,
  like_count    INTEGER,
  comment_count INTEGER,
  tags          TEXT,                 -- JSON 数组
  hashtags      TEXT,                 -- 从 description 解析
  transcript    TEXT,                 -- ASR/字幕全文，供 FTS5
  thumbnail_url TEXT,
  r2_video_key  TEXT,
  r2_thumb_key  TEXT,
  r2_srt_key    TEXT,
  downloaded_at TEXT DEFAULT (datetime('now')),
  UNIQUE(platform, video_id)

-- FTS5 全文索引（标题/描述/字幕/标签）
CREATE VIRTUAL TABLE videos_fts USING fts5(
  title, description, transcript, tags,
  content='videos', content_rowid='id'
);
-- 触发器同步 videos → videos_fts（INSERT/UPDATE/DELETE 各一个）

字段对照 yt-dlp 输出[35]。yt-dlp 本身不写 SQLite，需要 --dump-json + 自写 ~50 行 Python 胶水把 JSON 字段映射进表[36]。hashtag 各平台行为不一（单独字段 vs 从 description 解析），需实测。

全文搜索：SQLite FTS5 起步够用

FTS5 起步无需 Meilisearch。SQLite FTS5 内嵌 BM25 排序，几千到几十万条亚毫秒返回、零依赖[37]。Meilisearch 的优势是 typo tolerance / facet / 中文分词，但存储 6–10×、要独立进程。可以并存（FTS5 主库 + Meilisearch 同步索引 transcript），但个人库起步先 FTS5，量大了再加。Datasette + datasette-media 插件能把 SQLite 直接暴露成可浏览 Web UI、支持缩略图代理，适合快速搭前端原型[38]。

⚠️ 坑：FTS5 默认分词器不分中文。FTS5 默认 unicode61 按空格/标点切词，中文连写没有空格会被当成一个长 token，搜「化妆」可能搜不到「学化妆教程」。中文检索要换分词方案：① 最简用 FTS5 的 trigram tokenizer（任意子串匹配，配置一行、对中文够用，代价是索引变大）；② 入库前用 jieba 分词、把空格分好的结果写进 FTS 列；③ 重度需求上带 ICU 的构建或外部索引（Meilisearch）。个人库起步直接用 trigram，省事。

07私人库的检索与前端：现成项目为何不能直接用▾

有人会问「为什么不直接装个 Tube Archivist 之类的现成项目？」答案是：它们全是 YouTube 专用，没有一个能直接处理 TikTok/抖音/小红书。它们只能当灵感或下载触发器参考。

项目定位字幕全文搜索能用于短视频吗
Tube ArchivistYouTube 专用 + Elasticsearch 依赖重有无法用于 TikTok/Instagram[39]
PinchflatYouTube 专用，单容器轻量 + Plex/Jellyfin无无短视频、无字幕搜索[39]
MeTube纯下载前端（yt-dlp Web UI）无元数据库无检索[39]

为什么都不能直接用：这些项目要么绑死 YouTube extractor、要么没有元数据库、要么没有字幕全文搜索——而你的核心需求恰恰是「跨五个平台 + 按文案/字幕全文检索」。Tube Archivist 还要拖一个 Elasticsearch，对个人库是重型依赖。所以正确做法是自建：Ch6 的 SQLite + FTS5 已经把后端搞定，前端三选一。

08⚠️ 法律与封号边界：私人存档 vs 公开使用▾

这一章如实讲，不为任何灰产或二次发布背书。核心原则一句话：私人存档和公开使用是两回事——下载到自己硬盘上看，和把别人的视频重新发布/商用，是完全不同的法律性质。

🔴 红线一：视频号 MITM 抓包有真实封号风险

所有视频号下载工具都要 MITM 解密微信流量，明确违反微信 ToS，有账号风险[6]。这不是「理论上可能」——你装了本地根 CA 证书、把微信流量路由到代理，这本身就是微信反作弊系统能检测的行为模式。对策：用一个不重要的微信小号操作、下完立刻卸载证书、绝不用主号；能不下视频号就不下。这是全报告唯一标 🔴 的操作。补一句被低估的点：装根 CA + 系统代理期间，你的所有 HTTPS 流量（含微信会话、支付、其他 App）都对这套工具可见——只用一次性环境、用完彻底清理，别让抓包工具常驻。

🟡 红线四：凭证安全（容易忘的运维风险）

这套库会沉淀一堆敏感凭证：浏览器导出的 cookie（等于平台登录态）、R2 access key、Worker secret。别提交进 git、别明文写脚本里——用环境变量或 .env（加进 .gitignore），cookie 定期失效要轮换，R2 key 给最小权限（只读/只写对应桶）。SQLite 主库是核心资产，开 WAL + 定期备份（甚至上 R2 versioning），一旦损坏整个库的元数据和字幕全文就没了。

🟡 红线二：各平台 ToS——下载基本都违反，量级决定风险

抖音、小红书的批量下载工具都违反平台 ToS，但「小量私人存档」实践中低风险 🟡，「大量爬取/二次发布/商用」风险陡增[3]。MediaCrawler 这类非官方 API 爬虫随时被封 🔴[9]。TikTok/Twitter 下公开内容相对低风险 🟢，因为是公开 API 路径、不碰登录态。限速很重要：抖音风控严，请求过密触发 429/验证码（QPS 阈值无官方数字，⚠️估算 50 次/秒量级），批量下务必加延迟。

🟡 红线三：版权——私存容忍区，公开/商用必侵权

下载的视频仅适合私人存档。把别人的视频二次发布、剪辑后发布、商用，可能同时违反平台 ToS 和版权法[1]。阿杰人在马来西亚，受 马来西亚 Copyright Act 1987 管辖——该法对私人复制（private/personal use）有一定容忍空间，但「向公众传播」（communication to the public）是受限的专有权利。字幕也一样：你自己听写/ASR 出来的字幕，是原作的演绎成果，传播仍需原权利人许可，不产生独立于原作的可公开权利。

✅ 安全区 vs 危险区一览

行为性质风险
下载到本地/自己的 R2，自己看/学习/检索私人复制容忍区低（除视频号 MITM）🟢
下载后压缩/加字幕存私人库，不外传仍是私人使用低 🟢
R2 库生成 presigned URL 发给朋友看小范围传播，灰区中 🟡
剪辑/搬运后重新发布到任何平台公开传播 + 可能商用高，违 ToS + 版权 🔴
视频号 MITM 抓包（任何用途）违微信 ToS封号 🔴

本报告的立场：这套 pipeline 的正当用途是个人的研究、学习、内容研究的私有归档与检索——比如阿杰做内容研究时把素材下下来打标签、全文搜索。它不为二次发布、搬运、灰产提供任何便利或背书。R2 私有桶把内容默认锁死，访问要主动签发凭证——注意 presigned URL 是 bearer token，谁拿到链接在有效期内都能用，所以要短有效期 + 别外泄；要严格「仅本人」用 Worker 鉴权（Ch5）。这既是技术选择也是合规设计。一旦你想把库里的东西往外发，那就是另一套完全不同的版权授权问题，本报告不覆盖。

09阿杰路线建议：决策树 + 先做哪一步 ★▾

把前八章压缩成一棵决策树，回答两个问题：「我该搭哪一档」和「这周先做哪一步」。

Q1 · 你要存哪些平台？
只要 TikTok / Twitter✅ 最幸运，yt-dlp 一个工具搞定，公开内容低风险 → 继续 Q2（Ch2）
要抖音 / 小红书⚠️ 换 TikTokDownloader / XHS-Downloader，违 ToS 但小量私存可控 → 继续 Q2（Ch2）
非要视频号🔴 只能 MITM 抓包，封号风险 → 用小号、下完删证书、绝不主号（Ch2/Ch8）
Q2 · 你回来检索这些视频吗？
只想备份不检索→ A 档：yt-dlp 下到文件夹，完事。别过度工程（Ch1）
要按文案/字幕搜✅ B 档：Python 包 yt-dlp + SQLite FTS5 → 继续 Q3
Q3 · 多设备访问 / 长期养库吗？
先单机验证→ 留在 B 档，本地 SQLite + Datasette 前端，验证你真会用（Ch7）
要多设备 + 跟半米对接✅ C 档：加 R2 存储 + Worker 鉴权 + 半米后台（Ch5/Ch6）
Q4 · 库会膨胀到几百 GB 吗？
就几十 GB→ 跳过压缩，短视频本来小，省心（Ch4）
会很大✅ 加 H.265 存档档压缩，Mac VideoToolbox 批量跑，省一半（Ch4）

★ 先做哪一步（这周就能做的事）

第一步只做一件事：把"一个平台下载 → 存本地 → 建 SQLite 元数据"跑通。具体：① 选 TikTok（阻力最小），pip install yt-dlp；② 写 ~50 行 Python：yt-dlp --dump-json 拿元数据 → 映射进 Ch6 的 videos 表 → 建 FTS5 索引；③ 下 10 条你真关心的视频进库；④ 用 Datasette 点亮，试着按文案搜一次。这一步跑通你就有了一个能全文检索的私人短视频库，且不上云、无账号/安全风险（视频号 MITM 除外）——平台 ToS 与版权风险按 Ch8 的私存边界即可。

✅ 然后再按需加（不要一次全上）

验证你真的会回来检索之后，再分批加：加平台（抖音上 TikTokDownloader、小红书上 XHS-Downloader）→ 加字幕（TikTok 自带 SRT 直接抓，其余跑 SenseVoice）→ 加 R2（rclone sync 上云，要多设备时才需要）→ 加压缩（库变大才做，H.265 存档档）。视频号永远放最后、能不碰就不碰。每加一环都先确认上一环真的在用——大多数「全功能媒体库」死在第一周热情过后没人维护，B 档的最短链路才是能活下来的那个。

与姊妹篇的关系：这套 R2 + SQLite + Python 编排的骨架，和 RSS 知识库系统那篇是同一套地基。如果你两个库都要建，共用一个 SQLite 实例和一个 R2 桶（不同表/不同 key 前缀），编排脚本和鉴权逻辑只写一遍，维护成本省一半。

QFAQ：12 个最可能被问到的问题▾

Q1有没有一个工具能通吃全部五个平台？＋

没有，别找了。每个平台的反爬、协议、去水印都不同：TikTok/Twitter 用 yt-dlp，抖音用 TikTokDownloader（yt-dlp 已破损[2]），小红书用 XHS-Downloader（yt-dlp 改域名后残废[5]），视频号只能 MITM。号称全平台的 MediaCrawler 侧重评论数据、且是非官方 API 随时被封[9]。逐平台用最优解，比赌一个不稳定的全能工具靠谱得多。

Q2为什么视频号这么特殊，就不能像 TikTok 一样下？＋

因为视频号没有公开的 HTTP 视频流——它只走微信客户端内部的 finder 协议[1]。yt-dlp 这种靠请求公开接口的工具完全无从下手。唯一办法是 MITM 抓包解密微信流量（装本地根 CA 证书拦截 HTTPS），这明确违反微信 ToS、有封号风险[6]。腾讯官方的视频号助手只给创作者管理后台，不提供下载。所以视频号是五平台里唯一「能不碰就别碰」的。

Q3我人在马来西亚，下抖音国内版能直连吗？＋

不能，抖音国内版（douyin.com）海外访问需要代理；yt-dlp 对抖音的支持本身也在持续破损[2]，所以抖音走 TikTokDownloader + 代理。TikTok（国际版）海外直连无障碍，yt-dlp 直接跑。所以海外用户做这套库，TikTok/Twitter 零摩擦，抖音/小红书要挂代理，视频号最麻烦。批量下抖音务必限速，请求过密会触发 429/验证码。

Q4Mac 上做中文字幕，到底用 SenseVoice 还是 Whisper？＋

中文口播首选 SenseVoice。M4 Pro 实测它处理 27 分钟中文播客只要 13.83 秒（118× 实时）CER 10.78%，而 Whisper Large V3 Turbo 要 2 分 04 秒（13.1×）CER 12.55%[14]——又快又准。唯一不便是 SenseVoice 导出 SRT 要自己写序列化（多 ~30 行代码），WhisperX 则一键 --output_format srt。如果要词级时间戳或说话人分离，用 WhisperX；纯转写文案用 SenseVoice；无 GPU 用 OpenAI gpt-4o-mini-transcribe（$0.003/分[16]）。

Q5短视频本来就小，还有必要压缩吗？＋

起步阶段不必要——单条短视频几 MB 到几十 MB，B 档可以完全跳过压缩。只有当库膨胀到几百 GB、存储/上传成本开始肉疼时才值得做。那时用 H.265 存档档（libx265 CRF28 slow + hvc1）能省约一半体积[17]，Mac 上用 hevc_videotoolbox 硬件加速批量跑（~15× 软编速度）。记住 -tag:v hvc1 必须加，否则 iPhone 不认。

Q6为什么存 R2 而不是 AWS S3 或本地硬盘？＋

R2 的 egress（下行流量）全免费无上限[22]，而视频是「存得多、偶尔反复看」的数据，egress 才是大头。同样 100GB 存 + 500GB/月下行，R2 约 $1.35 而 S3 约 $47[23]。本地硬盘适合纯备份但不能多设备访问、容易坏。如果只单机用、不多设备，B 档完全可以先不上云、存本地——R2 是 C 档（多设备/对接半米）才需要的。

Q7下载这些视频违法吗？会被追责吗？＋

分两层。下载行为：多数平台 ToS 不允许，但「小量私人存档自己看」实践中低风险[3]，视频号 MITM 是唯一有真实封号风险的 🔴。版权：私人复制/个人学习落在容忍区（马来西亚 Copyright Act 1987 对 private use 有空间），但二次发布、搬运、商用就是确定的侵权 + 违 ToS 🔴。本报告只覆盖私人存档与检索，不为任何对外传播背书。

Q8怎么避免重复下载同一个视频？＋

主力用 yt-dlp 自带的 --download-archive archive.txt，它记录每个已下视频的 extractor video_id，跨 session 断点续传[34]。再在 SQLite 加 UNIQUE(platform, video_id) 约束做第二道保险。别用内容 hash 去重——同一视频不同清晰度 hash 就不同，没意义。批量回填历史时把已有的喂给 --download-archive existing.txt。

Q9为什么不直接装 Tube Archivist 这种现成的？＋

因为它们全是 YouTube 专用，没一个能处理 TikTok/抖音/小红书[39]。Tube Archivist 还要拖一个 Elasticsearch（个人库重型依赖），Pinchflat/MeTube 没有字幕全文搜索。你的核心需求是「跨五平台 + 按文案/字幕检索」，这恰好是它们做不到的。自建 SQLite + FTS5（Ch6）其实没多少代码，且完全贴合需求。它们只能当下载触发器或 UI 灵感参考。

Q10n8n 能不能直接搭整条 pipeline？＋

不建议让 n8n 当主力。云版 n8n 不支持本地 binary（跑不了 yt-dlp/ffmpeg），自托管虽能用 Execute Command 调，但相比直接写 Python 摩擦大、调试难[33]。对会写代码的你，Python 当核心逻辑、n8n 只当触发层和通知层（比如「每天定时拉收藏」「下载完发 Discord」）才是最优组合。n8n Docker 内写 R2 的完整示例也很少，细节得自调。

Q11私人库怎么做到「只有我能访问」？＋

R2 桶默认私有，三种私有访问方式：① Presigned URL（最简，boto3 生成 1h 有效临时链接，但不支持自定义域名）；② Cloudflare Access（Google/GitHub 登录，需自定义域 + Zero Trust，适合团队）；③ Worker 鉴权（最灵活，自定义域 + JWT/Cookie + 支持视频 Range seek，长期推荐）[30]。命名用 lessons/{id}/videos/{uuid}.mp4 防 URL 猜测[32]。单人用 presigned URL 起步就够。

Q12这套库能跟我的 RSS 知识库共用一套基础设施吗？＋

能，而且应该。这篇和姊妹篇 RSS 知识库系统共用同一套地基：R2 存储、SQLite + FTS5 检索、Python 编排。两个库共用一个 SQLite 实例（不同表）和一个 R2 桶（不同 key 前缀），鉴权和编排逻辑只写一遍。短视频专项的特殊性只在「下载层」（逐平台工具）和「ASR/压缩层」，后半段（存储/检索/前端）完全可以和文本知识库合并维护。
