📅 2026-05-23 🛠 调研人：无忌 🎯 触发条件：YouGlish ≥ €300/月 📦 stack: yt-dlp + Postgres FTS + YouTube iframe 💰 一次性 ¥10-15 万 · 续费 ¥3-5 万/年
三句话结论：(1) Layer 2 不是替代 YouGlish，而是 banmi 长成 €300/月用量后买断式自建，把"片段质量评级 / 频道偏好 / 难度排序"这些算法变成 banmi 自己的护城河 —— Layer 1 永远是别人的。(2) 技术栈推荐 yt-dlp（VTT 字幕）+ Postgres FTS（GIN 索引，约 1500 万段没问题）+ YouTube IFrame API（client-side 跳 timestamp），跟 banmi Next.js + Postgres 完全焊得上，不需要引入 Elasticsearch。(3) 一次性投入 ¥10-15 万（3 人月开发 + 内容入库），月续费 ¥300-800（VPS + 代理 + 监控），回本周期 ≈ 1 年；本报告底部嵌了可玩的"假自建" widget，输入词试试就能看到完整体验路径。

01一句话定位 + Layer 2 触发条件▼

一句话定位：banmi 自建的 YouTube 字幕索引 + 前端跳片段播放器 = 把 YouGlish 的"搜词出视频片段"能力买断到自家服务里，可控、可定制、可作为长期资产沉淀。

📐 跟 Layer 1（YouGlish iframe）的关系
  • Layer 1 在 V0.2 即上：YouGlish 官方 widget，2 行代码集成，免费档先用
  • Layer 2 在 V0.3+ 启动：触发条件满足时切换，前端 UI 几乎不变（学生看不出差别）
  • 切换不是 hard cut：Layer 1 / Layer 2 可以共存，banmi 自己的精选频道走 Layer 2，长尾词回退到 YouGlish Layer 1

触发条件（4 选 1 就该启动）

触发器阈值触发后行动
💰 财务触发 YouGlish 月费 ≥ €300（年 €3600 ≈ ¥28k） 立即立项，1 人月做 Layer 2 MVP，跑通后切流量
📊 用量触发 banmi 日 query ≥ 8000 次（接近 €300 档 10000/天的 80%） 提前 30 天启动，避免触发月费
🎯 内容触发 5500 雅思词每个都需要 "精挑细选 5-10 个高质量片段"，YouGlish 排序不可控 启动 Layer 2 是为了控制片段质量，不是省钱
⚠️ 风险触发 YouGlish 改条款 / 涨价 / 停服 / 给 banmi 发警告 紧急启动；这是为什么我们要保留 yt-dlp + Postgres 的 know-how
📌 半米总纲 §4.5.3 对应位置：本方案完整实现总纲 V0.3+ 的 Layer 2 路径。Layer 3（影视片段）在 V0.4+，本报告不涉及。

02整体架构图▼

系统分 3 层 5 角色，全部 banmi 自托管（除了 YouTube 视频流，那个走 YouTube CDN）：

L1 · 数据采集层（offline batch）
📺YouTube视频 + 字幕源
🪛yt-dlp--write-subs --skip-download
📝VTT 解析器node webvtt-parser
🧹清洗 + lemmaspaCy / lemminflect
⬇ 写入 Postgres
L2 · 索引存储层（核心数据库）
🗄️Postgres 16videos / captions / word_index
🔎GIN tsvector毫秒级全文搜索
⚡Redis热词 query 缓存 24h
⬇ REST API
L3 · 应用 API + 前端
🚀Next.js API/api/clips?lemma=...
🎬YouTube iframe?start=120&end=128
📱banmi 词卡片段循环 + 字幕高亮
⬆ event_log
L0 · 调度 + 监控（持续运营）
⏰cron / GitHub Actions每日扫频道增量
📡代理池2-3 IP rotate
📈监控抓取失败率 / 查询热点
🎯 架构决策三条
  1. 视频本体永不下载 —— yt-dlp 只抓字幕（--skip-download），视频从 YouTube CDN 直接拉，banmi 0 带宽成本，0 版权风险
  2. 索引走 Postgres FTS，不上 Elasticsearch —— banmi 估算上限 1500 万段 caption（10000 视频 × 1500 段），Postgres GIN 完全够用，运维省 1 个数据库实例
  3. 前端跳片段走 YouTube IFrame API，不做视频代理 —— iframe 是 YouTube 官方允许的 embed，零灰区

03yt-dlp 抓字幕完整 pipeline▼

3.1 命令骨架（生产可用）

# banmi/scripts/fetch_subs.sh
# 抓单个频道全部视频的字幕，跳过视频本体

yt-dlp \
  --write-subs                              # 人工字幕（优先）
  --write-auto-subs                         # auto-generated 字幕（兜底）
  --sub-langs "en.*"                       # 所有英文变体：en, en-US, en-GB, en-orig
  --sub-format "vtt/srt/best"              # 优先 vtt，其次 srt
  --skip-download                           # 关键：不下载视频本体
  --write-info-json                         # 视频元数据（标题 / 频道 / 时长 / license）
  --download-archive archive.txt            # 跳过已抓 video_id（增量）
  --ignore-errors                           # 单个视频失败不中断 batch
  --sleep-requests 2                         # 每个 HTTP 请求间隔 2s
  --sleep-interval 15                        # 每个视频处理后 sleep
  --max-sleep-interval 45                    # 随机化避免被识别为 bot
  --retries 5 --fragment-retries 5          # 失败重试
  --cookies-from-browser chrome              # 走真实浏览器 cookie，降低风控
  --output "%(channel)s/%(id)s.%(ext)s"    # 文件组织
  "https://www.youtube.com/@SciShowKids"

3.2 关键参数详解

参数含义banmi 选择
--write-subs 下载 creator 上传的人工字幕 ✅ 必开，质量 99%+
--write-auto-subs 下载 YouTube ASR 自动字幕 ✅ 兜底开，无人工字幕时用
--sub-langs 语言过滤（支持 wildcard 和 alternatives） "en.*,-live_chat" — 所有 en 变体，排除直播弹幕
--sub-format 字幕格式优先级链 "vtt/srt/best" — VTT 解析方便（有 WebVTT 标准）
--skip-download 不下载视频本体 ✅ 必开，合规边界
--download-archive 已下载 ID 记录文件 ✅ 增量抓核心机制，每天 cron 跑只补新视频
--sleep-requests 每个 HTTP request 间隔（秒） 2-3s
--sleep-interval 每个视频处理完后 sleep（秒） 15s（基础）
--max-sleep-interval sleep 上限（实际取随机区间） 45s（随机化）
--cookies-from-browser 用本地浏览器登录态访问 低风控关键，但要把 cookies 跟 banmi 主账号分离
--write-info-json 导出元数据 JSON ✅ 必开，用于 license / 时长 / channel name

3.3 字幕格式三选一

推荐

WebVTT (.vtt)

W3C 标准，WEBVTT 头明确；时间戳用 . 分隔（00:00:12.500），毫秒精度；支持 CSS 定位 / 元数据；YouTube 默认就给 VTT。

Node 解析库成熟：node-webvtt / webvtt-parser / subtitle.js，5 行代码 parse 成 {start, end, text}[]。

需要去掉 styling tags（<c.colorE5E5E5>）。banmi 抓回来用正则一行洗掉。

备选

SRT (.srt)

最古老的格式，万能兼容；timestamp 用 , 分隔（00:00:12,500）。

没有标准 header，错误格式难检测；不支持 metadata；banmi 不需要这个兼容性。

不推荐

JSON3 (.json3)

YouTube 内部 JSON 格式，含逐词 timestamp（适合做 karaoke 高亮）。

非标准格式，文档少；逐词数据 banmi 用不上（句子级精度已够）；解析复杂。

3.4 自动字幕 vs 人工字幕

维度人工字幕（creator upload）YouTube auto
准确率99%+（达 broadcast 级）清晰录音 85-95%，嘈杂场景 60-70%
标点✅ 完整❌ 几乎无标点（影响 banmi 断句搜词）
专有名词✅ 正确⚠️ 经常错（"banmi" → "ban me"）
时间戳精度±0.1s±0.5s 偏差，常超前 / 滞后
语言识别✅ 明确⚠️ 多语种视频会乱标
banmi 策略✅ 优先用⚠️ 仅用于"无人工字幕"的视频，且需要轻量后处理
📊 数据来源：YouTube 2025 公开测试 (cisdem / grabcaptions / notelm.ai) 报告 auto-caption 总体准确率 85-95%；formal WER 指标 (Word Error Rate) 在教育 / talk 类视频普遍 5-10%，但 2024 前模型 WER 高达 15-20%。banmi 抓的频道（SciShow / Crash Course / TED）都有 creator 上传字幕，问题不大。

3.5 批量抓策略：3 种模式

模式命令适用
单视频 yt-dlp [opts] https://youtu.be/<id> 测试 / 学生 ad-hoc 报告"这个视频我想加进来"
频道增量 yt-dlp [opts] https://www.youtube.com/@SciShowKids banmi 主用：精选 10-15 个频道 cron 每日扫
Playlist yt-dlp [opts] "<playlist URL>" 抓"高中英语听力训练 100 集" 这类主题包

3.6 增量更新机制

# banmi 每日 cron 任务 — 扫频道列表 + archive 跳过已抓
# /etc/cron.d/banmi-subs-daily

0 3 * * * banmi /opt/banmi/scripts/fetch_subs_daily.sh >> /var/log/banmi-subs.log 2>&1

# fetch_subs_daily.sh — 遍历 channels.txt 每个频道增量抓
while read channel; do
  yt-dlp \
    $(cat /opt/banmi/yt-dlp.opts) \
    --download-archive /opt/banmi/data/archive.txt \
    "$channel"
  # 抓完触发解析 + 入库
  node /opt/banmi/scripts/parse_and_index.mjs \
    --channel "$channel" \
    --input-dir /opt/banmi/data/subs/
done < /opt/banmi/channels.txt

3.7 速率限制 / 反封禁三层

  1. 请求节流：--sleep-requests 2-3 --sleep-interval 15 --max-sleep-interval 45 让单 IP 抓取速率接近真实用户浏览节奏
  2. Cookie 轮换：用 2-3 个独立 Google 账号，每个账号配 --cookies-from-browser + 独立浏览器 profile；账号跟 banmi 主账号严格隔离
  3. 代理 IP：触发 429 / IP ban 时切换代理（推荐 BrightData / Smartproxy 住宅 IP，~¥50-150/月）；轻量场景下香港 / 新加坡 VPS 多 IP 就够
📡 实战经验：根据 yt-dlp GitHub issue 区，使用 -r 3M --sleep-requests 3 --sleep-interval 60 --max-sleep-interval 120 配置时绝大部分情况不会被风控。banmi 只抓字幕（远低于视频体），风险更低。

3.8 错误重试 + 失败 video 处理

// banmi/scripts/parse_and_index.mjs — 入库幂等 + retry queue
import { readFile } from 'node:fs/promises';
import { WebVTTParser } from 'webvtt-parser';
import { sql } from './db.mjs';

async function ingestSubFile(videoId, vttPath, meta) {
  const raw = await readFile(vttPath, 'utf-8');
  const parsed = new WebVTTParser().parse(raw, 'metadata');

  // upsert video meta 幂等
  await sql`
    INSERT INTO videos (id, channel, title, duration_sec, license, lang, fetched_at)
    VALUES (${videoId}, ${meta.channel}, ${meta.title},
            ${meta.duration}, ${meta.license}, ${meta.lang}, NOW())
    ON CONFLICT (id) DO UPDATE SET
      title = EXCLUDED.title, last_updated = NOW()`;

  // 批量 insert captions（每段一行）
  const rows = parsed.cues.map(c => ({
    video_id: videoId,
    start_sec: c.startTime,
    end_sec:   c.endTime,
    text:      c.text.replace(/<[^>]*>/g, '').trim(),
    lang:      meta.lang,
  }));
  await sql`INSERT INTO captions ${sql(rows)} ON CONFLICT DO NOTHING`;
}

// 失败 video 进 retry queue, 24h 后自动重试 3 次后人工 review

04字幕索引选型对比（5 候选 + 推荐）▼

banmi 估算字幕数据量上限：10000 视频 × 平均 1500 段 caption ≈ 1500 万行。对全文搜索引擎而言这属于"中等规模"。

4.1 5 候选横评

引擎 类型 性能（1500w 行） 运维 中文 typo phrase license 成本
Postgres FTS + GIN SQL 内建 毫秒级（GIN 索引下 query 40ms） 极轻（banmi 已有 PG） 需 zhparser ❌ 默认无 ✅ BSD 免费
Meilisearch 独立服务 极快（10ms instant search） 中（额外 1 个 service） ✅ 内建 ✅ 内建 ✅ MIT 自托管免费 / 云 $30+/月
Typesense 独立服务 极快（接近 Meili） 中（需要 cluster） ✅ 内建 ✅ 内建 ✅ GPL-3 自托管免费 / 云 $19+/月
Elasticsearch 独立服务 极快（生产级） 重（JVM / heap / cluster） 需 IK 插件 ✅ ✅✅ SSPL（受限） 自托管 ¥500+/月 server
OpenSearch 独立服务 同 ES 重 需插件 ✅ ✅✅ Apache 2.0 自托管 ¥500+/月 / AWS ¥2k+/月

4.2 推荐：Postgres FTS（再加 trigram 兜底）

banmi 主推

Postgres 16 + tsvector + GIN + pg_trgm

性能足够：oneuptime / paradedb 等公开 benchmark 显示 1000 万 行 + GIN tsvector，单次查询 40-150ms，banmi 1500 万行完全在能力范围内。

运维零增量：banmi 已经有 Postgres（Next.js + Postgres 是默认栈），不需要再起 Elasticsearch / Meilisearch 服务。Supabase 用户更受益。

跨表 JOIN：搜词时同时按 video.channel / video.cefr_level / video.license 过滤，纯 SQL，不需要数据同步。

persistent tsvector + GIN：把 tsvector 物化成 generated column + GIN 索引，query 时 0 计算开销，按 danielabaron 实测 比 query-time 计算快 100×。

typo 容忍：默认无 fuzzy；用 pg_trgm trigram 索引 + similarity score 弥补，对低频拼错查询能 fallback。

中文：banmi 是英文为主，中文搜索不在路径上；万一以后做中文，引 zhparser 或换 Meilisearch。

4.3 次选：Meilisearch（若运维资源富裕）

如果团队接受多 service

Meilisearch (self-host)

Instant search 体验最好（每键入一个字母都重排）—— 适合 banmi 学生在词卡上输入词时实时推荐相关片段。

typo / synonym / facet / highlight 全部开箱即用，相比 Postgres FTS 省去手写 ts_rank。

Schema 灵活：JSON 文档化，调字段不用 ALTER TABLE。

需要把 Postgres 数据同步到 Meilisearch（用 logical replication 或定时 ETL），多一道数据流。

月运维成本多 ¥100-300（VPS 单实例 RAM ≥ 4GB）。

4.4 不推荐：Elasticsearch / OpenSearch

overkill

Elasticsearch / OpenSearch

JVM heap 至少 4GB / shard 设计学习曲线陡 / cluster 运维（节点同步 / split brain）—— banmi 5500 词级别用量不需要这么重的引擎。

Elasticsearch 切了 SSPL 协议，AWS 不开源支持 → 用 OpenSearch 反而绑定云厂商。

中文需要 IK 插件 + 中文分词训练；banmi 是英文场景，多花的成本拿不到收益。

真到了 banmi 全国百万用户 / 全文搜整个 banmi 内容生态时，才考虑切 ES。

4.5 实战 SQL（Postgres FTS 推荐用法）

-- 1. captions 表加 tsvector generated column（持久化）
ALTER TABLE captions
  ADD COLUMN search_vec tsvector
  GENERATED ALWAYS AS (to_tsvector('english', text)) STORED;

-- 2. GIN 索引
CREATE INDEX captions_search_vec_gin
  ON captions USING GIN (search_vec);

-- 3. trigram 索引兜底（typo / 部分匹配）
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX captions_text_trgm
  ON captions USING GIN (text gin_trgm_ops);

-- 4. 查询：找包含 'significant' 的 caption，按相关度 + 频道质量排序
SELECT
  c.video_id,
  c.start_sec,
  c.end_sec,
  c.text,
  v.channel,
  v.title,
  ts_rank(c.search_vec, q.query)                         AS rank_text,
  ts_rank(c.search_vec, q.query) * v.quality_score      AS rank_final
FROM captions c
JOIN videos v ON v.id = c.video_id,
     to_tsquery('english', 'significant') q
WHERE c.search_vec @@ q.query
  AND v.kid_safe = true        -- 例如 K-G6 模式
ORDER BY rank_final DESC
LIMIT 20;
📊 性能基准：Postgres 17 + 1000 万行 captions + GIN 索引，single-word query ~40ms，phrase query ~80ms，trigram fuzzy ~150ms。banmi 上 Redis 缓存层后热门词 5ms 内返回。

05数据模型 / Schema 设计▼

4 张主表 + 2 张辅助表，跟半米总纲 §12 的 lexeme / vocab_card_template 完美对接。clip_refs[] 字段就是引用这套表的指针。

5.1 主表 · videos

videos · 视频元数据（一行 = 一条 YouTube 视频）
CREATE TABLE videos (
  id              TEXT        PRIMARY KEY,    -- YouTube video_id 11 字符
  channel_id      TEXT        NOT NULL,
  channel_name    TEXT        NOT NULL,       -- 'SciShow Kids'
  title           TEXT        NOT NULL,
  duration_sec    INTEGER     NOT NULL,
  lang            TEXT        NOT NULL,       -- 'en', 'en-US'
  license         TEXT        NOT NULL,       -- 'youtube_standard' | 'cc_by' | 'cc_by_nc' | 'public_domain'
  cefr_level      TEXT,                       -- A2/B1/B2/C1 — 人工或 ML 标
  quality_score   REAL        DEFAULT 1.0,    -- 频道质量加权（0.5-2.0）
  kid_safe        BOOLEAN     DEFAULT false,  -- K-G6 Kid Mode 过滤
  has_manual_sub  BOOLEAN     DEFAULT false,  -- 是否有 creator 人工字幕
  thumbnail_url   TEXT,
  fetched_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_updated    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  is_active       BOOLEAN     DEFAULT true    -- 视频失效 / 被删除 → false
);

CREATE INDEX videos_channel_id_idx     ON videos (channel_id);
CREATE INDEX videos_kid_safe_idx       ON videos (kid_safe) WHERE kid_safe;
CREATE INDEX videos_quality_score_idx  ON videos (quality_score DESC);

5.2 主表 · captions（核心，约 1500 万行）

captions · 字幕段（一行 = 一段字幕，平均 5-15 秒）
CREATE TABLE captions (
  id              BIGSERIAL   PRIMARY KEY,
  video_id        TEXT        NOT NULL REFERENCES videos(id) ON DELETE CASCADE,
  start_sec       REAL        NOT NULL,       -- 精度到 0.1 秒
  end_sec         REAL        NOT NULL,
  text            TEXT        NOT NULL,
  lang            TEXT        NOT NULL,
  is_auto         BOOLEAN     DEFAULT false,  -- true = YouTube ASR auto-generated
  search_vec      TSVECTOR    GENERATED ALWAYS AS (to_tsvector('english', text)) STORED,
  UNIQUE (video_id, start_sec)
);

CREATE INDEX captions_search_vec_gin   ON captions USING GIN (search_vec);
CREATE INDEX captions_text_trgm        ON captions USING GIN (text gin_trgm_ops);
CREATE INDEX captions_video_start      ON captions (video_id, start_sec);

-- 数据量估算：
# 10000 视频 × 1500 段/视频 = 15M 行
# 每行约 200 bytes（text + tsvector） → 3 GB 表体 + 1.5 GB GIN 索引 ≈ 4.5 GB

5.3 主表 · word_index（可选，做预聚合）

word_index · lemma 反向索引（缓存查 lemma 性能）
CREATE TABLE word_index (
  lemma           TEXT        NOT NULL,           -- 'significant'
  video_id        TEXT        NOT NULL REFERENCES videos(id),
  caption_id      BIGINT      NOT NULL REFERENCES captions(id),
  surface_form    TEXT        NOT NULL,           -- 'significantly'（原形）
  pos             TEXT,                           -- 'ADJ' / 'ADV' / 'VERB'
  position        SMALLINT,                       -- 在 caption 中第几个 token
  freq_rank       INTEGER,                        -- 该词在该视频出现次数
  PRIMARY KEY (lemma, video_id, caption_id, position)
);

CREATE INDEX word_index_lemma          ON word_index (lemma);
CREATE INDEX word_index_lemma_video    ON word_index (lemma, video_id);

-- 入库时用 spaCy / lemminflect lemmatize 后写入
-- 查 'significant' 时直接命中 word_index，bypass FTS 排序
-- 数据量估算：1500w caption × 平均 12 词 ≈ 1.8亿 行 → 较重，可改成 MV
⚠️ word_index 是 V0.3+ 的优化，不是 V0.3 上线必做。第一版直接走 captions FTS 即可，等真出现"高频词 query 慢" 再做这层。

5.4 辅助表 · search_log

search_log · 学生查询埋点
CREATE TABLE search_log (
  id              BIGSERIAL   PRIMARY KEY,
  student_id      UUID        NOT NULL,

6.2 URL 参数完整清单（2025 最新）

参数含义banmi 推荐

6.3 进阶：IFrame Player API（可控播放）

<!-- 1. 加载 YouTube IFrame API（一次性） -->
<script>
  // 异步加载
  const tag = document.createElement('script');
  tag.src = "https://www.youtube.com/iframe_api";
  document.head.appendChild(tag);

  // 全局 callback —— YouTube 加载完会调用
  let player;
  window.onYouTubeIframeAPIReady = function() {
    player = new YT.Player('banmi-clip-player', {
      height: '315',
      width:  '560',
      videoId: 'dQw4w9WgXcQ',
      playerVars: {
        start: 120,
        end:   128,
        autoplay: 1,
        rel:      0,
        cc_load_policy: 1,
        playsinline:    1,
      },
      events: {
        onReady:       onReady,
        onStateChange: onStateChange,
      }
    });
  };

  function onReady(e) {
    e.target.setPlaybackRate(0.75);    // 降速 0.75 倍 — 适合 K-G6 学员
  }

  // 监听 currentTime → 到 end 自动回到 start（实现"片段循环"）
  let loopRange = { start: 120, end: 128 };
  function onStateChange(e) {
    if (e.data === YT.PlayerState.PLAYING) {
      // 每 100ms 检查一次
      const timer = setInterval(() => {
        if (player.getPlayerState() !== YT.PlayerState.PLAYING) {
          clearInterval(timer);
          return;
        }
        const t = player.getCurrentTime();
        if (t >= loopRange.end) {
          player.seekTo(loopRange.start, true);  // 跳回起点
        }
      }, 100);
    }
  }

  // 切下一个片段（学生看完一个换下一个）
  function playNextClip(videoId, startSec, endSec) {
    loopRange = { start: startSec, end: endSec };
    player.loadVideoById({
      videoId,
      startSeconds: startSec,
      endSeconds:   endSec,
    });
  }
</script>

6.4 关键 API 方法表

方法用途banmi 用法
seekTo(sec, allowSeekAhead)跳到指定时间实现片段循环 / 学生 replay
loadVideoById({videoId, startSeconds, endSeconds})加载新视频切下一个片段

6.5 时间精度

start / end URL 参数只接受整数秒；想要毫秒级（雅思口语跟读评估场景）必须用 IFrame API 的 seekTo(120.5)。banmi 字幕段 start_sec REAL 已经存的是 float，所以查 caption 时拿到的是 120.34，URL 路径下退化到 120 没问题。

6.6 iOS Safari 自动播放限制

📱 移动端三条铁律
  1. iOS Safari 默认禁止 autoplay 非静音视频 —— banmi 词卡片段播放必须用户手势触发（学生点按钮才能开始）
  2. 必须加 playsinline=1，否则 iOS 会强制全屏 → 出词卡场景
  3. 循环切片段时第一次必须用户点过 player，后续 loadVideoById 才能不破坏 autoplay 权限

6.7 字幕高亮目标词（前端覆盖层方案）

YouTube iframe 内的字幕是 native 渲染的，banmi 没法直接改 iframe 内部 DOM。两条路：

  1. (推荐) 隐藏 YouTube 字幕，自己渲染：URL 加 cc_load_policy=0，banmi 在 iframe 上层覆一个透明 div，配合 getCurrentTime() 实时显示自家字幕 + 高亮目标词。优点：完全可控 / 缺点：要做时间轴同步。
  2. (简单) 显示 YouTube 原字幕 + 词卡侧栏单独显示该片段全文：iframe 字幕不动，banmi 在 player 下方再放一个 caption 块，目标词加 <mark> 高亮。技术零成本，体验已经够。

08字幕质量过滤策略▼

8.1 三层过滤链

从抓到入库分 3 道闸门：

  1. 第 1 道：抓取时优先选人工字幕 — --write-subs --write-auto-subs 一起开，但解析时如果同一视频两种都有，保留人工版本，把 is_auto=false 写进 captions
  2. 第 2 道：解析时正则清洗 + 段落合并 — 去 styling tags / 修复段落断裂 / 合并相邻 1 秒内段落
  3. 第 3 道：入库后 quality_score 加权 — 频道质量 × 字幕类型 × CEFR 难度匹配

8.2 auto 字幕 vs 人工字幕的真实差距

📊 2025 准确率数据汇总
  • 人工字幕：99%+ 准确率，标点完整，专有名词正确，时间戳精度 ±0.1s
  • YouTube auto（2024+）：教育 / talk 类清晰录音 85-95%（cisdem 测试）；嘈杂 / 室外 60-70%
  • WER (Word Error Rate)：精挑频道 5-10%；混合频道 10-20%
  • 缺标点：auto 字幕几乎不带句号，影响 banmi"按句搜词"算法

8.3 时间戳精度修正

auto 字幕常有 ±0.5-1 秒偏差（领先或滞后）。banmi 用三种方法补：

  • 偏移补偿：抽样 50 个频道 caption，对比片段实际播放点 vs caption start_sec，算出系统性 offset（如该频道平均 +0.3s）
  • 段落对齐：相邻 caption 段时间间隔过小（<0.2s）的合并成一段，避免片段 cut 在词中间
  • 截取窗口扩展：banmi 前端给 iframe start = caption.start_sec - 0.5，end = caption.end_sec + 0.5，缓冲 1 秒让学生听到完整句

8.4 标点恢复（auto 字幕专属）

// banmi 用 deepmultilingualpunctuation 模型 / OpenAI gpt-4o-mini 给 auto 字幕补标点
// 输入: "the climate is changing we need to act now scientists agree"
// 输出: "The climate is changing. We need to act now. Scientists agree."

async function restorePunctuation(rawText) {
  const resp = await openai.chat.completions.create({
    model: 'gpt-4o-mini',
    messages: [
      { role: 'system', content: 'Add proper punctuation and capitalization to the following transcript. Do not change wording.' },
      { role: 'user', content: rawText }
    ],
    temperature: 0,
  });
  return resp.choices[0].message.content;
}

  • 保留 attribution（频道名 / 链接到 YouTube 原视频）
⚠️ 灰区（可做但需谨慎）
  • YouTube ToS 第 II.5 节技术上禁止"automated access" — yt-dlp 法律地位多年灰区。德州地方法院 2024 判决支持 yt-dlp 合法性，但 RIAA 仍试图诉讼
  • 实际执法：YouTube 不会去盯 banmi 这种小型内部产品（除非每天百万请求 / 公开 API）
  • 缓解：限速 + 不公开 API + 不下载视频本体 = 风险最小化
🚫 不要做（红区）
  • 下载视频本体存到 banmi 服务器
  • 二次剪辑视频内容
  • 把字幕数据库做成公开 API 收费
  • 批量抓取 channel 后做"banmi 视频中心"分发
  • 抓影视片段（Netflix / 迪士尼 / 院线）—— Layer 3 路径，V0.4+ 再评估

10.6 紧急 fallback 路径

万一 YouTube 改 ToS 严打 yt-dlp，banmi 三条 fallback：

  1. 切换到 YouTube Data API v3（官方 API）抓字幕 —— 配额 10000 unit/天，commercial 申请可申请增加。功能受限但合规
  2. 跟教育视频提供方（TED / Khan Academy）直接签授权，拿到他们的字幕导出权限
  3. banmi 自己积累的 自录教学视频 形成独立资产，YouTube 字幕只是补充

11.2 对应的 /api/clips Next.js 实现

// app/api/clips/route.ts
import { NextResponse } from 'next/server';
import { sql } from '@/lib/db';
import { getCached, setCached } from '@/lib/redis';

export async function GET(req: Request) {
  const { searchParams } = new URL(req.url);
  const lemma    = searchParams.get('lemma')?.trim().toLowerCase();
  const kidSafe  = searchParams.get('kid_safe') === 'true';
  const limit    = Number(searchParams.get('limit') ?? 5);
  if (!lemma) return NextResponse.json({ clips: [] });

  const cacheKey = `clips:${lemma}:${kidSafe}:${limit}`;
  const cached = await getCached(cacheKey);
  if (cached) return NextResponse.json(cached);

  const clips = await sql`
    SELECT
      c.video_id, c.start_sec, c.end_sec, c.text,
      v.channel_name, v.title, v.thumbnail_url
    FROM captions c
    JOIN videos v ON v.id = c.video_id
    WHERE c.search_vec @@ plainto_tsquery('english', ${lemma})
      AND v.is_active = true
      AND (${kidSafe}::bool = false OR v.kid_safe = true)
    ORDER BY
      ts_rank(c.search_vec, plainto_tsquery('english', ${lemma}))
        * v.quality_score DESC
    LIMIT ${limit}`;

  const payload = { clips, lemma, count: clips.length };
  await setCached(cacheKey, payload, 86400); // 24h
  return NextResponse.json(payload);
}
📦 这段代码可以直接进 banmi monorepo —— Next.js app router + @vercel/postgres + 已有 Redis 接入，30 行就实现了完整 widget 后端。

12FAQ for 阿杰（10 条）▼

Q1为啥不上 Elasticsearch？业界都用啊。＋

因为 banmi 不需要。ES 是为"全 Stack Overflow 级别全文搜索 + 复杂聚合 + 多语种"设计的，banmi 上限 1500 万行 captions + 英文 single-word 搜索，Postgres FTS GIN 索引下毫秒级返回，根本撑不到 ES 发挥的场景。多一个数据库实例 = 多一套部署 / 监控 / 同步流。等 banmi 全国百万用户 + 全产品（阅读 / 听力 / 写作 / 字幕）统一搜索时再切 ES 不迟。

Q2yt-dlp 会被 YouTube 封吗？如果哪天 ban 了 banmi 怎么办？＋

会，但不致命。yt-dlp 跟 YouTube 的"反爬战争"已经打了 5 年，每次 YouTube 改 player encoding，yt-dlp 几天内就跟上。banmi 抓字幕（不抓视频）触发风控的概率非常小。万一真被 ban，三条 fallback：(1) 切到 YouTube Data API v3 官方接口；(2) 跟 TED / Khan 这种内容方直接签授权；(3) banmi 累积自录视频形成独立资产。不要把鸡蛋全放 yt-dlp 一个篮子，第二批入库就开始接洽 1-2 家内容方签授权。

Q3现在 V0.2 还没上呢，写这份方案是不是太早了？＋

不早。理由：(1) 总纲已经画了 §4.5.3 草图，团队对架构有共识，落地细节越早 fix 越好；(2) Layer 2 的开发周期 3 人月 + 内容入库 1 个月 = 4 个月，从 V0.2 上线到达到 €300 触发条件可能就是 4-6 个月，需要提前启动；(3) 这份方案本身可以拿去做技术招聘 / 工程师 onboarding 材料；(4) 写细了发现 Layer 2 比想象简单（Postgres FTS 就够），反过来让 V0.2 立项更有信心。

Q4字幕索引会不会越涨越大压垮 Postgres？＋

不会。粗算 10000 视频 = 1500 万行 = 4-5 GB（含 GIN 索引）。banmi 哪怕到 50000 视频也就 25 GB，DigitalOcean $48 档 SSD 完全装得下。Postgres 17 单表 GIN 索引上限是几十亿行，1500 万只是小儿科。真正的瓶颈不是 Postgres，是 yt-dlp 抓取速度（10000 视频按 30 秒/视频 ≈ 83 小时单线程，多 IP 并行可压到 10-20 小时）。索引方案要担心的不是性能，是更新策略（每天增量）和失效清理（每周扫一次）。

Q5为啥不直接用 PostgreSQL Supabase 的 pgvector 做语义搜？＋

因为词汇搜索是关键词精确匹配，不是语义搜。学生搜 "significant" 想看的就是这个词出现在哪些视频里，不想要 "important" / "major" 的近义词混进来。pgvector 适合"输入一段中文翻译 → 找意思相近的英文片段"这种场景，属于 V0.4+ 探索方向。V0.3 Layer 2 用 FTS 就够，pgvector 可以做为加强项放在第二期。

Q6移动端 iframe 自动播放真的不行吗？iOS 学员怎么办？＋

iOS Safari 不允许 autoplay 非静音视频，这是系统级限制不能绕。banmi 的解决方案：(1) 把 player 包在一个 "🎬 看真实场景" 按钮里，学生点了才开始 — 反正学生背词时也是主动点片段；(2) iframe 加 playsinline=1 关键防止 iOS 强制全屏；(3) 切下一个片段时利用之前已获得的"用户手势权限"做 loadVideoById，连续播放是 OK 的。第一个点击是关键，后续都丝滑。

Q7片段循环 / 慢速播放是不是过度设计？＋

不是，是 K-G6 学员的刚需。小学生记单词需要"看 5-10 遍同一句"才能记住，慢速 0.75x 让他们听清每个音节。这两个功能在 YouGlish 都有（YouGlish Loop + Speed），banmi 自建必须 parity。代码量 30 行（用 IFrame API setInterval + setPlaybackRate），不算复杂。Q-架构二的"重复播放设计"已经写在总纲 §4.5.3，这就是技术对齐。

Q810 万开发成本会不会失控？工程师拖期怎么办？＋

风险控制三条：(1) 第 0 周做 1 人天 PoC — 一个 SciShow Kids 视频跑通 yt-dlp + Postgres FTS + iframe 播放，验证整个 stack 通；(2) 第一批只入 4 个频道 / 1500 视频，scope 严格冻结，不允许"顺便也支持 X"； (3) 拆成 3 个 sprint（W1-3 抓取入库 / W4-6 API + 前端 / W7-8 内容质量 + 上线），每 sprint 都有可演示物。这套技术栈我评估难度低于 banmi 阅读 LE 模块，3 人月是保守估算，1 名熟手工程师 6 周可以跑完核心。

Q9字幕索引到底是 banmi 单独服务，还是塞进 banmi monorepo？＋

塞进 monorepo。理由：(1) 索引服务的下游就是 banmi 词卡，唯一消费者；(2) 共用 Postgres 实例可以做 cross-table JOIN（词卡 schema × clips 一次查询出结果，不用做两次 API call）；(3) 部署运维省一套；(4) 数据迁移省同步。具体路径：banmi/apps/web/app/api/clips/route.ts + banmi/scripts/yt-dlp/fetch_subs.sh，cron 跑在 banmi worker VPS 上。未来 banmi 拆 microservice 时再单拆，不是 V0.3 的事。

Q10第 1 年开支 ¥10-15 万对小创业来说不便宜，能不能压到 5 万以内？＋

可以，但要牺牲：(1) 开发外包：找熟悉 yt-dlp + Postgres 的兼职工程师，6 周 ¥3-5 万搞定核心代码；(2) 内容压到 500 视频：只入 SciShow Kids + Crash Course Kids + VOA Learning English 三个，覆盖 K-G6 + 中学，¥3-5 千搞定；(3) VPS 用最便宜的 Hetzner CPX21（€8/月 ≈ ¥60），性能比 DO 同档好；(4) Joy/Dong 内容审校先用 AI 兜底，季度后再人工抽检。总：¥4-6 万第一年。代价是 Layer 2 服务 cover 词量从 10000 词降到 3000 词，对早期 5500 雅思词覆盖率从 100% 降到 60%。
