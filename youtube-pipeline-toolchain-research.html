YouTube 流水线工具链：开源项目能不能补强我们的「下载 + 转码 + 字幕 + 喂大模型」管线

📅 2026-05-31 🔍 ~45 次检索 + GitHub API 实查 📦 扒了 youtube-api / youtube-downloader / youtube-transcript-api 三个 topic 🎯 视角：阿杰的课程精读 + 研究摘要管线

带着一个问题去扒 GitHub：我们的 yt-dlp + ffmpeg + Opus 管线，有没有更快/更稳的零件可换或可补？

结论先抛：yt-dlp 不要换，它是底座，全场没有对手。但管线有三个真空位值得补—— ① 字幕抓取改用 youtube-transcript-api（比 yt-dlp 抓字幕更快更轻）； ② 「看一小时视频→1分钟摘要」直接接 fabric，一行命令跑通； ③ yt-dlp 在 SABR 时代建议配 PO Token provider 做缓解，这是大多数人忽略的命门（注意：是缓解手段，非稳定性保证）。

01一句话结论（先看这个）▼

这次研究的本质是一个「换零件」判断题，不是「找新玩具」。我带着阿杰那条「下载→转码→拉字幕→喂大模型」的流水线，逐个工位去问：现有零件够不够好？有没有更快/更稳的替代或补充？

✅ 直接抄走的三条

  1. 字幕工位换 youtube-transcript-api[1]：纯 HTTP 抓字幕，不下视频、不调浏览器，机制上比 yt-dlp 抓字幕轻得多（具体倍数未实测，见 Ch15 存疑）。课程精读 + 研究摘要两条线都受益。机制推断
  2. 研究摘要工位接 fabric[2]：fabric -y <url> 一行抓字幕喂 LLM，自带 extract_wisdom / summarize pattern，「一小时视频→1分钟摘要」当天就能跑通。多源
  3. 给 yt-dlp 配 PO Token provider[3]：YouTube 在逐步铺开 SABR + PoToken 强制，部分客户端/场景下裸 yt-dlp 会拿不到格式。配上 bgutil-ytdlp-pot-provider 是一个缓解手段（非稳定性保证）。单源·官方 wiki

⛔ 不要碰的三条

  1. 不要换掉 yt-dlp：167k 星、每天更新、1800+ 站点、内置字幕/转码/SponsorBlock，没有任何项目能替代它当底座。多源
  2. 「超快 MP3 转换 API」（Fast-YouTube-to-MP3-Converter-API）不要用：它不是自托管代码，是挂在 RapidAPI 上的付费第三方黑盒，要 key、有配额、随时可能停。已核实
  3. 多平台下载（TikTok/X/IG/FB）暂时是 nice-to-have：yt-dlp 本身已经支持，但对「课程精读 + 研究」这两条线没有实际刚需，先不立项。判断

02我们现有的两条管线（基准线）▼

评估「换不换」之前，先把现有管线摆清楚，否则容易被新项目的营销话术带跑。

管线 A：课程精读（banmi-course）

现状：yt-dlp 抓字幕 + 下视频 → ffmpeg 按 180s 截关键帧 → Opus(LLM) 清洗英文逐字稿 + 中文笔记 + 费曼重讲 → HTML。

痛点假设：下载/抓字幕这一段如果能更快更稳，整条线提速明显；视频体积大，gitignore 后只 push html + jpg。

管线 B：研究流程（想要的能力）

目标：「看一小时视频 → 1 分钟摘要」。这条线现在还没有现成积木，是这次研究最该补的缺口。

关键差异：管线 A 要的是完整逐字稿 + 视觉帧（深读）；管线 B 要的是快速摘要 + 打标签（扫读），两者对工具要求不同。

评估原则（贯穿全文）

  • 能不能真提速，而不是换汤不换药（换个 wrapper 底层还是 yt-dlp，不算提速）。
  • license 能不能商用（半米是商业项目，AGPL/GPL 要警惕）。
  • 是不是活的（最近 30 天有 push）、要不要 API key / 付费。

为什么没有替代品

yt-dlp 是 youtube-dl 的 fork，但早已青出于蓝。youtube-dl 现在基本停更，YouTube 一改内部接口就挂；yt-dlp 维护节奏极快，主动适配平台变化[5]。市面上几乎所有「下载器」——Seal、ytDownloader、cobalt 桌面、各种 GUI——底层调的都是 yt-dlp。换它等于换地基。

关于「速度」的诚实拆解

yt-dlp 支持 --concurrent-fragments N 把 DASH/HLS 分片并行下载；配 aria2c 当外部下载器，1GB 视频约 2 分钟（裸 youtube-dl 约 5 分钟）[5]。所以「想更快」的答案不是换工具，是把现有 yt-dlp 调对参数。

⚠️ 但有个坑：单 IP 用 --concurrent-fragments 16 会被 YouTube 限速甚至临时封[5]。课程精读是批量场景，并发拉太猛适得其反，建议 4 起步。

「换汤不换药」陷阱：很多看起来「更快/更现代」的下载项目（Seal、ytdlnis、各种 web UI）只是 yt-dlp 的壳。对我们这种已经命令行跑 pipeline 的场景，套个壳没有任何提速，反而多一层依赖。已核实

那 yt-dlp 的真痛点是什么？

不是速度，是稳定性——2026 年 YouTube 的 SABR + PO Token 让裸 yt-dlp 时不时抓不到格式（详见 Ch10）。所以正确动作是「留 yt-dlp + 补 PO Token provider」，不是「换掉 yt-dlp」。

一站式「贴链接拿文件」的下载器，支持 20+ 平台（TikTok/IG/X/Reddit/SoundCloud/Vimeo…），自身不缓存内容、像个漂亮代理[6]。

  • 🟡 它面向「人手动贴链接」，不是为我们这种命令行批量 pipeline 设计；而且 YouTube 那一侧它本来也得绕同样的 PoToken 问题，没有比 yt-dlp 更省心。
不接。它解决的是「给普通人一个网页下载器」，不是「给已有 pipeline 提速」。我们的场景 yt-dlp 完胜。
🐍
JuanBindez/pytubefix
1.5k ★ · Python · MIT · push 2026-05-30
轻量备选

pytube 的活跃 fork（原版 pytube 基本已死[7]）。纯 Python 库，能下视频/流/字幕/playlist，带 PO Token 支持，MIT license 可商用。

06「超快 MP3/MP4 转换 API」的真相（阿杰点名项）▼

阿杰特意点名 Fast-YouTube-to-MP3-Converter-API，我专门核实了。结论：不是你想的那种东西，不要用。

⚠️
matthew-asuncion/Fast-YouTube-to-MP3-Converter-API
381 ★ · "HTML" · 无 license · push 2026-05-16
避坑

名字像个开源转换引擎，实际上这个 repo 只是文档——真正的转换跑在作者挂在 RapidAPI 上的服务器后端[8]。

它的真实身份：

  • 🔴 要 RapidAPI key，freemium 模式：免费档有月配额上限，超了要付费[8]。
  • 🔴 转换是黑盒，发 video ID 给它、它返回下载链接，你不知道也控制不了后端怎么转、用什么质量。
  • 🔴 没有可自托管的后端——repo 里 GitHub 标的语言是「HTML」就是信号，里面是各语言调用示例，不是引擎。
  • 🔴 无 license，商业项目依赖一个第三方付费 API 当管线零件，随时可能涨价/停服/被 YouTube 封。
坚决不接。「快」是因为它在别人服务器上转、把成本和风险转嫁给你。我们已经有 yt-dlp+ffmpeg 在自己机器上转，可控、免费、无配额，没理由换成一个付费黑盒。

为什么会有一堆这种「转换 API」？ 它们的目标用户是「想在自己网站/App 里加个下载按钮、又不想自己跑 yt-dlp 服务器」的开发者，用付费换省事。对我们不成立——我们本来就在自己机器上跑 pipeline，自托管成本几乎为零。判断

07字幕层：youtube-transcript-api（最值得抄的一个）▼

📝
jdepoix/youtube-transcript-api
7.7k ★ · Python · MIT · v1.2.4 (2026-01-29)
强烈推荐·接

纯 Python 库，抓 YouTube 字幕/转录（含自动生成字幕），不要 API key、不要 headless 浏览器[1]。这是这次研究里跟我们管线咬合最紧的一个。

为什么比 yt-dlp 抓字幕好：

  • ⚡ 不下视频、不起浏览器，直接打 YouTube 内部字幕接口；yt-dlp 抓字幕要走完整提取流程，机制上重得多（具体快多少未跑基准，见 Ch15）。
  • 🧩 API 干净：YouTubeTranscriptApi().fetch(video_id) 一行拿到带时间戳的字幕；能列全部可用语言、能优先人工字幕、能翻译。
  • 📤 多格式输出：txt / json / srt / webvtt / csv——正好对上我们 yt-to-obsidian 那个「双语 CSV 直传」模式，省掉一道转换。关联判断
  • 📜 MIT、活跃（v1.2.4 今年 1 月发布，35 个 release）。
两条管线都接。课程精读用它取代 yt-dlp 抓字幕那一步（视频还是 yt-dlp 下）；研究摘要线用它当「拿文本」的第一棒。

⚠️ 必须知道的两个风险

  • 它用的是 YouTube 未公开接口，作者明说「不保证哪天不挂」[1]。所以它只能当「快路径」，失败要能 fallback 回 yt-dlp 抓字幕或 whisper 兜底。
  • 云 IP 会被封：文档承认 YouTube 已大面积封 AWS/GCP/Azure 等云厂商 IP，库内置了 Webshare 住宅代理支持来绕[9]。在阿杰本机（住宅 IP）跑没问题；如果哪天搬到云服务器批量跑，要配代理。

配套小工具：dermasmid/scrapetube（512★, MIT）能列出一个频道/playlist 的全部 video id，不用 API key[4]。配合 transcript-api，就能「给个频道→批量抓全频道字幕」，对 SciShow Kids 那种整频道精读场景有用。

09喂大模型积木：fabric / onefilellm（研究摘要线的核心）▼

阿杰问「有没有现成积木直接接 LLM 做摘要/打标签」。有，而且很成熟。这是管线 B（研究摘要）当天就能跑通的关键。

🧵
danielmiessler/Fabric
41.9k ★ · Go · MIT · push 2026-05-28
研究摘要·强推

「用 AI 增强人类」的开源框架，核心是一堆版本化的 prompt「pattern」。内置 YouTube 功能：fabric -y "<url>" 自动抓字幕喂给 LLM，配 pattern 出结构化结果[2]。

为什么正好对上「一小时视频→1分钟摘要」：

  • 🎯 自带 extract_wisdom（抽洞见/金句/引用/takeaway）和 summarize（结构化摘要）pattern，对长视频字幕效果极好[2]。
  • 🔌 支持多 LLM 后端：OpenAI / Anthropic / Gemini / 本地 Ollama——跟阿杰海外视角 + 现有 Opus/Gemini 栈完全兼容。
  • 📜 MIT 可商用，41.9k 星、Go 写的、维护极活跃。
研究摘要线直接接。最小路径：装 fabric → 配 Gemini/Claude key → fabric -y URL --pattern extract_wisdom。「打标签」也能自己写个 tag pattern。这是这次研究 ROI 最高的一接。
📦
jimmc414/onefilellm
2.0k ★ · Python · MIT · push 2026-02-08
多源聚合喂 LLM

把多种来源（GitHub repo/PR、arXiv 论文、网页、YouTube 字幕）聚合清洗成单个文本文件，自动复制到剪贴板、报告 token 数，方便整块喂 LLM[11]。底层 YouTube 那部分正是用 youtube-transcript-api。

备选。如果研究场景是「把一个视频 + 几篇论文 + 一个 repo 一起喂给模型对比」，onefilellm 比 fabric 更合适（多源聚合）。纯视频摘要还是 fabric 更顺。

注意我们其实已经有半套：yt-to-obsidian 和 yt-to-notebooklm skill 已经在做「YouTube→笔记/知识库」。fabric 的价值是补上「快速扫读摘要」这个更轻的档位——不是要做精读笔记，就想 1 分钟知道这视频讲了啥值不值得深看。两者互补，不冲突。关联判断

10PO Token / SABR：2026 年被忽略的命门▼

这一章是阿杰没问、但比「换不换工具」更重要的事。如果不处理，无论用 yt-dlp 还是别的，2026 年都会越来越多失败。

发生了什么：2025-2026 年 YouTube 逐步铺开 SABR（服务端自适应码率） + PO Token（Proof of Origin）强制——yt-dlp 官方 wiki 用词是「rolling out」，目前只有部分客户端/场景要求，不是对所有下载一刀切[3]。这不是 yt-dlp 的 bug，是 YouTube 的反爬升级，所有下载工具都受影响。

⚠️ 别把错误对号入座错：常见的 This content isn't available, try again later 在 yt-dlp 文档里主要归因于请求频率过高（限速），不一定是 PoToken 缺失。真正的 PoToken/SABR 症状是「只剩 storyboard 图、所有音视频格式拿不到」「nsig extraction failed」。先分清是哪种，再决定上 PoToken provider 还是降并发/加 sleep。官方 wiki

🔑
Brainicism/bgutil-ytdlp-pot-provider
548 ★ · TypeScript · GPL-3.0 · push 2026-04-10
配套·接

yt-dlp 的 PO Token provider 插件，自动生成 BotGuard token 让下载继续可用[12]。两种装法：

  • HTTP Server 模式（Docker）：跑个容器（默认 4416 端口），yt-dlp 向它要 token，最稳，推荐。
  • Script 模式（插件）：装成 yt-dlp 插件 + 本地 Node.js，按需生成，不用常驻服务。
课程精读 pipeline 要常态批量下载，建议上 Docker server 模式。这是「让 yt-dlp 在 SABR 时代更稳」的一个缓解手段（不是稳定性保证——它自己 README 也说有了 PoToken 也不保证绕过 403/bot 检查）。license 是 GPL-3.0，当外部 Docker 服务/插件调用、不静态链接进我们代码，传染风险低，但商业分发要留意。

这条发现的元价值：阿杰问的是「换更快的工具」，但真实瓶颈是稳定性（被 YouTube 拦）而非速度。研究的价值之一就是把问题问对——这条线该投的资源是「PoToken provider + 住宅 IP」，不是「找更快的下载器」。判断

11多平台下载（TikTok/X/IG/FB）值不值得搞▼

阿杰直接问了：「多平台下载对我们有没有实际用，还是 nice-to-have？」我的答案：当前是 nice-to-have，且能力已经白送，不用额外立项。

第一个事实：yt-dlp 本身就支持

yt-dlp 支持 1800+ 站点，TikTok（可下无水印）、Instagram（帖/reels/stories）、Twitter/X、Facebook、Vimeo、Twitch、Reddit、SoundCloud 全覆盖[13]。所以我们不需要为「多平台」再找工具——已经有了。

⚠️ 但社交平台抽取质量参差：IG/FB 常需 --cookies-from-browser 传浏览器 cookie 才能下；平台一改内部结构就临时坏，靠社区频繁更新 extractor[13]。能下 ≠ 像 YouTube 那样稳。

第二个判断：跟我们两条线的相关性

平台对课程精读对研究摘要结论
YouTube核心载体核心载体刚需
TikTok / Reels / Shorts太短、无深度内容偶尔有知识短视频nice-to-have
X / Twitter无偶尔存个讲解 thread 视频nice-to-have
Instagram / FB无基本无无关

结论：多平台对「课程精读 + 研究」没有刚需。但因为 yt-dlp 已经白送了这个能力，不用做任何额外工作就具备——哪天真要存个 X 上的讲解视频，同一条 yt-dlp 命令换个 URL 就行。不立项，但留着这个口子。（顺带：我们已有 save-tweet skill 处理 X 文字推文存档，视频可以并到那条线。）判断

12转码层：ffmpeg 还需要补吗？▼

阿杰管线里 ffmpeg 负责截关键帧 + 转格式。这次扫 GitHub没有发现值得替换 ffmpeg 的项目——ffmpeg 是音视频处理的事实标准底座，跟 yt-dlp 一样属于「不换」类。

真要优化的话，是参数不是工具：

  • 截关键帧用 -vf "select='eq(pict_type,I)'" 抽 I 帧，或现有 180s 定时截帧——按内容密度调间隔比换工具有用。
  • 音频抽取喂 ASR 时，-ar 16000 -ac 1 降到 16kHz 单声道，whisper 系列要的就是这个格式，文件更小转得更快。

这些是「调对参数」而非「找新积木」，跟 Ch4 的速度结论一脉相承。

诚实声明：本次研究焦点在 youtube-api 生态的下载/字幕/摘要工具，对 ffmpeg 替代品没有做穷尽搜索（GPU 加速转码如 NVENC、或 Rust 的音视频库等方向未深挖）。如果转码成为实测瓶颈，值得单开一份研究。存疑·未尽

13推荐项目 Top 5（带接入位）▼

从全部扫描里挑出真正该并入工作流的五个，按 ROI 排序。

🥇 #1 fabric — 研究摘要线的发动机

41.9k★ MIT。fabric -y URL 一行把视频字幕喂 LLM，自带 extract_wisdom/summarize。直接实现阿杰要的「一小时视频→1分钟摘要」。接管线 B（研究摘要）。当天可跑通，ROI 最高。

🥈 #2 youtube-transcript-api — 字幕快路径

7.7k★ MIT。纯 HTTP 抓字幕，不下视频不起浏览器，比 yt-dlp 抓字幕快一档，多格式输出对上我们 CSV 直传模式。接管线 A + B 的「取文本」第一棒。

🥉 #3 bgutil-ytdlp-pot-provider — 让 yt-dlp 2026 年继续稳

548★ GPL-3.0。补 PO Token，解决 SABR 时代 yt-dlp 抓不到格式的命门。接管线 A（课程精读批量下载）。比换任何下载器都管用。（GPL：作为外部 Docker 服务/插件调用、不与我们代码静态链接，传染风险低；但要留意。）

4️⃣ #4 faster-whisper — 字幕兜底引擎

23.3k★ MIT。无字幕/字幕烂时本地转录，比原版 whisper 快 4 倍。接字幕层第三级 fallback。（要词级时间戳做「点词跳秒」再上 whisperX。）

5️⃣ #5 onefilellm — 多源聚合喂 LLM（备选）

2.0k★ MIT。视频 + 论文 + repo 聚合成一个文件喂模型。研究场景需要跨源对比时再上，纯视频摘要 fabric 优先。

共同点：四个是 MIT/BSD（可放心商用），只有 bgutil 是 GPL-3.0（当外部 Docker 服务/插件调用、不静态链接进我们代码，传染风险低）；全部活跃维护；全部不要付费 API key（fabric/onefilellm 要你自己的 LLM key，但那是你本来就有的）。这是刻意筛的——避开了 AGPL 服务端代码（cobalt）和付费第三方黑盒（Fast-MP3-API）。

↓

目标管线形态（改造后）

管线 A（课程精读）改造：

字幕：youtube-transcript-api（快路径）→ fallback yt-dlp → fallback faster-whisper
视频：yt-dlp + bgutil-pot-provider（+ --concurrent-fragments 4）
截帧/转码：ffmpeg（不变，调参）
清洗/笔记：Opus（不变）

管线 B（研究摘要）新建：

fabric -y URL --pattern extract_wisdom → 1 分钟摘要
（底层 transcript-api 抓字幕；LLM 后端用现有 Gemini/Claude key）
想跨源对比 → 换 onefilellm 聚合多个来源再喂。

落地顺序（ROI 排序，先做最划算的）

  1. 先装 fabric 跑通管线 B——零改造、当天见效、直接交付阿杰要的能力。
  2. 再把课程精读的字幕工位换成 transcript-api——小改、提速明显、有 fallback 兜底。
  3. 然后上 PoToken provider——等真撞到下载失败时再上（按需，不是预防性投入）。
  4. faster-whisper / onefilellm 留作兜底/备选，需要时再接。

15风险、存疑与没做到的部分（诚实交代）▼

🔴 风险 1：未公开接口随时可能挂

transcript-api、pytubefix、cobalt 全部依赖 YouTube 未公开接口，作者都明说不保证稳定[1]。所以推荐的架构永远带 fallback——不把鸡蛋放一个篮子。yt-dlp 因为维护最猛，是最稳的那一个，所以留它当底座。

🔴 风险 2：云 IP 封禁

transcript-api / yt-dlp 在云服务器（AWS/GCP）批量跑会被封 IP[9]。阿杰本机住宅 IP 跑没问题；要上云批量化必须配住宅代理（Webshare 等），这是额外成本。

🟡 失败模式分类（别把所有报错都当 PoToken）

工程化时要按症状分诊，对症下药，不要一报错就上 PoToken provider：

  • 限速（"try again later"）→ 降并发 + 加 --sleep-requests / backoff，不是 PoToken 问题。
  • PoToken/SABR（只剩 storyboard 图 / nsig extraction failed）→ 上 PoToken provider + 装 JS runtime（Deno）。
  • IP 封（云 IP）→ 住宅代理。
  • 年龄/地区限制→ cookies / 换区，部分视频无解。
  • 私有/已删/会员/直播回放/Shorts→ 各有不同行为，要单独处理。
  • 无字幕 / 自动字幕烂→ 走 ASR（whisper）兜底。

配套运维：yt-dlp 版本要勤更（stable vs nightly）、设重试预算、字幕做缓存。运维建议

🟡 存疑 1：transcript-api 实测速度未跑基准

「比 yt-dlp 快一个量级」是基于「不下视频不起浏览器」的机制推断 + 社区共识，我没有在本机跑过 head-to-head 基准测试。机制上确定更快，具体倍数存疑。单源+机制推断

🟡 存疑 2：fabric 对中文/双语视频的摘要质量

fabric 的 pattern 主要是英文社区调的，对中英混合或纯中文视频的 extract_wisdom 效果我没实测。质量主要取决于后端 LLM（Gemini/Claude 都强），但 pattern 提示词可能需要本地化微调。未实测

🟡 没做到：ffmpeg 替代/GPU 转码未深挖

本研究聚焦 youtube-api 生态，对转码层（NVENC GPU 加速、Rust 音视频库）没做穷尽搜索。如果转码是实测瓶颈，需单开研究（见 Ch12）。

🟡 知道存在、本轮未深挖的相关项目（诚实标注）

这次主要靠 topic 检索 + 名气筛，下面这些明确该补研究但本轮没展开，列出来不让它们成为盲区：

  • whisper.cpp — 本地 CPU / Apple Silicon ASR，阿杰是 Mac，可能比 faster-whisper 更贴本机（无需 CUDA）。字幕兜底层值得跟 faster-whisper 实测对比。
  • yt-dlp-ejs / 官方列出的 PoToken provider（如 getpot 系列） — PoToken 这块不止 bgutil 一个方案，JS runtime（Deno）方向也能解 nsig，应做横向对比再定。
  • ytdl-sub — 声明式频道/playlist 订阅式批量下载，对「整频道精读」（SciShow Kids 那种）可能比手写脚本省事。
  • MeTube / Tube Archivist — 更重的 yt-dlp 队列/归档系统，如果课程精读要做成常驻服务可参考。
  • 官方 YouTube Data API v3 — 列频道/playlist 元数据，scrapetube（非官方爬虫）该跟它的配额/key 取舍对比，不该只推爬虫。

这些不影响本报告的核心结论（yt-dlp 留 + transcript-api/fabric/PoToken），但若要把管线工程化成常驻服务，建议就这几个再补一轮。未尽·待补

?FAQ▼

Q一句话：yt-dlp 到底换不换？+

不换。167k 星、每天更新、1800+ 站点，没有替代品。它的问题不是慢（调参就能更快），是被 YouTube 拦（配 PoToken provider 缓解，不是彻底解决）。换它等于换地基，纯亏。

Q那「超快转换 API」为什么显得那么快？+

因为它在别人的服务器上转，把算力成本和封禁风险转嫁给服务商，你付费换省事。我们本来就在自己机器上跑、免费、可控，没理由换成付费黑盒（还要 RapidAPI key、有月配额、随时可能停服）。

Q我就想要「一小时视频→1分钟摘要」，最短路径？+

装 fabric → 配一个 LLM key（Gemini/Claude）→ fabric -y "视频URL" --pattern extract_wisdom。完事。这是 ROI 最高的一接，零 pipeline 改造。

Qtranscript-api 和 yt-dlp 抓字幕，差在哪？+

transcript-api 只打字幕接口，不下视频、不起浏览器；yt-dlp 抓字幕要走完整提取流程，机制上重。课程精读改用 transcript-api 抓字幕（视频仍 yt-dlp 下），字幕这一步机制上更轻（具体倍数未实测）。但 transcript-api 用未公开接口，要带 fallback——真正独立的兜底是 ASR（whisper），不是 yt-dlp 字幕。

Qcobalt 那么火（40k 星），为什么不推？+

三个原因：① 公共实例下 YouTube 已被封，要自托管跑 Docker；② AGPL-3.0 license 对商业项目有传染风险；③ 它是给「人手动贴链接」设计的网页下载器，不是给我们这种命令行批量 pipeline。火是因为对普通用户好用，跟我们场景不匹配。

QPO Token 是什么？我现在 yt-dlp 用着没事啊？+

YouTube 2025-2026 上的反爬机制，要求请求带「证明来自合法客户端」的 token。现在没事是因为住宅 IP + 还没大面积铺开，但会越来越多「This content isn't available」。撞到了就装 bgutil-ytdlp-pot-provider（Docker）。属于「按需上」，不用现在预防性投入。

Q没有字幕的视频怎么办？+

三级 fallback：transcript-api 抓不到 → yt-dlp 自动字幕 → 还不行用 faster-whisper 本地转录（比原版 whisper 快 4 倍）。要做「点单词跳到视频对应秒」就上 whisperX（带词级时间戳）。

Q多平台（TikTok/X/IG）要单独搞工具吗？+

不用。yt-dlp 已经支持这些平台（1800+ 站点），换个 URL 就能下。但对「课程精读+研究」没刚需，属于白送的 nice-to-have——留着口子，不立项。

Qpytube 13k 星，为什么说它死了？+

星是历史积累，维护已停滞，YouTube 一变就坏，社区共识「pytube is dead」。要用活跃 fork pytubefix。这也是个教训：选项目看活跃度（最近 push）比看星数重要。

Q这些工具会不会有法律/合规问题？+

下载受版权保护内容用于再分发有风险；用于内部学习/精读/研究风险较低。半米是商业项目，建议：① 优先抓字幕（文本，风险低于下视频）；② 选 MIT/BSD license 工具避开 AGPL 传染；③ 涉及把下载内容做成产品功能时单独走合规判断。非法律意见

Qfabric 和我们现有的 yt-to-obsidian skill 冲突吗？+

不冲突，互补。yt-to-obsidian 做的是「深度双语笔记」（精读档）；fabric 做的是「快速扫读摘要」（1分钟判断值不值得深看）。两个档位，按需求选。

Q如果只能接一个，接哪个？+

fabric。因为它直接补上我们现在完全没有的能力（快速视频摘要），零改造、当天跑通、ROI 最高。其他三个是优化现有管线，fabric 是开新能力。
